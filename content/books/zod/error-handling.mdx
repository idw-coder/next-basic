`safeParse` が失敗したとき、`result.error` に入っているのが `ZodError` です。既定のメッセージは**英語で、開発者向けの文言**なので、そのままユーザーに見せることはできません。この章でその整形方法を扱います。

## issues — 失敗の一覧

`ZodError` の中身は `issues` という配列です。失敗した項目の数だけ要素が入ります。

```ts
const schema = z.object({ name: z.string().min(1), age: z.number() });
const result = schema.safeParse({ name: '', age: 'x' });

result.error.issues;
// [
//   { code: 'too_small', path: ['name'],
//     message: 'Too small: expected string to have >=1 characters' },
//   { code: 'invalid_type', path: ['age'],
//     message: 'Invalid input: expected number, received string' }
// ]
```

主なプロパティです。

| プロパティ | 内容 |
| --- | --- |
| `code` | 失敗の種類（`invalid_type` / `too_small` / `custom` など） |
| `path` | どの項目か。ネストは `['user', 'name']`、配列は `['tags', 1]` |
| `message` | 人が読むメッセージ |

<Marker>`path` があるので「どの入力欄のエラーか」を機械的に振り分けられます。</Marker>

## 整形用のヘルパー

`issues` の配列をそのまま画面に流すのは扱いづらいので、用途別の変換関数が用意されています。

| 関数 | 返る形 | 向いている用途 |
| --- | --- | --- |
| `z.treeifyError(error)` | 構造をそのまま辿れる入れ子オブジェクト | ネストしたフォーム |
| `z.flattenError(error)` | `fieldErrors` / `formErrors` の平坦な形 | 1階層のフォーム |
| `z.prettifyError(error)` | 人が読む複数行の文字列 | ログ・開発時の確認 |

```ts
z.flattenError(result.error);
// {
//   formErrors: [],
//   fieldErrors: {
//     name: ['Too small: expected string to have >=1 characters'],
//     age: ['Invalid input: expected number, received string']
//   }
// }
```

```ts
z.treeifyError(result.error);
// { errors: [], properties: {
//     name: { errors: ['Too small: ...'] },
//     age:  { errors: ['Invalid input: ...'] } } }
```

```ts
console.log(z.prettifyError(result.error));
// ✖ Too small: expected string to have >=1 characters
//   → at name
// ✖ Invalid input: expected number, received string
//   → at age
```

`fieldErrors` は「項目名 → メッセージ配列」なので、フォームの各入力欄の下に出すのがそのまま書けます。ネストの無いフォームなら `flattenError` が一番扱いやすいです。

<Callout type="info" title="parseで受け取る場合">
`parse` は失敗すると `ZodError` を throw します。`catch (e)` の中で `e instanceof z.ZodError` を確かめれば、同じ `z.flattenError(e)` に渡せます。書き方は[parseとsafeParseの章](/books/zod/parse-and-safeparse)にあります。
</Callout>

### ネストがあるとflattenErrorは位置の情報を落とす

`flattenError` がキーにするのは `path` の**先頭の要素だけ**です。オブジェクトの入れ子や配列があると、どの階層・何番目の要素で失敗したのかが結果から消えます。

```ts
const schema = z.object({
  user: z.object({ name: z.string() }),
  tags: z.array(z.string()),
});
const result = schema.safeParse({ user: { name: 1 }, tags: ['a', 2] });

result.error.issues.map((issue) => issue.path);
// [['user', 'name'], ['tags', 1]]

z.flattenError(result.error).fieldErrors;
// {
//   user: ['Invalid input: expected string, received number'],
//   tags: ['Invalid input: expected string, received number']
// }
```

`user.name` の失敗が `user` に、`tags[1]` の失敗が `tags` にまとめられました。`treeifyError` なら、オブジェクトは `properties`、配列は `items` を辿って元の位置まで降りられます。

```ts
const tree = z.treeifyError(result.error);

tree.properties?.user?.properties?.name?.errors;
// ['Invalid input: expected string, received number']

tree.properties?.tags?.items?.[1]?.errors;
// ['Invalid input: expected string, received number']
```

失敗していない位置には値が入りません（上の例では `items[0]` が空です）。そのため `?.` で辿ります。

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">
入力欄が1階層に並ぶフォームは `flattenError`、住所や明細行のように入れ子・配列があるフォームは `treeifyError`、と覚えておけば足りるよ。
</SpeechBubble>

## フォームの入力欄の下にエラーを出す

`fieldErrors` を state に入れ、項目名で引いて表示します。Reactで書くと次の形になります。

```tsx
'use client';

import { useState } from 'react';
import { z } from 'zod';

const schema = z.object({
  name: z.string().min(1, '名前を入力してください'),
  email: z.email('メールアドレスの形式で入力してください'),
});

type FieldErrors = { name?: string[]; email?: string[] };

export function SignupForm() {
  const [errors, setErrors] = useState<FieldErrors>({});

  const handleSubmit = (event: React.FormEvent<HTMLFormElement>) => {
    event.preventDefault();
    const values = Object.fromEntries(new FormData(event.currentTarget));
    const result = schema.safeParse(values);

    if (!result.success) {
      setErrors(z.flattenError(result.error).fieldErrors);
      return;
    }
    setErrors({});
    // result.data を送信する
  };

  return (
    <form onSubmit={handleSubmit} noValidate>
      <label htmlFor="name">名前</label>
      <input id="name" name="name" aria-invalid={Boolean(errors.name)} aria-describedby="name-error" />
      {errors.name && <p id="name-error" role="alert">{errors.name[0]}</p>}

      <label htmlFor="email">メールアドレス</label>
      <input id="email" name="email" aria-invalid={Boolean(errors.email)} aria-describedby="email-error" />
      {errors.email && <p id="email-error" role="alert">{errors.email[0]}</p>}

      <button type="submit">登録</button>
    </form>
  );
}
```

押さえる点は3つです。

- `fieldErrors` の値は**配列**です。1つの項目に複数の検証が失敗すると複数入るので、1件だけ見せるなら `[0]` を取ります
- 失敗していない項目は、キーそのものが存在しません。`errors.name` が `undefined` かどうかで表示を切り替えられます
- `aria-invalid` と `aria-describedby` を付けると、スクリーンリーダーが入力欄とエラー文を結び付けて読み上げます

入力のたびに検証したい、送信中の状態も管理したい、という段階になったら[React Hook Formと組み合わせる章](/books/zod/react-hook-form)の方法が向いています。

## メッセージを日本語にする3つの方法

### 1. ロケールを適用してまとめて日本語にする

Zodには日本語ロケールが同梱されています。アプリの起動時に1回設定すれば、既定のメッセージがすべて日本語になります。

```ts
import { z } from 'zod';

z.config(z.locales.ja());
```

適用の前後で、同じ検証のメッセージがこう変わります。

| 検証 | 適用前 | 適用後 |
| --- | --- | --- |
| `z.string()` に数値 | `Invalid input: expected string, received number` | `無効な入力: stringが期待されましたが、数値が入力されました` |
| `z.string().min(8)` | `Too small: expected string to have >=8 characters` | `小さすぎる値: stringは8文字以上である必要があります` |
| `z.email()` | `Invalid email address` | `無効なメールアドレス` |

<Callout type="warning" title="ロケールだけではユーザー向けの文章にならない">
「stringが期待されましたが」のように、翻訳はされていても**開発者向けの語彙が残ります**。エンドユーザーに見せる画面では、次の方法で項目ごとに文言を書く方が親切です。ロケールは「書き漏らした箇所の受け皿」と考えるとちょうどよいです。
</Callout>

### 2. メソッドの第2引数で指定する

個別の検証にメッセージを添えます。もっとも手軽で、実務でよく使う形です。

```ts
z.string().min(8, 'パスワードは8文字以上で入力してください');
z.array(z.string()).min(1, 'タグを1つ以上選んでください');
```

### 3. スキーマ生成時に `error` で指定する

型そのものが違う場合（文字列を期待したのに数値が来た等）のメッセージは、スキーマの引数で指定します。

```ts
z.string({ error: '文字列で入力してください' });
```

`error` には関数も渡せます。引数の `issue` から入力値（`issue.input`）や制約の値（`issue.minimum` など）を読めるので、「未入力」と「型が違う」でメッセージを分けたり、上限・下限の数値を文言に埋め込んだりできます。

```ts
const name = z.string({
  error: (issue) => (issue.input === undefined ? '必須です' : '文字列で入力してください'),
});

name.safeParse(undefined).error?.issues[0].message; // '必須です'
name.safeParse(1).error?.issues[0].message; // '文字列で入力してください'

const password = z.string().min(8, {
  error: (issue) => `${issue.minimum}文字以上で入力してください`,
});

password.safeParse('abc').error?.issues[0].message; // '8文字以上で入力してください'
```

<Callout type="warning" title="v3の `required_error` は v4では効きません">
Zod 3にあった `z.string({ required_error: '必須です' })` は、v4では**エラーにも警告にもならず、単に無視されます**。メッセージが英語のまま変わらないときは、この書き方が残っていないか確認してください。v4では `error` に統一されています。
</Callout>

## 実務での組み立て方

APIのハンドラでは、`safeParse` の失敗をそのまま400として返す形が定番です。

```ts
const result = createUserSchema.safeParse(body);

if (!result.success) {
  return Response.json(
    { message: '入力内容を確認してください', errors: z.flattenError(result.error).fieldErrors },
    { status: 400 },
  );
}
```

<Marker>全項目分のエラーがまとめて返るので、フロントは1回のレスポンスですべての入力欄にエラーを表示できます。</Marker>1件ずつ指摘して何度も送信させる、という体験を避けられます。

エラーの中身をそのままレスポンスに載せて大丈夫なの？
</SpeechBubble>

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">
`fieldErrors` くらいなら問題ないよ。ただし `error` オブジェクト全体をJSONにするのは避けよう。内部のスキーマ構造が推測できる情報が混ざることがあるからね。返すのは「項目名」と「メッセージ」だけに絞るのが安全だよ。

## よくあるハマりどころ

### 英語のメッセージがそのまま画面に出る

既定のメッセージは英語です。ロケール適用か、項目ごとのメッセージ指定が必要です。

### `required_error` を書いても変わらない

v3の書き方です。v4では `error` を使います。

### `refine` のメッセージが `Invalid input` になる

[refineの章](/books/zod/refine-and-transform)のとおり、`refine` は第2引数を省略すると `Invalid input` になります。

### エラーが画面に出ない

`path` が空のissueは `fieldErrors` ではなく `formErrors` に入ります。`fieldErrors` だけを表示しているフォームでは、どの入力欄にも出ません。オブジェクト全体に掛けた `refine` がこの形になります。

```ts
const schema = z
  .object({ password: z.string(), confirm: z.string() })
  .refine((v) => v.password === v.confirm, { error: 'パスワードが一致しません' });

z.flattenError(schema.safeParse({ password: 'a', confirm: 'b' }).error!);
// { formErrors: ['パスワードが一致しません'], fieldErrors: {} }
```

`path` を指定すると、その項目の `fieldErrors` に入ります。

```ts
.refine((v) => v.password === v.confirm, {
  error: 'パスワードが一致しません',
  path: ['confirm'],
});
// { formErrors: [], fieldErrors: { confirm: ['パスワードが一致しません'] } }
```

### `error.flatten()` や `error.format()` に取り消し線が付く

Zod 3の書き方です。v4でもメソッドは残っていて動きますが、非推奨になりました。`error.flatten()` は `z.flattenError(error)` に、`error.format()` は `z.treeifyError(error)` に書き換えます。置き換えの一覧は[v3からv4への移行の章](/books/zod/zod-v4-migration)にまとめています。

## ちゃんと使うためのポイント

- `ZodError` の本体は `issues` の配列。`code` / `path` / `message` を持つ
- <Marker>1階層のフォームなら `z.flattenError()` の `fieldErrors` が一番扱いやすい</Marker>
- 入れ子や配列があるなら `z.treeifyError()`。`flattenError` は `path` の先頭しか残さない
- `path` が空のissueは `formErrors` に入る。入力欄に出したいなら `refine` に `path` を付ける
- `z.config(z.locales.ja())` で既定メッセージを日本語化できるが、語彙は開発者向けのまま
- ユーザーに見せる文言は、メソッドの第2引数か `{ error: '...' }` で個別に書く
- v3の `required_error` はv4では無視される
