## インストール

```bash
npm init playwright@latest
```

このコマンドで以下が自動的にセットアップされます。

- `playwright.config.ts` — 設定ファイル
- `tests/example.spec.ts` — 最小構成のサンプルテスト
- `package.json` への `@playwright/test` の追加
- ブラウザのダウンロード（Chromium, Firefox, WebKit）

作られるファイルは、[Playwright公式のインストール手順](https://playwright.dev/docs/intro)（英語）に記載されているものです。古いバージョンでは `tests-examples/` というフォルダも作られましたが、現在の手順には含まれていません。

<Callout type="info">
### 既存プロジェクトへの追加

既存のプロジェクトに追加する場合も同じコマンドです。TypeScript、テストディレクトリの場所、GitHub Actions の設定を対話的に選べます。

</Callout>

### ブラウザだけを入れ直す

Playwrightは、テストに使うブラウザを自分でダウンロードして使います。PCに入っているChromeは使いません。`@playwright/test` を更新したあとや、CIのように毎回まっさらな環境で動かすときは、ブラウザのダウンロードを別に実行します。

```bash
# ブラウザをダウンロードする
npx playwright install

# Linux（CIやWSL）では、ブラウザが使うOSのライブラリも一緒に入れる
npx playwright install --with-deps
```

ブラウザが入っていない状態でテストを実行すると、次のエラーで止まります。

```
Error: browserType.launch: Executable doesn't exist at /…/chromium-1234/chrome-linux/chrome
Looks like Playwright was just installed or updated.
Please run the following command to download new browsers:

    npx playwright install
```

</SpeechBubble>

`@playwright/test` のバージョンが上がると、対応するブラウザのバージョンも変わるんだ。パッケージは新しくなったのに、ブラウザは古いまま、という状態になっている。メッセージのとおり `npx playwright install` を実行すれば直るよ。

## 設定ファイル

`playwright.config.ts` の主要な設定項目です。

```ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,

  reporter: 'html',

  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
    {
      name: 'firefox',
      use: { ...devices['Desktop Firefox'] },
    },
    {
      name: 'webkit',
      use: { ...devices['Desktop Safari'] },
    },
  ],

  webServer: {
    command: 'npm run dev',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});
```

### 主要な設定

| 設定 | 意味 |
|---|---|
| `testDir` | テストファイルの場所 |
| `fullyParallel` | テストを並列実行するか |
| `retries` | 失敗時のリトライ回数 |
| `baseURL` | `page.goto('/')` のベースURL |
| `trace` | トレース（操作の記録）の取得タイミング |
| `webServer` | テスト前にサーバーを起動するコマンド |

<Callout type="note">
### webServerの設定

`webServer` を設定すると、テスト実行前に自動でサーバーが起動し、テスト後に停止します。`reuseExistingServer: true` にすると、すでに起動済みのサーバーがあればそれを使います。開発中は手動でサーバーを起動しておく方が効率的です。

</Callout>

## テストの書き方

### 基本構造

```ts
import { test, expect } from '@playwright/test';

test('ページタイトルが正しい', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveTitle(/サイト名/);
});
```

### 要素の取得方法

Playwrightはアクセシビリティを基準にした **ロケーター** で要素を取得します。

```ts
// ロールで取得（推奨）
page.getByRole('button', { name: '送信' })
page.getByRole('textbox', { name: 'メールアドレス' })
page.getByRole('link', { name: 'ホーム' })

// ラベルで取得
page.getByLabel('パスワード')

// テキストで取得
page.getByText('ログインに成功しました')

// プレースホルダーで取得
page.getByPlaceholder('検索...')

// テストIDで取得（他の方法で取れない場合の最終手段）
page.getByTestId('user-avatar')
```

<Figure src="/images/stepup_suit_man_color-1.png" alt="ステップアップする男性のイラスト" maxWidth="300px" />

### ユーザー操作

```ts
// クリック
await page.getByRole('button', { name: '送信' }).click();

// テキスト入力
await page.getByLabel('メールアドレス').fill('alice@example.com');

// セレクトボックス
await page.getByLabel('都道府県').selectOption('東京都');

// チェックボックス
await page.getByLabel('利用規約に同意する').check();

// キーボード操作
await page.keyboard.press('Enter');
```

### アサーション

```ts
// 要素が表示されている
await expect(page.getByText('成功')).toBeVisible();

// 要素が表示されていない
await expect(page.getByText('エラー')).not.toBeVisible();

// URLが正しい
await expect(page).toHaveURL('/dashboard');

// 入力値が正しい
await expect(page.getByLabel('名前')).toHaveValue('Alice');

// 要素の数
await expect(page.getByRole('listitem')).toHaveCount(5);
```

## 自動待機（Auto-waiting）

Playwrightの大きな特徴が **自動待機** です。操作対象の要素が準備できるまで自動で待ちます。

```ts
await page.getByRole('button', { name: '送信' }).click();
```

`click()` の場合、Playwrightは次の条件がすべて満たされるまで待ってからクリックします（[公式ドキュメントのActionability](https://playwright.dev/docs/actionability)、英語）。

| 待つ条件 | 意味 |
|---|---|
| ロケーターが1つの要素に定まる | 一致する要素がちょうど1つある |
| Visible | 表示されている |
| Stable | アニメーション中でない、またはアニメーションが終わっている |
| Receives Events | 他の要素に覆われていない |
| Enabled | `disabled` になっていない |

条件が満たされないまま待ち続けると、テスト1件あたりの制限時間（既定は30秒）に達して `Test timeout of 30000ms exceeded.` で失敗します。「送信ボタンが `disabled` のまま」「読み込み中の表示がボタンを覆ったまま」といった不具合は、このタイムアウトとして現れます。

この自動待機があるため、`sleep` や `waitForTimeout` を使う必要がほとんどありません。テストが安定し、かつ不要な待ち時間がなくなります。

## UIモードでテストを視覚的に確認する

Playwrightの **UIモード** は、テストの実行をブラウザ上で視覚的に確認できる機能です。

```bash
npx playwright test --ui
```

UIモードでは以下のことができます。

- **テストの実行状況をリアルタイムで確認** — どのステップが今実行されているかが画面上でわかる
- **各ステップのスクリーンショット** — テストの各操作時点での画面状態を確認
- **タイムトラベル** — 任意のステップに戻って、その時点の画面状態を確認
- **DOMのインスペクト** — 各時点でのDOM構造を確認
- **ネットワークリクエスト** — テスト中に発生したリクエストを確認

    classDef feature fill:#8b5cf6,color:#fff,stroke:#7c3aed

テストが失敗したとき、UIモードで実行すると「どのステップで何が起きたか」を視覚的に確認できるため、デバッグが格段に楽になります。

## コード生成（Codegen）

Playwrightにはブラウザ上の操作からテストコードを自動生成する **Codegen** 機能があります。

```bash
npx playwright codegen http://localhost:3000
```

ブラウザが起動し、操作するとリアルタイムでテストコードが生成されます。生成されたコードをそのまま使うのではなく、**テストの骨組みを素早く作るための出発点** として活用します。

<Callout type="info">
### Codegenの活用法

Codegenは、ロール・テキスト・テストIDの順に優先してロケーターを選びます（[公式ドキュメントのTest generator](https://playwright.dev/docs/codegen-intro)、英語）。`getByRole` で書かれたコードがそのまま出てくるので、ロケーターを書き直す必要はあまりありません。手を入れるのは、確認用に押しただけの余計な操作の削除と、「何を確かめるテストか」が伝わるアサーションの追加です。

</Callout>

## 導入直後によく出るエラー

### strict mode violation

```
Error: locator.click: Error: strict mode violation: getByRole('button', { name: '削除' }) resolved to 3 elements
```

ロケーターに一致する要素が複数あるときに出ます。Playwrightのロケーターは、操作の対象が1つに定まらないとエラーにします（[公式ドキュメントのStrictness](https://playwright.dev/docs/locators#strictness)、英語）。一覧の各行に「削除」ボタンがある画面が典型例です。

対処は、対象を1つに絞ることです。

```ts
// 行を先に特定してから、その中のボタンを探す
await page
  .getByRole('row', { name: '田中太郎' })
  .getByRole('button', { name: '削除' })
  .click();

// 名前の一部が一致して複数になるなら、完全一致にする
await page.getByRole('button', { name: '削除', exact: true }).click();
```

`.first()` を付ければエラーは消えますが、「何番目か」に頼るテストは、並び順が変わると別の要素を操作します。上のように、意味で絞るほうが壊れにくくなります。

### Playwright Test did not expect test() to be called here

```
Error: Playwright Test did not expect test() to be called here.
Most common reasons include:
- You are calling test() in a configuration file.
- You are calling test() in a file that is imported by the configuration file.
- You have two different versions of @playwright/test.
```

VitestやJestを使っているプロジェクトにPlaywrightを足したときに、`npm test` で出ることがあります。原因は、単体テストのランナーが、Playwrightのテストファイル（`*.spec.ts`）まで拾って実行していることです。

対処は、どちらのランナーがどのファイルを担当するかを分けることです。

| 方法 | 設定 |
|---|---|
| フォルダで分ける | Playwrightのテストを `e2e/` に置き、`playwright.config.ts` の `testDir` を `./e2e` にする |
| 単体テスト側で除外する | Vitestなら `test.exclude` に `e2e/**` を足す |

```ts
// vitest.config.ts
import { configDefaults, defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    exclude: [...configDefaults.exclude, 'e2e/**'],
  },
});
```

`configDefaults.exclude` を展開しているのは、`exclude` を自分で書くと、`node_modules` などの既定の除外設定が上書きされて消えるためです。

## テストの実行

```bash
# 全テストを実行
npx playwright test

# 特定のファイルを実行
npx playwright test tests/login.spec.ts

# 特定のブラウザで実行
npx playwright test --project=chromium

# UIモードで実行
npx playwright test --ui

# ヘッドモード（ブラウザ表示あり）で実行
npx playwright test --headed

# テストレポートを表示
npx playwright show-report
```

### テストレポート

`reporter: 'html'` の設定で、テスト結果がHTMLレポートとして生成されます。失敗したテストのスクリーンショット、トレース、エラーメッセージが確認できます。

## トレースビューア

`trace: 'on-first-retry'` の設定で、リトライ時にトレースが記録されます。トレースには操作の一つ一つのスクリーンショット、ネットワークリクエスト、コンソールログが含まれます。

```bash
npx playwright show-trace trace.zip
```

CIで失敗したテストのトレースをダウンロードして確認する、というワークフローが定番です。

<Callout type="warning">
### トレースのサイズに注意

`trace: 'on'` にすると全テストでトレースが記録されますが、ファイルサイズが大きくなります。CIでは `on-first-retry`（リトライ時のみ）にするのが実用的です。

</Callout>

## まとめ

- <Marker>`npm init playwright@latest` で導入できる。設定ファイル、ブラウザ、サンプルテストが自動生成される</Marker>
- `playwright.config.ts` で `baseURL`、`webServer`、`trace` などを設定
- ロケーターは **`getByRole`、`getByLabel`** を優先。`getByTestId` は最終手段
- **自動待機** により `sleep` が不要。テストが安定し高速
- **UIモード** でテストの実行を視覚的に確認。タイムトラベルでデバッグ
- **Codegen** でブラウザ操作からテストの骨組みを自動生成
- `Executable doesn't exist` は、ブラウザが入っていない。`npx playwright install` を実行する
- `strict mode violation` は、ロケーターに一致する要素が複数ある。行やラベルで絞り込む

何をどの粒度でテストするかの考え方は、[E2Eテストのシナリオ設計](/books/integration-and-e2e-testing/07-scenario-design)で扱っています。
