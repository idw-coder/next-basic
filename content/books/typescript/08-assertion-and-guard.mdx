## 型アサーション（as）

型アサーションは、TypeScriptの型推論結果を開発者が上書きする手段です。

**構文：** `値 as 型`

```tsx
// getElementById の戻り値は HTMLElement | null
const input = document.getElementById('my-input') as HTMLInputElement;

// HTMLInputElement として扱えるので、input 固有のプロパティが使える
console.log(input.value);
```

`as` を書いた瞬間、コンパイラは推論をやめて「開発者の申告」を信じます。データそのものは何も変わらず、**型の見え方だけが変わる**点がポイントです。

<Callout type="note">
### もう1つの記法 `<型>値`

`const input = <HTMLInputElement>document.getElementById('my-input');` のような山かっこ記法もあります。ただしJSX（Reactのタグ記法）と構文が衝突するため `.tsx` ファイルでは使えず、現在は `as` を使うのが一般的です。

</Callout>

### どういう時に使用するか

具体的な使用シーンは主に以下の3つです。

| 使用シーン                                    | 説明                                                                                                                                                                                                                                       |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| DOM要素を取得する時                           | `document.getElementById('my-input')` などで要素を取得すると、TypeScriptはそれを単なる「一般的なHTML要素」としか認識しません。`HTMLInputElement` など具体型に断言することで、`.value` など要素固有のプロパティがエラーにならずに使えます。 |
| 外部データ（APIのレスポンスなど）を受け取る時 | `JSON.parse()` の結果など、外部から来たデータは中身がわからないため `any` や `unknown` 型になります。「このデータは `User` 型だ」と断言して、プログラム内で扱いやすくします。                                                              |
| イベントハンドラの引数を使う時                | クリック時などの `event.target` は抽象的な型になっているため、ボタンやリンクなど具体的なHTML要素の型に断言して操作します。                                                                                                                 |

コードで書くと次のようになります。

```tsx
// ① DOM要素を取得する時
const input = document.getElementById('email') as HTMLInputElement;
input.value = 'test@example.com';

// ② 外部データ（APIのレスポンスなど）を受け取る時
type User = { id: number; name: string };
const user = JSON.parse(jsonText) as User;
console.log(user.name);

// ③ イベントハンドラの引数を使う時
document.querySelector('button')?.addEventListener('click', (event) => {
  const target = event.target as HTMLButtonElement;
  target.disabled = true;
});
```

型アサーションは「コンパイラの安全装置をオフにして無理やり通す」行為です。そのため、本当にその型である確証がある時だけ使う（乱用しない）のが鉄則です。

### 型アサーションは最後の手段

「TypeScriptの画面上ではエラーが出ないのに、実際にプログラムを動かすとエラーで落ちる（実行時エラー）」というリスクが上がります。

コンパイラが「本当にその型で合ってる？危険だよ」と警告してくれていたはずのものを、プログラマが強制的に黙らせてしまうからです。

### 型アノテーションと型アサーションの違い

**[型アノテーション](/books/typescript/02-basic-types)** と **型アサーション** は、

- **型アノテーション『注釈』**

  変数や関数を定義する際に、「これにはこの型のデータが入る」と最初から明示的に指定するもの

- **型アサーション『断定』**

  コンパイラが自動で推論した型に対して、プログラマが「いいや、これはこの型として扱え」と強制的に上書きするものです

どちらも型を指定する役割を持ちますが、使われる目的やタイミングに違いがあります。

```tsx
// 型アノテーション：定義時に「この型が入る」と宣言する
// 中身が User と合っていなければ、その場でコンパイルエラーになる
const user1: User = { id: 1, name: 'Tanaka' };

// 型アサーション：推論結果を「この型として扱え」と上書きする
// 中身が本当に User かどうかはチェックされない
const user2 = JSON.parse(jsonText) as User;
```

<Marker>アノテーションはコンパイラのチェックを受ける「宣言」、アサーションはチェックを迂回する「断言」です。</Marker>

### 型アサーションと型キャストの違い

**型キャスト** は別の型に変換する手段です。

一方、**型アサーション** はデータそのものは一切変更しません。TypeScriptのコンパイラに対する「見せ方（認識）」だけを変えます。

下記は型キャストの例

```tsx
const n = 123; // nは数値（Number）
const s = String(n); // sは文字列（String）の "123" に変換される
```

## 非nullアサーション（!）

非nullアサーションは、変数の後ろに `!` を付けることで「この値は `null` や `undefined` ではない」とコンパイラに断言する記法です。

値が `null` または `undefined` になりうる型（例：`string | null`）に対して、開発者が「ここでは絶対に値が存在する」と保証することで、`null` チェックなしでプロパティやメソッドにアクセスできるようになります。

```tsx
function getLength(text: string | null) {
  // ① text は null の可能性があるため、そのまま .length にアクセスするとエラー
  // console.log(text.length); // ❌ 'text' is possibly 'null'.

  // ② ! を付けて「null ではない」と断言すると、エラーにならずアクセスできる
  console.log(text!.length);
}
```

よく使われるのは、DOM要素の取得結果のように「存在するはずだが、型の上では `null` の可能性が残る」ケースです。

```tsx
// getElementById の戻り値は HTMLElement | null
const button = document.getElementById('submit')!;
// ! を付けることで HTMLElement として扱える
button.addEventListener('click', () => {});
```

<Callout type="column">
### 「!」は実行時の安全を保証しない

非nullアサーションも型アサーション（`as`）と同じく、**コンパイラのチェックを黙らせるだけ**で、実際に値が `null` でないことを保証するわけではありません。

もし実行時に本当に `null` や `undefined` だった場合、`Cannot read properties of null` のような**実行時エラー**で落ちてしまいます。コンパイラが警告してくれていた危険を、プログラマが強制的に押し切る行為だという点を忘れないでください。

</Callout>

そのため、可能な限り `!` ではなく、より安全な代替手段を優先します。

| 手段                            | 例                          | 特徴                                                   |
| ------------------------------- | --------------------------- | ------------------------------------------------------ |
| **オプショナルチェーン（?.）**  | `text?.length`              | `null` / `undefined` なら処理を中断し `undefined` を返す |
| **Null合体演算子（??）**        | `text ?? '初期値'`          | `null` / `undefined` のときに既定値を使う              |
| **型ガード（if文によるチェック）** | `if (text !== null) { ... }` | 実行時に確認するため最も安全                            |

`!` は「他に手段がなく、かつ値が存在することが確実に分かっている」場合の最後の手段として使うのが鉄則です。

<Callout type="column">
### 「!」は TypeScript 専用、「?.」「??」は JavaScript の機能

代替手段として挙げた3つは、由来が異なります。

- **非nullアサーション（`!`）** は TypeScript 独自の構文です。コンパイル時にコンパイラへ型を伝えるだけで、JavaScript にトランスパイルされると**消えてなくなります**。そのため実行時には一切影響しません。
- 一方、**オプショナルチェーン（`?.`）** と **Null合体演算子（`??`）** は JavaScript の演算子（ES2020〜）です。コンパイル後も残り、実行時に実際に `null` / `undefined` を判定して動作します。

```tsx
// TypeScript（コンパイル前）
console.log(text!.length); // 非nullアサーション
console.log(text?.length); // オプショナルチェーン
```

```js
// JavaScript（コンパイル後）
console.log(text.length); // ! は消える
console.log(text?.length); // ?. はそのまま残る
```

つまり `!` だけが「型の世界だけの存在」で、`?.` と `??` は「実行時にも生きている本物の処理」だという違いがあります。

</Callout>

## 型ガードで型安全を保証する

型ガード（Type Guard）とは、
プログラムの実行時にデータの中身をチェックすることで、TypeScriptの型を安全に絞り込む仕組みです。

```tsx
function printValue(value: string | number) {
  // ① この時点では string か number か分からないため、文字列専用の value.length はエラーになる

  if (typeof value === 'string') {
    // ② 型ガードが働き、このブロック内では確実に「string（文字列）」として認識される！
    console.log(value.length); // エラーにならない
  } else {
    // ③ ここでは自動的に残りの「number（数値）」として認識される
    console.log(value * 10);
  }
}
```

`typeof` のほか、`instanceof` や `in` を使った基本の絞り込みは[05章の型の絞り込み（Narrowing）](/books/typescript/05-narrowing)で扱いました。ここでは、その絞り込みロジックを**再利用可能な関数**として切り出す方法を見ていきます。

### ユーザー定義型ガード（is）

同じ判定ロジックをあちこちの `if` 文に書くのは冗長です。そこで判定処理を関数に切り出し、**戻り値の型の位置に「型述語（type predicate）」を書く**ことで、呼び出し元でも型の絞り込みが効くようにしたものが、ユーザー定義型ガードです。

**構文：** `function 関数名(引数名: 型): 引数名 is 絞り込み後の型`

| 部分                     | 説明                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `引数名: 型`             | チェックしたい値。外部データの検証では `unknown` で受けることが多い                                          |
| `引数名 is 絞り込み後の型` | 戻り値の型の位置に書く型述語。この関数が `true` を返した場合、呼び出し元でその引数が指定した型に絞り込まれる |

**戻り値：** `boolean`（`true` = その型である / `false` = 違う）

典型例は、APIレスポンスのような `unknown` なデータを検証してから使うパターンです。

```tsx
type User = {
  id: number;
  name: string;
};

function isUser(value: unknown): value is User {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    typeof value.id === 'number' &&
    'name' in value &&
    typeof value.name === 'string'
  );
}
```

この `isUser` を通すと、`if` ブロックの中では `unknown` が `User` として扱えます。

```tsx
async function fetchUser(): Promise<User | null> {
  const res = await fetch('/api/user');
  const data: unknown = await res.json();

  if (isUser(data)) {
    return data; // ✅ このブロック内では data は User 型
  }
  return null; // 検証に失敗したデータは通さない
}
```

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
結局「これは User だ」って自分で申告してるんだから、`as User` と同じじゃないの…？
</SpeechBubble>

決定的な違いは、**実行時チェックの有無**です。`as` は中身を一切確認せずに型だけを上書きしますが、`is` を使った型ガードは「実行時に中身を検査し、合格したものだけを通す」仕組みです。<Marker>`as` は「ノーチェックの自己申告」、`is` は「実行時検査に合格したことをコンパイラに伝える契約」です。</Marker>

<Figure src="/images/search_woman_color.png" alt="型ガードのイメージ" caption="型ガードは中身を検査してから通す門番。asは顔パス" maxWidth="240px" />

<Callout type="warning">
### 「嘘をつく型ガード」に注意

コンパイラは `is` の**中身の検査ロジックが正しいかどうかまでは検証しません**。実装が間違っていても、コンパイラは型述語を信じてしまいます。

```tsx
// ❌ id も name も確認していないのに User だと申告している
function isUser(value: unknown): value is User {
  return typeof value === 'object' && value !== null;
}
```

検査漏れがあると、結局 `as` と同じ危険を抱え込みます。プロパティ数が多い型の検証は手書きだと漏れやすいため、実務ではZodなどのバリデーションライブラリに任せるのが定番です。

</Callout>

型述語は、配列の `filter` で「絞り込んだ結果の配列」を得たいときにも使えます。

```tsx
const values = ['a', null, 'b', null]; // (string | null)[]

// 型述語をアロー関数の戻り値に書くと、結果が string[] になる
const strings = values.filter((v): v is string => v !== null);
```

<Callout type="column">
### TypeScript 5.5からは「型述語の推論」が効く

2024年6月リリースのTypeScript 5.5で、**単純な関数なら `is` を書かなくても型述語が自動推論される**ようになりました。上の `filter((v) => v !== null)` も、5.5以降は `is` なしで `string[]` と正しく推論されます。

ただし推論が効くのは「戻り値の型注釈がない・実装が単純」な場合だけです。`isUser` のように「`object` かどうかのチェック結果を `User` という特定の型に対応づけたい」場合は、今でも明示的に `is User` を書く必要があります。

</Callout>

なお、`true` / `false` を返す代わりに「不正なら `throw` する」形で切り出すアサーション関数（`asserts`）もあります。こちらは[05章のアサーション関数パターン](/books/typescript/05-narrowing)で扱いました。

## ダブルアサーション（as unknown as T）の罠

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
`as any` がダメなら `as unknown as` にすれば安全ですよね？ AIに「anyを使わないで」って指示したら、こっちに書き換えてくれたんですけど……
</SpeechBubble>

<Marker>結論から言うと、**`as unknown as T` を書いている時点で型安全性は放棄しています**。</Marker>`as any as T` と本質的な危険度は大差ありません。

```tsx
// どちらも「型チェックを黙らせる」行為
const a = value as any as TargetType;
const b = value as unknown as TargetType;
```

TypeScriptは通常、互換性のない型同士のアサーションをエラーにしてくれます。

```tsx
const n: number = 42;
const s = n as string;
// ❌ 型 'number' から型 'string' への変換は、互いに十分に重複できないため
//    間違っている可能性があります。意図的にそうする場合は、
//    まず式を 'unknown' に変換してください。ts(2352)
```

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
エラーメッセージ自体が「まず `unknown` に変換してください」と回避策を教えてくれるの、なんだか不思議です。これっておまじないですか？
</SpeechBubble>

### なぜ `unknown` を挟むと通るのか

おまじないではなく、はっきりしたルールがあります。<Marker>`as` は「どちらか一方向に代入できる型同士」でしか許可されません。</Marker>これがエラーメッセージの言う「十分に重複」の正体です。`number` と `string` はどちらも互いに代入できないため、直接のアサーションは拒否されます。

一方 `unknown` は、あらゆる型を受け入れる**トップ型**です。そのため2段に分けると、それぞれが個別にルールを満たします。

```tsx
const step1 = n as unknown; // ✅ 何でも unknown には代入できる
const step2 = step1 as string; // ✅ unknown は任意の型にアサーションできる
```

つまりダブルアサーションは、ルールを「経由」してすり抜けているだけです。そしてここが肝心なのですが、これは**コンパイル時だけの話**です。

```tsx
const n = 42;
const s = n as unknown as string;

s.toUpperCase(); // 💥 TypeError: s.toUpperCase is not a function
```

実行時の値は数値のままなので、`string` のつもりでメソッドを呼べば落ちます。型注釈に嘘をついただけで、値そのものは1ビットも変わっていません。この `number` → `string` の例に限っていえば、<Marker>エラーは正しく仕事をしていたので、消すのではなく従うのが正解です。</Marker>値を本当に変えたいなら、この章の前半で見た型キャスト、つまり変換関数を使います。

```tsx
String(n); // "42" — n.toString() や `${n}` でもよい
```

ダブルアサーションは、一度 `any` や `unknown` を経由することで**この安全装置を迂回**します。`unknown` 経由のほうが `@typescript-eslint/no-explicit-any` ルールに引っかからないぶん行儀が良く見えますが、迂回していること自体は変わりません。

<Callout type="note">
### `as any` と `as unknown as T` の違い

危険度は同じですが、汚染する範囲が違います。`any` は**そのあとの式全体に伝播**し、どんなプロパティアクセスも素通しにします。対して `as unknown as T` は<Marker>その場で `T` に型が確定するため、以降は通常どおり型チェックが効きます</Marker>。実務で後者が好まれるのは、主にこの理由です。

```tsx
const a = value as any;
a.foo.bar.baz(); // 何を書いてもエラーにならない

const b = value as unknown as User;
b.foo; // ❌ プロパティ 'foo' は型 'User' に存在しません
```

</Callout>

<Callout type="warning">
### AI生成コードでよく見るパターン

AIに「`any` を使わないで」と指示すると、`as any` を機械的に `as unknown as` へ置き換えることがあります。lint警告は消えますが、**型安全性は改善されていません**。「`any` を消す」のが目的ではなく、「型チェックが正しく機能する状態にする」のが本来の目的です。

</Callout>

ダブルアサーションが出てきたら、まず設計を見直します。

| 状況 | 代わりにやること |
|---|---|
| APIレスポンスの型が合わない | ジェネリクスで型パラメータを渡す / Zodなどでバリデーション |
| ライブラリの型定義が古い | `@types` を更新する / 型定義を拡張（declaration merging） |
| テストでモックを作りたい | `Partial<T>` や `satisfies` を活用する |
| 本当にどうしようもない | `as unknown as T` を使い、コメントで理由を残す |

### 使ってよい場面 — 「実行時の値は正しいが、コンパイラには証明できない」とき

とはいえ、ダブルアサーションが常に悪というわけではありません。判断基準はシンプルです。

| 実行時の値 | 判定 |
| --- | --- |
| 本当にその型になっている | 許容。なぜ安全といえるかをコメントで残す |
| その型になっていない | 修正すべきコードを隠しているだけなので不可 |

先ほどの `number` → `string` は後者なので論外でした。前者に当たる典型例は次の3つです。

- **テストのモック** — 巨大なインターフェースの一部だけ作って渡したい
- **型定義が実態とズレたライブラリの回避** — `@types` の更新が追いついていない
- **ジェネリクスの内部** — 実装者には正しいと分かるが、コンパイラが変換を追跡しきれない

いずれも「実行時の値は本当に正しい」のが前提です。頻度としては、普通のアプリケーションコードなら年に数回出るかどうかという程度で、日常的に書くものではありません。

ただし「モックだから常にダブルアサーションが要る」わけではない点に注意してください。

```tsx
type User = { id: number; name: string; email: string };

// ✅ プロパティが足りないだけなら、1段の as で通る
const mockUser = { id: 1 } as User;

// ❌ プロパティの型が食い違うと ts(2352) になる
const mockRequest = { url: '/api', headers: { 'content-type': 'json' } } as Request;
```

理由は、さきほどのルール（片方向に代入できればOK）で説明できます。`User` は `{ id: 1 }` の形に代入できるので前者は通り、`headers` が `Headers` 型と噛み合わない後者は両方向とも失敗します。<Marker>unknown を足す前に、まず1段の `as` で足りないか試すのが正しい順番です。</Marker>

<Callout type="note">
### ブランド型も1段で足りる

`type UserId = string & { readonly __brand: 'UserId' }` のようなブランド型（nominal typing）は、`as unknown as UserId` で生成している例をよく見かけます。ですが `UserId` は `string` に代入できるので、`raw as UserId` の1段で通ります。

</Callout>

<SpeechBubble character="/images/oksign_man_color.png" name="先生">
`as unknown as` に統一すること自体は悪くありません。lintルールと整合しますし、コードレビューで「ここは意図的にキャストしている」と分かりやすくなります。ただ、**そもそもダブルアサーションが必要な設計自体を見直すほうが先**、という順番が大事です。
</SpeechBubble>

## constアサーション（as const）

`as const` は名前こそ「アサーション」ですが、これまでの `as T` とは性格が正反対です。型を偽るのではなく、**推論される型をできるだけ狭く・固定的にする**ための機能で、安全に使えます。

まず、`as const` なしの推論結果を見てみます。

```tsx
const config = {
  endpoint: '/api/users',
  method: 'GET',
};
// 推論結果: { endpoint: string; method: string }
```

`method` の値は `'GET'` と書いたのに、型は `string` に**広げられて**（widening）推論されます。オブジェクトのプロパティは後から書き換えられるため、TypeScriptは安全側に倒して広い型を付けるのです。これが困る場面があります。

```tsx
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';

function request(url: string, method: HttpMethod) {
  /* ... */
}

request(config.endpoint, config.method);
// ❌ エラー：string は HttpMethod に代入できない
```

`as const` を付けると、推論結果がリテラル型のまま固定されます。

```tsx
const config = {
  endpoint: '/api/users',
  method: 'GET',
} as const;
// { readonly endpoint: "/api/users"; readonly method: "GET" }

request(config.endpoint, config.method); // ✅ "GET" は HttpMethod に代入できる
```

`as const` の効果は次の3つです。

| 効果                     | 説明                                                                     |
| ------------------------ | ------------------------------------------------------------------------ |
| リテラル型に固定         | `'GET'` が `string` に広げられず、`"GET"` 型のまま保たれる               |
| すべて `readonly` になる | プロパティへの再代入がコンパイルエラーになる（ネストしたオブジェクトも） |
| 配列が読み取り専用タプルになる | `[10, 20]` が `number[]` ではなく `readonly [10, 20]` になる             |

### 配列からユニオン型を導出する定番パターン

`as const` の実務での代表的な使いどころが、「選択肢の配列」と「その要素のユニオン型」を1つの定義から導出するパターンです。

```tsx
const CATEGORIES = ['tech', 'design', 'business'] as const;
// 型: readonly ["tech", "design", "business"]

type Category = (typeof CATEGORIES)[number];
// 型: "tech" | "design" | "business"

// 実行時は配列として使える
CATEGORIES.map((c) => console.log(c));

// 型の世界ではユニオン型として使える
function setCategory(category: Category) {
  /* ... */
}
```

<Marker>配列（実行時の値）とユニオン型（型の世界）を1つの定義から導出できるため、選択肢を追加するときの修正が1箇所で済みます。</Marker>

<Callout type="note">
### as constは「安全なアサーション」

`as T` はコンパイラのチェックを迂回しますが、`as const` は型を狭くする方向にしか働かないため、実行時エラーのリスクを増やしません。むしろ `readonly` によって意図しない書き換えを防げるので、**定数定義には積極的に使ってよい**機能です。

</Callout>

## 型アサーション vs 型ガード — どちらを使うべきか

| 手法 | 安全性 | 使う場面 |
|---|---|---|
| 型ガード（`typeof`, `in`, ユーザー定義） | 高い | ランタイムで検証できる場合 |
| 型アサーション（`as T`） | 低い | 型が正しいと確信できる場合 |
| ダブルアサーション（`as unknown as T`） | 最低 | テストやモックなどやむを得ない場面のみ |

<Figure src="/images/toppa_suit_woman_color.png" alt="型アサーションと型ガード" caption="迷ったら型ガード。asは「ここは自分が型チェッカーより詳しい」と確信できるときだけ" maxWidth="240px" />

基本方針：**まず型ガードで解決できないか考える。** `as` は「TypeScriptが推論できないが、自分には型が分かっている」場面の最終手段として使います。

## ちゃんと使うためのポイント

- <Marker>型ガードはランタイムで検証するので安全。型アサーションは自己申告なので危険</Marker>
- `as any` も `as unknown as T` も型安全性を放棄している点は同じ。ただし `any` は後続の式に伝播し、`as unknown as T` はその場で型が確定する
- <Marker>`ts(2352)` が出たら、`unknown` を挟む前に「1段の `as` で足りないか」「そもそも値の型が間違っていないか」を先に確認する</Marker>
- `as const` はアサーションではなくリテラル型への固定。安全に使える
- ユーザー定義型ガード（`is`）はAPIレスポンスのバリデーションで特に有用。ただし検査ロジックの正しさは自分で保証する
- TypeScript 5.5以降、単純な関数の型述語は自動推論される（特定の型へ絞る場合は明示的に `is` を書く）

次の章では、`Partial` や `Pick` など、既存の型から新しい型を作り出す[ユーティリティ型](/books/typescript/09-utility-types)を学びます。この章の表に登場した「モックには `Partial<T>` を使う」の正体も、そこで分かります。
