Route Handlersは `/api/users` のようなAPIエンドポイントを作る仕組みでした。では、ページやAPIに到達する**前**に、ログイン状態を見てリダイレクトしたり、特定のURLだけアクセス制御したりしたい場合はどうすればよいでしょうか。

Next.jsでは、そうした「リクエストの入口で行う処理」を `proxy.ts` で書けます。Next.js 15以前の記事では `middleware.ts` と呼ばれていることが多いですが、**Next.js 16では `middleware.ts` は非推奨になり、`proxy.ts` にリネーム**されています。

<a id="proxy-overview"></a>

## Proxyとは

Proxyは、リクエストがページやRoute Handlerに届く前に実行される処理です。

```txt
ブラウザ
  ↓
proxy.ts        ← ここで認証、リダイレクト、rewrite、ヘッダー操作
  ↓
page.tsx / route.ts
```

<MermaidDiagram
  id="next-proxy-flow"
  chart={`
flowchart LR
    A["ブラウザからリクエスト"] --> B["proxy.ts"]
    B --> C{"処理を分岐"}
    C -- "通す" --> D["page.tsx または route.ts"]
    C -- "別URLへ移動" --> E["redirect"]
    C -- "内部的に行き先変更" --> F["rewrite"]
    F --> D
`}
/>

たとえば、次のような処理に向いています。

| やりたいこと                           | Proxyが向いている理由                  |
| -------------------------------------- | -------------------------------------- |
| 未ログインユーザーを `/login` に飛ばす | ページに入る前にまとめて判定できる     |
| 古いURLを新しいURLへリダイレクトする   | レンダリング前にURLを変えられる        |
| A/Bテストや地域別のrewriteをする       | リクエスト情報を見て行き先を変えられる |
| 一部APIにCORSヘッダーを付ける          | Route Handlerに届く前に共通処理できる  |

ただし、Proxyは**すべてのリクエストの入口に近い場所**で動きます。便利だからといって、DBアクセスや重いビジネスロジックを入れる場所ではありません。

<Callout type="warning" title="Proxyは最後の手段に近い">
  Next.js公式でも、Middleware/Proxyは強力な機能であり、使いすぎを避ける方向が示されています。ページ内で済む処理、Route
  Handlerで済む処理、Server Actionsで済む処理は、まずそちらに置く方が分かりやすく保守しやすいです。
</Callout>

<a id="basic-proxy"></a>

## `proxy.ts` の基本形

`proxy.ts` は、`app/` の中ではなく、プロジェクトのルート、または `src/` を使っている場合は `src/proxy.ts` に置きます。

```txt
my-app/
├── src/
│   ├── app/
│   │   └── page.tsx
│   └── proxy.ts
└── next.config.ts
```

基本形は次のとおりです。

```ts
// src/proxy.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;

  if (pathname.startsWith('/admin')) {
    // ここで認証チェックなどを行う
  }

  return NextResponse.next();
}
```

`NextResponse.next()` は「特に止めずに、次の処理へ進める」という意味です。ページなら `page.tsx`、APIなら `route.ts` へ進みます。

<a id="execution-order"></a>

## リクエストが処理される順番 — Proxyはどこで実行されるか

<SpeechBubble character="/images/question_woman_04_color.png" name="学習者">
  `proxy.ts` がポートをlistenして、全部のリクエストを最初に受け取っているの？
</SpeechBubble>

ポートをlistenしているのは `proxy.ts` ではなく、**Next.jsのHTTPサーバー**です。`next dev` や `next start` を実行すると、Node.jsのプロセスがポート（デフォルトは3000）をlistenします。`proxy.ts` に書いた `proxy()` は、そのサーバーがリクエストを受け取るたびに呼び出す関数です。

```txt
ブラウザ
  ↓ HTTPリクエスト
Next.jsのHTTPサーバー（ポート3000をlisten）
  ↓ リクエストごとに proxy(request) を呼ぶ
proxy.ts
  ↓ NextResponse.next() が返ったら先へ進む
page.tsx / route.ts / 静的ファイル
```

また、`proxy()` はサーバーの処理の中で一番最初に実行されるわけではありません。Next.js公式ドキュメントは、1つのリクエストに対する実行順を次のように定めています。

| 順番 | 実行されるもの                                                          |
| ---- | ----------------------------------------------------------------------- |
| 1    | `next.config.js` の `headers`                                           |
| 2    | `next.config.js` の `redirects`                                         |
| 3    | **Proxy**                                                               |
| 4    | `next.config.js` の `rewrites`（`beforeFiles`）                         |
| 5    | ファイルシステムのルート（`public/`、`_next/static/`、`app/` など）     |
| 6    | `next.config.js` の `rewrites`（`afterFiles`）                          |
| 7    | 動的ルート（`/blog/[slug]` など）                                       |
| 8    | `next.config.js` の `rewrites`（`fallback`）                            |

<MermaidDiagram
  id="next-proxy-execution-order"
  chart={`
flowchart TB
    A["HTTPサーバーが受信"] --> B["config の headers"]
    B --> C["config の redirects"]
    C --> D["proxy.ts"]
    D --> E["config の rewrites"]
    E --> F["public や _next/static"]
    F --> G["app のページと route.ts"]
`}
/>

この順番から、次の2点が分かります。

- **`next.config.js` の `redirects` に一致したリクエストは、Proxyに届きません。** 3番目のProxyより先に、2番目でリダイレクトのレスポンスが返るためです
- <Marker>Proxyは、`public/` や `_next/static/` のファイルを返す処理（5番目）より前に実行されます。</Marker> つまり、ページだけでなくCSS・JavaScript・画像へのリクエストでも `proxy()` が呼ばれます

2点目は、次の節で扱う `matcher` が必要になる理由です。

<Callout type="note" title="デプロイ先によって実行場所は変わる">
  `next start` で自分のサーバーに置く場合、Proxyはアプリ本体と同じNode.jsプロセスの中で実行されます。ホスティングサービスにデプロイした場合にProxyがどこで実行されるかは、サービスごとに異なります。デプロイ先の公式ドキュメントで確認してください。
</Callout>

<a id="matcher"></a>

## `matcher` で対象URLを絞る

<Marker>`matcher` を書かない場合、Proxyはすべてのリクエストで実行されます。</Marker> 公式ドキュメントには、対象に含まれるものとして次が挙げられています。

- ページとRoute Handler
- ビルドされたJavaScript・CSS（`_next/static`）
- 画像最適化のリクエスト（`_next/image`）
- `public/` フォルダのファイル

`matcher` なしで「Cookieがなければ `/login` へリダイレクト」と書くと、ログインページが読み込むCSSやJavaScriptのリクエストまでリダイレクトされ、画面が崩れます。そのため、実務では `config.matcher` で対象を明示するのが基本です。

```ts
// src/proxy.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  return NextResponse.next();
}

export const config = {
  matcher: ['/dashboard/:path*', '/admin/:path*'],
};
```

この例では、`/dashboard` と `/admin` 配下だけでProxyが動きます。

<Callout type="info" title="まずは狭く指定する">
  最初からサイト全体を対象にするより、`/dashboard/:path*` や `/admin/:path*`
  のように守りたい範囲を絞る方が安全です。対象が広いほど、画像、静的ファイル、API、プリフェッチなども考慮する必要が出ます。
</Callout>

### サイト全体を対象にして、静的ファイルだけ除外する

ほぼ全ページを対象にしたい場合は、「除外するパス」を正規表現の否定先読み `(?!...)` で指定します。

```ts
export const config = {
  matcher: [
    // api、_next/static、_next/image、.png で終わるパス以外すべて
    '/((?!api|_next/static|_next/image|.*\\.png$).*)',
  ],
};
```

`matcher` に書ける値をまとめます。

| 書き方           | 例                                        | 対象                               |
| ---------------- | ----------------------------------------- | ---------------------------------- |
| 文字列1つ        | `'/about'`                                | `/about` だけ                      |
| 文字列の配列     | `['/about', '/contact']`                  | どれかに一致したパス               |
| パスパターン     | `'/dashboard/:path*'`                     | `/dashboard` とその配下すべて      |
| 正規表現         | `'/((?!api\|_next/static).*)'`            | 正規表現に一致したパス             |

`:path*` の `*` は「0個以上のパス区切り」を表します。`/dashboard/:path*` は `/dashboard`、`/dashboard/a`、`/dashboard/a/b` のすべてに一致します。

<a id="auth-redirect"></a>

## 認証リダイレクトの例

ログイン済みかどうかをCookieで判定し、未ログインなら `/login` にリダイレクトする例です。

```ts
// src/proxy.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const session = request.cookies.get('session')?.value;

  if (!session) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('next', request.nextUrl.pathname);
    return NextResponse.redirect(loginUrl);
  }

  return NextResponse.next();
}

export const config = {
  matcher: ['/dashboard/:path*', '/admin/:path*'],
};
```

`new URL('/login', request.url)` と書くと、現在のオリジンを保ったまま `/login` のURLを作れます。`next` クエリに元のパスを入れておけば、ログイン後に戻す処理も作りやすくなります。

<MermaidDiagram id="next-proxy-auth-sequence" chart={`
sequenceDiagram
    participant U as User
    participant P as proxy.ts
    participant L as login page
    participant D as dashboard

    U->>P: GET /dashboard
    P->>P: session Cookieを確認
    alt sessionなし
        P-->>U: redirect login next dashboard
        U->>L: GET /login
    else sessionあり
        P->>D: NextResponse.next()
        D-->>U: dashboardを表示
    end

`} />

<Callout type="warning" title="Proxyだけで認可を完結させない">
  Proxyで未ログインを弾くのは有効ですが、それだけで安全とは言い切れません。Server ActionsやRoute
  Handlersの中でも、必ず「このユーザーがこの操作をしてよいか」を確認してください。`matcher`
  の変更やURL構成の変更で、Proxyの対象から外れる可能性があるためです。
</Callout>

<a id="next-request-response"></a>

## NextRequestとNextResponseの使い方

Proxyでは、[Route Handlers](/books/next-js/route-handlers) と同じく `NextRequest` / `NextResponse` をよく使います。

### URLを読む

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname;
  const searchParams = request.nextUrl.searchParams;

  if (pathname === '/old') {
    const url = new URL('/new', request.url);
    url.search = searchParams.toString();
    return NextResponse.redirect(url);
  }

  return NextResponse.next();
}
```

### Cookieを読む

```ts
export function proxy(request: NextRequest) {
  const token = request.cookies.get('token')?.value;

  if (!token) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  return NextResponse.next();
}
```

### ヘッダーを追加する

```ts
export function proxy(request: NextRequest) {
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-from-proxy', 'true');

  return NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  });
}
```

`NextResponse.next({ request: { headers } })` は、後続のページやRoute Handlerに渡すリクエストヘッダーを変更します。一方で、クライアントに返すレスポンスヘッダーを設定したい場合は、`const response = NextResponse.next()` を作ってから `response.headers.set()` します。

```ts
export function proxy(request: NextRequest) {
  const response = NextResponse.next();
  response.headers.set('x-frame-options', 'DENY');
  return response;
}
```

### 表示するURLを変えずに別のページを返す（rewrite）

`NextResponse.rewrite()` は、ブラウザのアドレスバーのURLを変えずに、別のパスの内容を返します。`redirect()` との違いは、ブラウザに新しいURLへの再リクエストをさせるかどうかです。

```ts
export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === '/about') {
    // ブラウザのURLは /about のまま、/about-2 の内容を返す
    return NextResponse.rewrite(new URL('/about-2', request.url));
  }

  return NextResponse.next();
}
```

| メソッド     | ブラウザに返るもの                         | アドレスバーのURL | リクエスト回数 |
| ------------ | ------------------------------------------ | ----------------- | -------------- |
| `redirect()` | ステータス307と `Location` ヘッダー        | 新しいURLに変わる | 2回            |
| `rewrite()`  | 書き換え先のページの内容（ステータス200）  | 変わらない        | 1回            |

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">
  URLを変えたいなら `redirect()`、URLはそのままで中身だけ差し替えたいなら `rewrite()` だよ。
</SpeechBubble>

### Cookieを書き込む・削除する

リクエストのCookieは `request.cookies` で読み、レスポンスのCookieは `response.cookies` で書きます。`response.cookies.set()` を呼ぶと、レスポンスに `Set-Cookie` ヘッダーが付きます。

```ts
export function proxy(request: NextRequest) {
  const response = NextResponse.next();

  // Set-Cookie: theme=dark; Path=/; HttpOnly をレスポンスに付ける
  response.cookies.set('theme', 'dark', { path: '/', httpOnly: true });

  // ブラウザ側の old-token を削除する
  response.cookies.delete('old-token');

  return response;
}
```

### ページに進ませず、ProxyからJSONを返す

`NextResponse.next()` を返さずに `NextResponse.json()` を返すと、後続の `route.ts` は実行されず、そのJSONがそのままレスポンスになります。APIへの未認証リクエストを401で止める例です。

```ts
export function proxy(request: NextRequest) {
  const session = request.cookies.get('session')?.value;

  if (!session) {
    return NextResponse.json({ error: 'unauthorized' }, { status: 401 });
  }

  return NextResponse.next();
}

export const config = {
  matcher: '/api/:path*',
};
```

ページへのアクセスは `redirect()` で `/login` へ送り、APIへのアクセスは `json()` で401を返す、という使い分けになります。`fetch` で呼ばれるAPIにリダイレクトを返すと、呼び出し側はログインページのHTMLを受け取ってしまうためです。

## NextRequest・NextResponseの一覧

ここまでに出てきたものを含め、Proxyでよく使うプロパティとメソッドをまとめます。どちらも `next/server` からimportします。

### NextRequest — リクエストを読む

`NextRequest` は、Web標準の `Request` にNext.js用のプロパティを足したクラスです。`request.method` や `request.headers` など、`Request` のプロパティはそのまま使えます。

| プロパティ・メソッド            | 戻り値                             | 内容                                         |
| ------------------------------- | ---------------------------------- | -------------------------------------------- |
| `request.nextUrl.pathname`      | 文字列                             | パス。`/dashboard/settings` など             |
| `request.nextUrl.searchParams`  | `URLSearchParams`                  | クエリ文字列                                 |
| `request.url`                   | 文字列                             | オリジンを含むURL全体                        |
| `request.method`                | 文字列                             | `GET`、`POST` など                           |
| `request.headers.get(name)`     | 文字列 / `null`                    | リクエストヘッダーの値                       |
| `request.cookies.get(name)`     | `{ name, value }` / `undefined`    | Cookieを1つ取得する                          |
| `request.cookies.getAll()`      | `{ name, value }` の配列           | Cookieをすべて取得する                       |
| `request.cookies.has(name)`     | `boolean`                          | Cookieがあるかどうか                         |

`request.cookies.get('session')` の戻り値はオブジェクトなので、値を取り出すには `?.value` を付けます。

### NextResponse — レスポンスを作る

`NextResponse` は、Web標準の `Response` にNext.js用のメソッドを足したクラスです。次の4つはすべて静的メソッドで、`NextResponse` のインスタンスを返します。

| メソッド                             | 引数                                   | 動作                                                   |
| ------------------------------------ | -------------------------------------- | ------------------------------------------------------ |
| `NextResponse.next(init?)`           | `init.request.headers` で転送ヘッダー  | 後続の処理（ページ・Route Handler）へ進める            |
| `NextResponse.redirect(url, init?)`  | `url` は絶対URL。`init` はステータス   | 別のURLへリダイレクトする。デフォルトのステータスは307 |
| `NextResponse.rewrite(url, init?)`   | `url` は絶対URL                        | ブラウザのURLを変えずに、別のパスの内容を返す          |
| `NextResponse.json(body, init?)`     | `body` はJSONにする値。`init.status`   | JSONのレスポンスを返す                                 |

`redirect()` と `rewrite()` の `url` には、`'/login'` のような相対パスではなく絶対URLを渡します。そのため `new URL('/login', request.url)` と書いて、現在のオリジンを付けたURLを作ります。

作ったレスポンスに対しては、次のメソッドでヘッダーとCookieを操作できます。

| メソッド                                       | 戻り値                           | 動作                                           |
| ---------------------------------------------- | -------------------------------- | ---------------------------------------------- |
| `response.headers.set(name, value)`            | なし                             | レスポンスヘッダーを設定する                   |
| `response.cookies.set(name, value, options?)`  | `response.cookies` 自身          | `Set-Cookie` ヘッダーを付ける                  |
| `response.cookies.get(name)`                   | `{ name, value }` / `undefined`  | レスポンスに設定済みのCookieを取得する         |
| `response.cookies.delete(name)`                | `boolean`                        | Cookieを削除する。削除したら `true`            |

`response.cookies.set()` の `options` には、`path`・`httpOnly`・`secure`・`sameSite`・`maxAge` など、`Set-Cookie` ヘッダーの属性を指定します。

<Callout type="info" title="Route Handlerでも同じクラスを使う">
  `NextRequest` と `NextResponse` は、[Route Handlers](/books/next-js/route-handlers) の `route.ts` でも同じものを使います。ただし `NextResponse.next()` はProxy専用です。`route.ts` には「後続の処理」がないため、`NextResponse.json()` などでレスポンスを返します。
</Callout>

<a id="edge-runtime"></a>

## Edge Runtimeとは

Edge Runtimeは、Node.jsサーバーよりもユーザーに近い場所で軽量に処理を動かすための実行環境です。Vercelにデプロイした場合で考えると、アプリ本体が動くリージョンとは別に、CDNに近い場所でリクエストをさばくイメージです。

ただし、Edge Runtimeは「Node.jsをそのままエッジで動かす環境」ではありません。Web標準APIを中心にした、制限のあるJavaScript実行環境です。

```txt
Node.js Runtime
  - fs, crypto, net などNode.js APIを使える
  - DB接続や重いサーバー処理に向く
  - アプリのレンダリングやRoute Handlerの標準実行環境

Edge Runtime
  - fetch, Request, Response, Headers などWeb標準API中心
  - 起動が軽く、リクエストの入口処理に向く
  - Node.jsのネイティブAPIは使えない
```

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
  Edge Runtimeって速そうだけど、Node.jsと同じコードが全部動くわけではないんだね。
</SpeechBubble>

その通りです。`fs` でファイルを読む、Node.js専用のライブラリを使う、ネイティブモジュールに依存する、といった処理はEdge Runtimeでは動かないことがあります。

<a id="edge-vs-node"></a>

## Edge RuntimeとNode.js Runtimeの違い

違いを実務目線で整理すると、次のようになります。

| 観点          | Node.js Runtime                                       | Edge Runtime                                      |
| ------------- | ----------------------------------------------------- | ------------------------------------------------- |
| 主な用途      | レンダリング、Route Handler、DB連携、重いサーバー処理 | リダイレクト、rewrite、軽い認証判定、ヘッダー操作 |
| 使えるAPI     | Node.js APIを広く使える                               | Web標準API中心                                    |
| `fs`          | 使える                                                | 使えない                                          |
| `require`     | 使える場面が多い                                      | 基本はES Modules                                  |
| npmパッケージ | Node.js前提のものも使いやすい                         | Edge対応していないと動かない場合がある            |
| DB接続        | 向いている                                            | 直接接続は避けたいことが多い                      |
| 起動・配置    | アプリのサーバー側                                    | ユーザーに近い場所で動かしやすい                  |

Edge Runtimeは「軽い入口処理」に向いています。逆に、DBへ複雑なクエリを投げる、外部APIをいくつも叩いて集約する、ファイルを読み書きする、といった処理はRoute HandlerやServer Actionsに寄せる方が安全です。

    B --> C["軽い判定"]
    C --> D["redirect / rewrite / next"]

<Callout type="note" title="Next.jsのバージョンでランタイムの扱いが変わっている">
  古いMiddlewareの記事では「MiddlewareはEdge
  Runtimeのみ」と説明されていることがあります。これは当時の制約としては重要でした。一方、Next.js
  15.5でMiddlewareのNode.js Runtimeサポートが安定し、Next.js 16の `proxy.ts`
  では公式ドキュメント上、ProxyはNode.js
  Runtimeがデフォルトとされています。古い記事と現行仕様が食い違って見えるのは、この変遷があるためです。
</Callout>

<a id="is-vercel-only"></a>

## Edge RuntimeはVercel独自の概念なのか

Edge Runtimeという考え方自体は、Vercelだけのものではありません。Cloudflare Workers、Deno Deploy、Netlify Edge Functionsなど、ユーザーに近い場所で軽量なJavaScriptを実行する仕組みは複数あります。

ただし、**Next.jsのEdge Runtimeとして何が使えるか、どの機能がどう動くかは、Next.jsとデプロイ先の実装に依存**します。VercelではNext.jsとの統合が強く、ProxyやEdge向け機能を自然に使いやすい一方、セルフホスティングや別プラットフォームでは対応状況を確認する必要があります。

実務では、次のように考えると迷いにくいです。

- Edge Runtimeは「Vercelだけのマーケティング用語」ではない
- ただし、Next.jsでのEdge Runtimeの挙動はNext.jsとデプロイ先の対応に左右される
- Node.js APIに依存する処理はEdgeに置かない
- 認証の最終チェックやDB更新は、Route Handler / Server Actions側にも必ず置く

<a id="middleware-to-proxy"></a>

## Next.js 16の変更 — `middleware.ts` から `proxy.ts` へ

<Marker>
  Next.js 16では、従来の `middleware.ts` というファイル規約が非推奨になり、`proxy.ts`
  にリネームされました。
</Marker>

```diff
- src/middleware.ts
+ src/proxy.ts
```

関数名も変わります。

<MermaidDiagram
  id="next-proxy-rename-flow"
  chart={`
flowchart LR
    A["Next.js 15以前"] --> B["middleware.ts"]
    B --> C["middleware(request)"]
    C --> D["Next.js 16以降"]
    D --> E["proxy.ts"]
    E --> F["proxy(request)"]
`}
/>

```diff
- export function middleware(request: NextRequest) {
+ export function proxy(request: NextRequest) {
    return NextResponse.next();
  }
```

移行用のcodemodも用意されています。

```bash
npx @next/codemod@canary middleware-to-proxy .
```

名称変更の意図は、Expressのような「アプリ内部のmiddleware」と誤解されやすかったためです。Next.jsのProxyは、アプリのレンダリングコードの中間に差し込むというより、**アプリの前段にあるネットワーク境界でリクエストを処理するもの**と捉える方が近いです。

<Callout type="info" title="古い記事では middleware.ts と書かれている">
  Next.js 15以前の記事・教材・サンプルでは `middleware.ts` が多く登場します。Next.js
  16以降で新しく書くなら `proxy.ts` を使い、古いコードを読むときは「middleware.ts =
  現在のproxy.tsの旧名」と読み替えましょう。
</Callout>

<a id="when-to-use"></a>

## Proxyに書くべき処理・書くべきでない処理

Proxyは便利ですが、何でも置ける場所ではありません。

| 処理                                   | Proxyに置いてよいか | 理由                                            |
| -------------------------------------- | ------------------- | ----------------------------------------------- |
| 未ログインなら `/login` にリダイレクト | 向いている          | ページ到達前に判断したい                        |
| `/old` を `/new` にリダイレクト        | 向いている          | レンダリング不要                                |
| `/dashboard` 配下だけアクセス制御      | 向いている          | `matcher` で絞りやすい                          |
| 複雑なDB検索                           | 避ける              | 重くなりやすく、入口処理に向かない              |
| ユーザーの権限を最終確定する           | Proxyだけでは不十分 | Server Actions / Route Handlers側でも確認が必要 |
| フォーム送信後のDB更新                 | 向かない            | Server ActionsやRoute Handlerの責務             |
| ページごとの細かい表示分岐             | 向かないことが多い  | Server Component内で扱う方が自然                |

迷ったら、「その処理はリクエストがページ/APIに届く前に終わっている必要があるか？」と考えます。必要がなければ、ページ、Route Handler、Server Actionsに置く方が読みやすいです。

<a id="common-pitfalls"></a>

## よくあるハマりどころ

| ハマりどころ                                    | 原因                                      | 対策                                                  |
| ----------------------------------------------- | ----------------------------------------- | ----------------------------------------------------- |
| 画像や静的ファイルにもProxyが走る               | `matcher` が広すぎる                      | 対象パスを狭くする                                    |
| ログインページへ無限リダイレクトする            | `/login` 自体もProxy対象になっている      | `matcher` から `/login` を外す                        |
| Edgeで動かないライブラリがある                  | Node.js APIやネイティブ機能に依存している | Edge対応ライブラリにするか、処理をRoute Handlerへ移す |
| Proxyで認証したのにAPIが叩ける                  | APIが `matcher` 対象外                    | Route Handler側でも認証・認可する                     |
| 古い記事の `middleware.ts` をそのまま使っている | Next.js 16で名称が変わった                | `proxy.ts` と `proxy()` に移行する                    |
| ProxyにDB処理を入れて遅くなる                   | 入口処理が重い                            | 軽い判定だけにし、詳細処理はサーバー側へ寄せる        |

<a id="summary"></a>

## まとめ

- `proxy.ts` は、ページやRoute Handlerに届く前に実行される入口処理
- Next.js 16では `middleware.ts` が非推奨になり、`proxy.ts` / `proxy()` にリネームされた
- ポートをlistenするのはNext.jsのHTTPサーバーで、`proxy()` はリクエストごとに呼び出される関数。`next.config.js` の `headers` と `redirects` の後、ファイルやページを返す処理の前に実行される
- `matcher` を書かないと、`_next/static` や `public/` のファイルを含むすべてのリクエストで実行される。`matcher` で対象URLを狭く絞るのが基本
- `NextRequest` でURL・Cookie・ヘッダーを読み、`NextResponse` の `next()`・`redirect()`・`rewrite()`・`json()` でレスポンスを決める
- Edge RuntimeはWeb標準API中心の軽量な実行環境で、Node.js Runtimeとは使えるAPIが異なる
- 古いMiddlewareはEdge Runtimeのみという説明が多いが、Next.js 15.5以降とNext.js 16のProxyではランタイムの扱いが変わっている
- Proxyは強力だが、認証・認可の最終チェックはRoute HandlerやServer Actions側にも必ず置く

次の章では、データ取得中の **[ローディングとエラー処理](/books/next-js/08-loading-and-error)** を扱います。`fetch` を待つ間に何を見せるか、失敗したらどう表示するか——`loading.tsx` と `error.tsx` で宣言的に実装できます。
