[テーブルを作ってデータを入れる](/books/mysql/create-table-and-write-data)で `SHOW CREATE TABLE` を実行したとき、書いていないのに末尾へ付いてきた行がありました。

```
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
```

`CHARSET` と `COLLATE` は [文字コードと照合順序](/books/mysql/character-set-and-collation)で扱いました。残った `ENGINE=InnoDB` が、この章の主題です。

<Callout type="note" title="この章で扱う範囲">
インデックスの張り方や `EXPLAIN` の読み方そのものは別の章の担当です。ここでは、その前提になる**InnoDBがデータをどう並べているか**を押さえます。`SELECT` の書き方は [SQLとデータベースの基礎](/books/sql-basics/select-basics) の内容がそのまま通用します。
</Callout>

## ストレージエンジンとは何か

MySQLは、SQLを解釈する部分と、データを実際にディスクへ読み書きする部分が分かれています。この後半を担当するのが**ストレージエンジン**です。

そして<Marker>ストレージエンジンはテーブルごとに選べます。</Marker>同じデータベースの中に、InnoDBのテーブルとMyISAMのテーブルが混在できるということです。これはMySQLの構造上の特徴で、他のRDBMSにはあまりない考え方です。

いま利用できるエンジンは `SHOW ENGINES;` で確認できます。実務で名前を見るのは次の4つ程度です。

| エンジン | 位置づけ |
| --- | --- |
| `InnoDB` | 既定。トランザクション・行ロック・クラッシュリカバリを備える |
| `MyISAM` | 5.5以前の既定。トランザクションなし。古いシステムに残っている |
| `MEMORY` | メモリ上のテーブル。再起動で消える |
| `CSV` | CSVファイルとして保存。データ受け渡し用 |

## InnoDBとMyISAMの違い

比較として意味があるのは、実質この2つです。

| | InnoDB | MyISAM |
| --- | --- | --- |
| トランザクション | あり | **なし** |
| ロックの単位 | 行 | テーブル |
| クラッシュ後の復旧 | ログから自動復旧 | 手動修復が必要なことがある |
| 外部キー制約 | 使える | 無視される |
| `COUNT(*)` | 数え上げが必要 | 行数を保持しているので即答 |
| データの並び | 主キー順（クラスタ化） | 挿入順 |

`COUNT(*)` の速さだけはMyISAMが勝ちますが、それ以外は比べる段階にありません。<Marker>1行更新している間そのテーブル全体が止まる（テーブルロック）という一点だけでも、Webアプリケーションでは選べません。</Marker>

MySQL 5.5からInnoDBが既定になり、8.0ではMySQL自身の管理情報（データディクショナリ）もInnoDBに置かれるようになりました。MyISAMはまだ動きますが、新規に選ぶ理由はありません。

<Callout type="warning" title="古いダンプを取り込むと混在する">
5.1以前に作られたスキーマのダンプには `ENGINE=MyISAM` が書かれていることがあります。そのまま流すと、**その指定が優先されてMyISAMのテーブルができます**。移行時は次のクエリで確認します。

```sql
SELECT TABLE_NAME, ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp' AND ENGINE <> 'InnoDB';
```

変換は `ALTER TABLE テーブル名 ENGINE = InnoDB;` です。テーブル全体の作り直しになるため、行数が多い場合は所要時間を見積もってから実行します。
</Callout>

## クラスタ化インデックス — データは主キー順に並んでいる

ここからがInnoDBの中身です。<Marker>InnoDBでは、テーブルのデータそのものが主キーの順に並んで格納されています。</Marker>これを**クラスタ化インデックス**と呼びます。

「インデックスがデータを指している」のではなく、「インデックスの葉に行そのものが入っている」という構造です。主キーで引く検索が速いのは、目的の行がインデックスをたどった先にそのまま置かれているからです。

<Callout type="note" title="主キーを書かなかった場合">
`PRIMARY KEY` を指定しないテーブルでも、InnoDBは内部的にクラスタ化インデックスを作ります。使われるのは、最初の「`NOT NULL` な `UNIQUE` インデックス」、それも無ければ**内部生成の6バイトのID**です。この内部IDはSQLからは見えず、アプリケーションからは使えません。主キーは必ず自分で決めます。
</Callout>

### セカンダリインデックスは主キーを持っている

主キー以外に張ったインデックス（セカンダリインデックス）の葉には、行データではなく**主キーの値**が入っています。そのため、主キー以外の条件で検索して行の中身を取るときは、2段階になります。

### 主キーが大きいと、すべてのインデックスが太る

セカンダリインデックスは主キーの値を含むので、**主キーが大きいほど、テーブル上のすべてのインデックスがその分だけ大きくなります**。

[データ型の選び方](/books/mysql/data-types)で主キーに `BIGINT UNSIGNED`（8バイト）を勧めたのは、この構造とのバランスです。文字列のUUID（`CHAR(36)` なら36文字）を主キーにすると、インデックス1つごとにその36文字ぶんが行数分だけ積まれます。

### 主キーがランダムだと挿入が遅くなる

データが主キー順に並んでいるということは、**新しい行はその値の位置に挿入される**ということです。

- `AUTO_INCREMENT` の連番 — 常に末尾に追加される。並べ替えが起きない
- UUIDv4のようなランダムな値 — 途中に割り込む。挿入のたびにページの分割や再配置が発生する

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
UUIDを主キーにするのは、分散システムでよく見る設計だと思っていました。
</SpeechBubble>

設計として間違いではありません。アプリケーション側でIDを採番できる利点は本物です。問題は**ランダムな順序**のほうなので、時刻順に増えるUUID（UUIDv7）を使う、`BINARY(16)` に詰めてサイズを抑える、といった対処と組み合わせます。「UUIDだから遅い」ではなく「主キーがランダムだと遅い」と理解しておくと、判断を間違えません。

## ページとバッファプール

InnoDBはデータを**ページ**という単位で扱います。既定のページサイズは16KBで、ディスクとの読み書きはすべてこの単位です。1行だけ読むときも、その行が入っている16KBを読み込みます。

読み込んだページを載せておくメモリ領域が**バッファプール**です。

| 変数 | 既定値 | 意味 |
| --- | --- | --- |
| `innodb_page_size` | 16KB | ページの大きさ。作成後は変更できない |
| `innodb_buffer_pool_size` | 128MB | ページを載せておくメモリの量 |

既定の128MBは開発用の値です。<Marker>データベース専用のサーバーでは、バッファプールに搭載メモリの大部分を割り当てるのが基本的なチューニングです。</Marker>よく使うデータがここに載りきっている間、読み取りはディスクに触らずに済みます。

「本番だけクエリが遅い」という現象の一部は、SQLではなく**バッファプールに載りきらないデータ量**の問題です。

## クラッシュしても壊れない仕組み

InnoDBは、更新をいきなりデータファイルへ書きません。先に**REDOログ**へ書き、あとからまとめてデータファイルへ反映します。途中で電源が落ちても、再起動時にログから復旧できます。

| 仕組み | 役割 |
| --- | --- |
| REDOログ | 変更内容を先に記録する。復旧の元になる |
| ダブルライトバッファ | ページの書き込み途中で落ちたときの破損を防ぐ |
| `innodb_flush_log_at_trx_commit` | コミット時にログをディスクへ確実に書くかどうか。既定は `1`（毎回書く） |

`innodb_flush_log_at_trx_commit` を `0` や `2` にすると書き込みは速くなりますが、**落ちたときに直近のコミットが失われる可能性**を受け入れることになります。速度のために触る前に、何を失う設定なのかを理解しておく必要があります。

<Callout type="info" title="テーブルごとにファイルが分かれている">
既定では `innodb_file_per_table` が有効で、テーブルごとに `.ibd` ファイルが作られます。テーブルを削除したときにディスク領域が返りやすい、テーブル単位で移動できる、といった運用上の利点があります。
</Callout>

## よくあるハマりどころ

### COUNT(*) が遅い

InnoDBは行数を保持していないため、`SELECT COUNT(*) FROM orders;` は数え上げになります。MyISAMから移行したときに「同じSQLなのに遅くなった」と感じる典型がこれです。
概算でよければ `information_schema.TABLES` の `TABLE_ROWS`（推定値）を見る、正確な件数が頻繁に要るならカウンタ用のテーブルを持つ、といった設計で回避します。

### 主キーのないテーブルを作ってしまう

主キーが無くてもテーブルは作れますが、InnoDBは見えない内部IDで並べます。行を一意に指せないので更新や削除が書きにくく、運用上も扱いづらくなります。**すべてのテーブルに主キーを付ける**、で構いません。

### エンジンだけ変えてトランザクションが効かない気がする

`ALTER TABLE ... ENGINE = InnoDB` でエンジンは変わりますが、MyISAM時代に**外部キー制約を書いていた場合、その定義は取り込まれていません**（MyISAMは構文を無視するため）。移行後に、必要な制約を張り直したかを確認します。

### バッファプールを増やしすぎてOSが苦しくなる

「大部分を割り当てる」は「全部」ではありません。OSと他のプロセス、接続ごとのメモリ（[接続を確認する](/books/mysql/connect-and-max-connections)で見た接続数のぶんだけ積み上がります）を残した上での話です。

## ちゃんと使うためのポイント

- ストレージエンジンはテーブル単位。混在しうるので、移行時は `information_schema.TABLES` で確認する
- 現在の選択肢は実質InnoDBのみ。MyISAMはトランザクションもなく、ロックがテーブル単位
- InnoDBのデータは主キー順に並んでいる（クラスタ化インデックス）
- セカンダリインデックスの葉には主キーが入る。主キーが大きいと全インデックスが太る
- 主キーがランダムだと挿入時にページの分割が起きる。連番か、時刻順に増えるIDを選ぶ
- 読み書きの単位は16KBのページ。載せておく場所がバッファプール（既定128MB）
- REDOログとダブルライトによって、クラッシュしても復旧できる
- `innodb_flush_log_at_trx_commit` を緩めるのは、失うものを理解してから

主キーの順に並んでいること、セカンダリインデックスが主キーを経由すること——この2つが分かると、インデックスがなぜ効くのか、なぜ効かないことがあるのかを構造から説明できるようになります。
