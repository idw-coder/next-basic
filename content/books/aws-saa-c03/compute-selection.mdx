## 代表サービスの使い分け

| サービス | 向いている用途 |
|---|---|
| EC2 | OSやミドルウェアを細かく制御したい |
| Lambda | イベント駆動、短時間処理、サーバーレス |
| ECS | コンテナをAWSネイティブに運用したい |
| Fargate | サーバー管理なしでコンテナを動かしたい |
| EKS | Kubernetesを使いたい |
| Elastic Beanstalk | アプリを簡単にデプロイしたい |
| AWS Batch | 大量のバッチジョブを実行したい |

各サービスの役割はAWS公式の[AWS Lambda](https://docs.aws.amazon.com/ja_jp/lambda/latest/dg/welcome.html)、[ECS起動タイプ](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/launch_types.html)、[AWS Fargate](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/AWS_Fargate.html)、[Amazon EKS](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/what-is-eks.html)、[Elastic Beanstalk](https://docs.aws.amazon.com/ja_jp/elasticbeanstalk/latest/dg/Welcome.html)、[AWS Batch](https://docs.aws.amazon.com/ja_jp/batch/latest/userguide/what-is-batch.html)で確認できます。

## EC2を選ぶ場面

EC2は自由度が高い反面、OSパッチ、スケーリング、監視、可用性設計を自分で考える必要があります。

EC2が候補になる要件:

- OSやカーネル設定を制御したい
- 特定のエージェントやミドルウェアが必要
- GPUや特殊なインスタンスタイプを使いたい
- 既存アプリをそのまま移行したい

Auto ScalingとALBを組み合わせることで、可用性と伸縮性を高めます。

### インスタンスファミリーとサイズを選ぶ

EC2インスタンスタイプは、CPU、メモリ、ストレージ、ネットワークなどの比率が異なるインスタンスファミリーと、各ファミリー内のサイズで構成されます。

| ファミリーの分類 | 代表例 | 向くワークロード |
|---|---|---|
| 汎用 | M、T | Webサーバー、開発環境、CPUとメモリを均衡させたい処理 |
| コンピューティング最適化 | C | 高いCPU比率が必要なバッチ、ゲーム、エンコード |
| メモリ最適化 | R、X | インメモリDB、大規模キャッシュ、メモリ集約処理 |
| ストレージ最適化 | I、D、H | ローカルストレージの高IOPS・高スループットが必要な処理 |
| 高速コンピューティング | P、G、Inf、Trn | GPU、機械学習推論・学習、専用アクセラレーター |

T系はCPUクレジットを使うバースト可能な汎用インスタンスです。持続的にCPUを使う処理をT系だけで判断せず、CPUクレジットと長時間の負荷を確認します。

サイズは想定値だけで固定せず、CPU、メモリ、ネットワーク、EBS帯域幅、アプリケーションレイテンシーを負荷試験とCloudWatchで測ります。利用できるファミリーとプロセッサー、ネットワーク、ストレージ特性はAWS公式の[EC2インスタンスタイプ](https://docs.aws.amazon.com/ja_jp/AWSEC2/latest/UserGuide/instance-types.html)で確認できます。

EC2の永続ブロックストレージにはEBSを使い、複数サーバーで共有するファイルにはEFSやFSxを検討します。EBSタイプと共有ストレージの選択は[ストレージ選択](/books/aws-saa-c03/storage-selection)で扱います。

### プレイスメントグループを選ぶ

プレイスメントグループは、EC2インスタンスを基盤上へどのように配置するかを指定します。

| 戦略 | 配置 | 向く要件 |
|---|---|---|
| Cluster | 1つのAZ内でインスタンスを近接配置 | ノード間の低レイテンシーと高スループットが必要 |
| Partition | 論理パーティションごとに別のハードウェアへ分散 | Hadoop、Cassandra、Kafkaなど大規模分散処理の障害範囲を分けたい |
| Spread | 少数の重要インスタンスを異なるハードウェアへ分散 | インスタンス障害を相互に分離したい |

<MermaidDiagram
  chart={`
flowchart TB
    WORKLOAD["Workload Requirement"] --> CLUSTER["Cluster<br/>Close Placement"]
    WORKLOAD --> PARTITION["Partition<br/>Separate Failure Domains"]
    WORKLOAD --> SPREAD["Spread<br/>Distinct Hardware"]
    CLUSTER --> PERF["Low Latency / High Throughput"]
    PARTITION --> DISTRIBUTED["Large Distributed System"]
    SPREAD --> CRITICAL["Small Number of Critical Instances"]
`}
/>

Clusterはネットワーク性能を優先する一方、単一AZ内の配置です。高可用性要件と混同せず、複数AZの冗長化が必要なシステムでは障害範囲を別に設計します。各戦略の制約はAWS公式の[プレイスメントグループ](https://docs.aws.amazon.com/ja_jp/AWSEC2/latest/UserGuide/placement-groups.html)で確認できます。

### EC2 Auto Scalingを構成する

起動テンプレートにはAMI、インスタンスタイプ、Security Group、IAM Instance Profile、User Data、ストレージなど、EC2を再作成するための情報を定義します。Auto Scaling Groupでは複数AZのサブネット、最小・希望・最大キャパシティ、ヘルスチェック、スケーリングポリシーを設定します。

<MermaidDiagram
  chart={`
flowchart TB
    TEMPLATE["Launch Template<br/>AMI / Instance Type / IAM"] --> ASG["Auto Scaling Group<br/>min / desired / max"]
    METRIC["CloudWatch Metric"] --> POLICY["Scaling Policy"]
    POLICY --> ASG
    ASG --> EC2_A["EC2<br/>AZ-a"]
    ASG --> EC2_C["EC2<br/>AZ-c"]
    ALB["ALB Health Check"] --> ASG
`}
/>

Auto Scaling Groupは希望キャパシティを維持し、異常なインスタンスを置き換えます。起動テンプレートの構成はAWS公式の[Auto Scalingの起動テンプレート](https://docs.aws.amazon.com/ja_jp/autoscaling/ec2/userguide/launch-templates.html)、グループの動作は[Auto Scaling Group](https://docs.aws.amazon.com/ja_jp/autoscaling/ec2/userguide/auto-scaling-groups.html)で確認できます。

ターゲット追跡、ステップ、スケジュール、予測スケーリングと、ウォームアップ・スケールインの設計は[スケーラビリティと高可用性](/books/aws-saa-c03/scalability-and-ha)で扱います。

## Lambdaを選ぶ場面

Lambdaは、サーバー管理なしでコードを実行するサービスです。

向いている処理:

- S3にファイルが置かれたら処理する
- API Gateway経由で軽量APIを実行する
- [EventBridge Scheduler](/books/aws-saa-c03/monitoring-and-cloudwatch#eventbridge-scheduler)で定期実行する
- SQSメッセージを処理する

注意点:

- 実行時間の上限がある
- コールドスタートがある
- ステートレスに設計する
- VPC内接続が必要な場合はネットワーク設計も考える

Lambdaの実行時間、メモリ、同時実行数などの制約とクォータはAWS公式の[Lambdaのクォータ](https://docs.aws.amazon.com/ja_jp/lambda/latest/dg/gettingstarted-limits.html)で確認します。長時間処理、ホスト制御、常駐プロセスが必要ならEC2やコンテナを検討します。

## コンテナ: ECS/Fargate/EKS

コンテナを使う場合は、コンテナのオーケストレーターと実行基盤を分けて考えます。

| 要件 | 選択肢 |
|---|---|
| AWSでシンプルにコンテナ運用したい | ECS |
| EC2管理なしでコンテナを動かしたい | ECS on Fargate |
| Kubernetesエコシステムを使いたい | EKS |

KubernetesのAPIやエコシステムが要件ならEKS、AWSネイティブなコンテナ管理ならECSを検討します。EC2ホストを管理せずタスク単位で実行したい場合はFargate、ホストのインスタンスタイプやOSを制御したい場合はEC2起動タイプを選びます。

## ECR — コンテナイメージの保管庫

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
「ECRリポジトリにイメージをpushする」と言われたのですが、リポジトリってGitのことじゃないんですか？コードはもうGitHubにあるのに……
</SpeechBubble>

ここでつまずく人はとても多いです。**「リポジトリ」という同じ名前で、中身がまったく違うもの**が2つ登場するからです。まずはこの2つを切り分けましょう。

### GitリポジトリとECRリポジトリの違い

<Figure
  src="/images/aws-saa-c03-repository-difference.svg"
  alt="Gitリポジトリはソースコードとコミットを保管し、ECRリポジトリはDockerイメージとタグを保管する違いを示す図"
  maxWidth="760px"
  caption="Gitは作り方、ECRはビルド済みの実行パッケージを置く場所"
/>

| | Gitリポジトリ | ECRリポジトリ |
|---|---|---|
| **保管するもの** | ソースコード（テキストファイル） | Dockerイメージ（ビルド済みの実行環境一式） |
| **たとえるなら** | 料理のレシピ帳 | 完成した冷凍食品の倉庫 |
| **バージョン管理の単位** | コミット | イメージ＋タグ |
| **代表的なサービス** | GitHub、CodeCommit | ECR、Docker Hub |

<SpeechBubble character="/images/oksign_man_color.png" name="先生">
Gitに入っているのは「作り方」、ECRに入っているのは「できあがった実行パッケージ」です。コードをビルドしてイメージを作り、それをECRに置く——役割が直列につながっているだけで、どちらかがどちらかの代わりになるものではありません。
</SpeechBubble>

### イメージとは — アプリを丸ごとパックしたもの

**Dockerイメージ**は、アプリのコード、ランタイム（Node.jsやPython本体）、ライブラリ、OSレベルの設定までを1つのパッケージに固めたものです。対応するCPUアーキテクチャと実行環境で同じ依存関係を再現しやすくなります。「ECRイメージ」と呼ばれたら「ECRに保管されたDockerイメージ」という意味です。

### タグとは — 同じリポジトリ内のイメージを区別するラベル

1つのECRリポジトリには、ビルドのたびに新しいイメージが積み重なっていきます。それを区別するのが**タグ**で、`リポジトリ名:タグ` の `:` の後ろの部分を指します。

```
my-app:latest   ← 最新版という意味でよく使われるタグ
my-app:v1.2.3   ← リリースバージョンで識別
my-app:abc123   ← Gitのコミットハッシュで識別
```

Gitのタグと考え方は同じで、「特定の1つに名前を付けて参照しやすくする」仕組みです。タグを省略すると `latest` が暗黙的に使われます。

### 全体の流れ

コードがユーザーに届くまでの流れを図にすると、こうなります。

```
Gitリポジトリ（ソースコード）
    ↓ docker build
Dockerイメージ（実行可能なパッケージ）
    ↓ docker push
ECRリポジトリ（イメージの保管場所）
    ├── my-app:v1.2.3
    └── my-app:latest
    ↓ docker pull（タスク実行ロールの権限で）
ECSタスクとして起動
```

タスク定義には、この保管場所を指すイメージURIを書きます。実際のURIは次のような形式です。

```
123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/my-app:v1.2.3
（アカウントID）.dkr.ecr.（リージョン）.amazonaws.com/（リポジトリ名）:（タグ）
```

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
本番でも `latest` タグを指定しておけば、常に最新版が動いて便利そうですね！
</SpeechBubble>

<SpeechBubble character="/images/oksign_man_color.png" name="先生">
`latest` はpushによって指す先が変わり得るため、実行したイメージの追跡が難しくなります。本番では `v1.2.3` やコミットハッシュのような変更しないタグ、またはイメージダイジェストを使うと、デプロイ対象とロールバック先を特定しやすくなります。
</SpeechBubble>

<Callout type="note">
### 実務でのECR運用ポイント

- **イミュータブルタグ設定**: リポジトリの設定で「タグの上書き禁止」にできます。同じタグへの再pushを防ぎ、「`v1.2.3` なのに中身が変わっていた」という事故をなくせます
- **ライフサイクルポリシー**: 古いイメージを自動削除するルールを設定できます。不要なイメージを残し続けるとストレージ料金が積み上がります
- **イメージスキャン**: push時にOSパッケージの既知の脆弱性を自動スキャンできます

</Callout>

タグの上書き防止はAWS公式の[イメージタグのミュータビリティ](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/image-tag-mutability.html)、脆弱性検出は[Amazon ECRのイメージスキャン](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/image-scanning.html)、自動削除は[ライフサイクルポリシー](https://docs.aws.amazon.com/ja_jp/AmazonECR/latest/userguide/LifecyclePolicies.html)で確認できます。

<Callout type="warning">
### ECRへプライベート接続する判断ポイント

ECRからのイメージプルに必要な権限は**タスク実行ロール**に付与します（アプリが使うタスクロールではありません）。また、プライベートサブネットのFargateタスクがNATゲートウェイなしでECRからイメージを取得したい場合は、**VPCエンドポイント**（ECR用 + S3ゲートウェイ型）を作成します。イメージの実体はS3に保存されているため、S3のエンドポイントも必要になる点がひっかけどころです。

必要なECRとS3のエンドポイントはAWS公式の[Amazon ECSのVPCエンドポイント](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/vpc-endpoints.html)で確認できます。

</Callout>

## ECS・Fargate・タスク定義の全体像

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
ECS、Fargate、タスク定義、サービス、クラスター…… 用語がたくさん出てきて関係性がわかりません。
</SpeechBubble>

ECSの構造は、次の5つの層で整理すると見通しが良くなります。

| 層 | 役割 | たとえるなら |
|---|---|---|
| **タスク定義** | コンテナの設計図（どのイメージ、CPU/メモリ、環境変数、ポート等） | 料理のレシピ |
| **タスク** | タスク定義から起動された実体（1つ以上のコンテナの集合） | レシピから実際に作った料理 |
| **サービス** | タスクの望ましい数を維持し、ALB連携やデプロイ戦略を管理する | キッチンのシフト管理（常に3皿出す等） |
| **クラスター** | サービスやタスクを論理的にまとめる器 | レストランそのもの |
| **Fargate** | タスクが実際に動くサーバーレスコンピュート基盤 | 厨房設備をリースで用意してくれる業者 |

<SpeechBubble character="/images/oksign_man_color.png" name="先生">
ECSは「何をどう動かすか」を管理するオーケストレーター。Fargateは「どこで動かすか」を担当するコンピュート基盤、という切り分けです。
</SpeechBubble>

Fargateと対になるのが **EC2起動タイプ** です。EC2起動タイプではEC2インスタンスをクラスターに登録して自分で管理します。Fargateを選ぶとEC2インスタンス管理は不要になります。ホストレベルの制御や必要なハードウェア、タスクの実行条件、料金モデルを比較します。

## タスク定義 — コンテナの実行仕様書

タスク定義は、コンテナをどう動かすかをJSON形式でまとめた**テンプレート**です。タスク定義そのものがコンテナを動かすのではなく、「こう動かせ」という指示書にあたります。

主な設定項目:

| 項目 | 設定内容 |
|---|---|
| コンテナイメージ | ECRやDocker HubのイメージURI |
| CPU / メモリ | タスク全体およびコンテナごとの割り当て |
| 環境変数 | アプリケーションの設定値 |
| ポートマッピング | ホスト↔コンテナのポート対応 |
| ログ設定 | CloudWatch Logs等への出力先 |
| IAMロール | タスクロール、タスク実行ロール |

### リビジョン — タスク定義のバージョン管理

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
タスク定義を変更したいときはどうするんですか？直接編集できますか？
</SpeechBubble>

タスク定義は一度登録すると**変更不可**（イミュータブル）です。設定を変えたければ、新しい**リビジョン**として登録します。

```
my-app:1  ← 最初の登録
my-app:2  ← メモリを増やした版
my-app:3  ← 環境変数を追加した版
```

サービスは特定のリビジョンを参照して動くので、デプロイ時に新しいリビジョンを指定してローリングアップデートします。古いリビジョンは登録解除すると **INACTIVE** 状態になり、要件に応じて削除できます。実行中のタスクやサービスが参照するリビジョンへの影響を確認してから整理します。

タスク定義の構成とリビジョンはAWS公式の[Amazon ECSタスク定義](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/task_definitions.html)で確認できます。

<Callout type="note">
### ECRのタグと混同しない

`my-app:1` という表記はECRのイメージタグ（`my-app:v1.2.3`）とそっくりですが、別物です。ECRのタグは「**どのイメージか**」、タスク定義のリビジョンは「**そのイメージをどう動かすか（CPU、環境変数など）の設定が何版か**」を指します。新しいイメージをデプロイするときは、新タグのイメージURIを書いた新リビジョンを登録する、という二段構えになります。

</Callout>

## タスクロール vs タスク実行ロール

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
タスクロールとタスク実行ロール、名前が似すぎてどっちがどっちかわかりません……
</SpeechBubble>

この2つは名前が似ていますが、権限を使う主体が異なります。

| | タスク実行ロール（executionRoleArn） | タスクロール（taskRoleArn） |
|---|---|---|
| **誰が使うか** | ECSエージェント（インフラ側） | コンテナ内のアプリケーションコード |
| **いつ使うか** | コンテナを**起動するまで** | コンテナが**動いている間** |
| **代表的な権限** | ECRからのイメージプル、CloudWatch Logsへのログ送信、Secrets Manager / SSM Parameter Storeからの秘密値取得 | S3へのファイル保存、DynamoDBの読み書き、SQSへのメッセージ送信 |

<SpeechBubble character="/images/oksign_man_color.png" name="先生">
ざっくり言えば、実行ロールは「インフラ側の権限」、タスクロールは「アプリ側の権限」です。EC2のインスタンスプロファイルに近いのはタスクロールの方ですね。
</SpeechBubble>

<Callout type="warning">
### どの主体が権限を使うかでロールを選ぶ

「ECSタスク内のアプリからS3にアクセスしたい」→ **タスクロール**に権限を付与。「ECRからプライベートイメージをプルしたい」→ **タスク実行ロール**に権限を付与。問題文で「何が」「いつ」権限を使うのかを読み取ることが正答のカギです。

</Callout>

タスク実行ロールの用途はAWS公式の[Amazon ECSタスク実行IAMロール](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/task_execution_IAM_role.html)、アプリケーションへ渡す権限は[Amazon ECSタスクIAMロール](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/task-iam-roles.html)で確認できます。

## ECSのログ出力設定

タスク定義内のコンテナ定義で `logConfiguration` を指定することで、コンテナのログ出力先を設定します。

### awslogs ログドライバー（最も一般的）

CloudWatch Logsに直接送る構成で、最もシンプルです。

設定する3つのパラメータ:

| パラメータ | 内容 |
|---|---|
| `awslogs-group` | CloudWatch Logsのロググループ名 |
| `awslogs-region` | ロググループが存在するリージョン |
| `awslogs-stream-prefix` | ログストリーム名のプレフィックス |

### Fargateで使えるログドライバー

| ログドライバー | 用途 |
|---|---|
| `awslogs` | CloudWatch Logsへ直接送信 |
| `splunk` | Splunkへ送信 |
| `awsfirelens` | Fluent Bit / Fluentdで柔軟にルーティング |

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
FireLensって何が嬉しいんですか？awslogsで十分ではないですか？
</SpeechBubble>

awslogsはCloudWatch Logsに送るだけですが、**FireLens**を使うとFluent BitやFluentdコンテナを**サイドカー**として同じタスク内に立て、ログをS3、OpenSearch、Datadog等に柔軟にルーティングできます。「ログを複数の宛先に送りたい」「特定条件でフィルタリングしたい」といった要件が出たらFireLensが候補になります。

`awslogs`の設定項目はAWS公式の[awslogsログドライバー](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/using_awslogs.html)、FireLensの構成は[カスタムログルーティング](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/firelens-using-fluentbit.html)で確認できます。

## Fargateとネットワークモード

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
Fargateを使うと `awsvpc` が必須と聞きました。これは何ですか？
</SpeechBubble>

Fargateでは、ネットワークモードが **`awsvpc`** に限定されます。`awsvpc` モードでは、各タスクに**ENI**（Elastic Network Interface）が割り当てられ、タスクごとに独自のプライベートIPアドレスを持ちます。

これにより:

- タスク単位でセキュリティグループを適用できる
- VPC内の他リソースと同じネットワークでプライベート通信できる
- ALB / NLBのターゲットとして直接登録できる

<Callout type="note">
### ENIの上限に注意

`awsvpc` モードでは、タスクごとにENIが必要です。サブネット内のIPアドレス数やENIの上限が、同時に起動できるタスク数の制約になることがあります。大規模な場合はサブネットのCIDR設計に注意してください。

</Callout>

FargateタスクのENI、サブネット、Security Group、送信経路の要件はAWS公式の[Fargateタスクネットワーク](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/fargate-task-networking.html)で確認できます。

Web API、画像変換、長時間バッチを、実行時間と運用責任に合わせて別のコンピューティングサービスへ配置します。

設計では次を確認します。

1. 常時受け付けるWeb APIはECSサービスで必要タスク数を維持する
2. タスクを複数AZへ配置し、ALBのヘルスチェックで正常なタスクへ送る
3. イベント単位の短時間処理はLambdaへ分離する
4. 長時間の大量ジョブはAWS Batchへ送り、キューとコンピューティング環境を分ける
5. ECRイメージを変更しないタグまたはダイジェストで指定する
6. CPU、メモリ、タスク数、処理時間、エラー、キュー滞留を監視する

## 試験問題での判断パターン

| 問題文の要件 | 第一候補 | 判断理由 |
|---|---|---|
| OS、エージェント、カーネル、特殊ハードウェアを制御したい | EC2 | インスタンスとOSを利用者が管理できる |
| S3・SQS・EventBridgeのイベントごとに短時間コードを実行したい | Lambda | サーバー管理なしでイベントに応じて実行できる |
| AWSネイティブにコンテナを管理したい | ECS | タスクとサービスでコンテナを管理できる |
| EC2ホストを管理せずコンテナを実行したい | ECS on Fargate | タスク単位でコンピューティングを利用できる |
| Kubernetes APIとエコシステムが必要 | EKS | マネージドKubernetesコントロールプレーンを使える |
| ソースコードからWebアプリを簡単にデプロイしたい | Elastic Beanstalk | 環境のプロビジョニングとデプロイを管理できる |
| 大量の依存関係を持つバッチジョブをキューで実行したい | AWS Batch | ジョブキューとコンピューティング環境を管理できる |
| EC2間の低レイテンシーと高スループットを優先したい | Clusterプレイスメントグループ | インスタンスを1つのAZ内で近接配置できる |
| 複数AZでEC2台数を負荷に応じて増減したい | EC2 Auto Scaling | 希望台数の維持とスケーリングポリシーを使える |

この表は、要件から第一候補を絞るための筆者の整理です。実際には実行時間、状態、起動速度、ネットワーク、ストレージ、可用性、運用責任、費用を確認します。

## よくあるハマりどころ

### ECSとFargateを同じ種類のサービスとして比較する

ECSはコンテナの配置と状態を管理し、FargateはECSタスクを実行するコンピューティング基盤です。ECSではFargateとEC2起動タイプを要件に合わせて選びます。

### Lambdaへ長時間処理やローカル状態を持たせる

Lambdaの実行時間と一時ストレージの制約を確認し、処理を分割できない長時間ジョブはECS、AWS Batch、EC2などを検討します。状態はS3、DynamoDB、RDSなど外部の永続ストアへ保存します。

### Clusterプレイスメントグループを高可用性のために使う

Cluster戦略はネットワーク性能を優先して1つのAZへ近接配置します。AZ障害へ備える目的では、複数AZへの分散と復旧構成を別に設計します。

### Auto Scaling Groupへ手作業で変更したEC2を置く

異常なインスタンスは置き換えられるため、AMI、起動テンプレート、User Data、デプロイ処理から同じ構成を再作成できるようにします。

## まとめ

コンピューティング選択では、制御したい範囲と運用負荷のバランスを見ます。

- <Marker>OSやミドルウェアまで細かく制御したいならEC2を選ぶ</Marker>
- イベント駆動ならLambda
- コンテナならECS/Fargate
- Kubernetes要件があるならEKS
- 簡単なデプロイならElastic Beanstalk
- EC2は負荷特性に合うインスタンスファミリー、配置、Auto Scalingを選ぶ

RDS、Aurora、DynamoDB、ElastiCache、Redshiftなどの使い分けは、[データベース選択](/books/aws-saa-c03/database-selection)で扱います。
