## CloudWatch Metrics

CloudWatch Metricsは、AWSリソースの**数値データを時系列で収集・可視化**する機能です。EC2のCPU使用率、ELBのリクエスト数、RDSの接続数など、多くのAWSサービスが自動的にメトリクスを送信します。

### 標準メトリクスとカスタムメトリクス

| 種類 | 説明 | 例 |
|---|---|---|
| 標準メトリクス | AWSサービスが自動で送信。収集間隔や料金はサービスごとに確認する | EC2: CPUUtilization、NetworkIn |
| カスタムメトリクス | ユーザーが独自に送信する | メモリ使用率、アプリのキュー長 |

<Callout type="warning">
### EC2のメモリ使用率は標準メトリクスに含まれない

EC2の標準メトリクスにはCPU使用率やネットワークは含まれますが、**メモリ使用率やディスク使用率は含まれません**。これらを監視するにはCloudWatch Agentをインストールしてカスタムメトリクスとして送信する必要があります。タスク2.2の「ビジネス要件に基づいてメトリクスを特定する」に対応する判断です。

</Callout>

### メトリクスの期間と保持

| 期間 | 保持期間 |
|---|---|
| 1秒（高解像度） | 3時間 |
| 60秒（標準） | 15日 |
| 5分 | 63日 |
| 1時間 | 15ヶ月 |

保持期間が過ぎた短い期間のデータポイントは、長い期間へ集約されます。期間ごとの保持仕様はAWS公式の[CloudWatchメトリクスの概念](https://docs.aws.amazon.com/ja_jp/AmazonCloudWatch/latest/monitoring/cloudwatch_concepts.html)で確認できます。

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
メトリクスを元に自動で何かさせたい場合はどうしますか？
</SpeechBubble>

それが **CloudWatch Alarms** の役割です。メトリクスがしきい値を超えたら、SNS通知を送ったり、Auto Scalingのスケールアウトをトリガーしたり、EC2インスタンスを停止・再起動したりできます。

## CloudWatch Alarmsのしきい値・評価期間・アクション

CloudWatch Alarmは、選んだメトリクスまたは数式を一定間隔で評価し、条件に応じて状態を変更します。

| 設定 | 役割 | 例 |
|---|---|---|
| Statistic | 評価する集計値 | 平均、合計、最大値、パーセンタイル |
| Period | 1つのデータポイントへ集計する時間 | 1分間の平均CPU使用率 |
| Threshold | 異常とみなす境界 | CPU使用率が80%より大きい |
| Evaluation periods | 判定に使う直近の期間数（N） | 直近5期間を見る |
| Datapoints to alarm | N期間中に違反が必要な回数（M） | 5期間中3回でALARM |
| Missing data | データがない期間の扱い | 欠損、不足、正常、異常として扱う |
| Action | 状態変化時に実行する操作 | SNS通知、EC2操作、Auto Scaling |

たとえば「1分平均のCPU使用率が、直近5期間のうち3期間で80%を超えたら通知する」と設定すると、単発の短い上昇ではなく継続的な負荷を検知できます。どの程度の変動を許容するかはワークロードごとに決めます。

### 3つの状態

| 状態 | 意味 |
|---|---|
| `OK` | しきい値の条件を満たしていない |
| `ALARM` | しきい値の条件を満たした |
| `INSUFFICIENT_DATA` | 判定に必要なデータが不足している |

アラームは状態が変化したときにアクションを実行します。メトリクスアラームではSNS、EC2アクション、EC2 Auto Scaling、Systems Managerなどを利用できます。設定要素とアクションはAWS公式の[CloudWatchアラーム](https://docs.aws.amazon.com/ja_jp/AmazonCloudWatch/latest/monitoring/CloudWatch_Alarms.html)で確認できます。

<MermaidDiagram
  chart={`
flowchart TB
    METRIC["Metric<br/>CPU / Queue / Errors"] --> PERIOD["Period and Statistic"]
    PERIOD --> EVAL["M of N Evaluation"]
    EVAL --> STATE{"Alarm State"}
    STATE -->|"OK"| NORMAL["Continue Monitoring"]
    STATE -->|"ALARM"| SNS["SNS Notification"]
    STATE -->|"ALARM"| SCALE["Auto Scaling Action"]
    STATE -->|"INSUFFICIENT_DATA"| REVIEW["Check Missing Data"]
`}
/>

複数のメトリクスアラームを条件式で組み合わせる**複合アラーム**は、通知ノイズを減らす用途に使えます。ただし複合アラームからEC2操作やAuto Scalingアクションは実行できないため、通知と自動スケーリングの要件を分けます。

<Callout type="warning">
### 欠損データを正常と決めつけない

リクエストがないときに値を送らないメトリクスと、常に値を送るはずの死活監視では、欠損の意味が異なります。メトリクスの発行方法を確認し、欠損を「正常」「異常」「状態維持」のどれとして扱うかを決めます。

</Callout>

## CloudWatch Logs

<Figure src="/images/search_woman_color.png" alt="ログを調査している人のイラスト" maxWidth="320px" />

CloudWatch Logsは、AWSリソースやアプリケーションの**ログを収集・保存・検索**するサービスです。

### ログの階層構造

<MermaidDiagram
  chart={`
flowchart TB
    LG["Log Group"] --> LS1["Log Stream 1"]
    LG --> LS2["Log Stream 2"]
    LG --> LS3["Log Stream 3"]
    LS1 --> E1["Log Event"]
    LS1 --> E2["Log Event"]
    LS1 --> E3["Log Event"]
`}
/>

| 用語 | 説明 |
|---|---|
| ロググループ（Log Group） | ログの保持期間やアクセス制御を共有するログストリームのまとまり。通常はサービスやアプリ単位で作成する |
| ログストリーム（Log Stream） | 時系列のログイベントの連続。通常はインスタンスやコンテナ単位で作成される |
| ログイベント（Log Event） | タイムスタンプとメッセージで構成される1件のログ |

### 主なログ送信元

| 送信元 | 方法 |
|---|---|
| EC2 | CloudWatch Agent をインストール |
| ECS / Fargate | `awslogs` ログドライバーを指定 |
| Lambda | 自動で `/aws/lambda/{関数名}` に送信 |
| API Gateway | ステージの設定で有効化 |
| VPC Flow Logs | VPC・Subnet・ENI単位で有効化 |
| Route 53 | DNSクエリログ |

<Callout type="note">
### ログの保持期間はデフォルト「無期限」

CloudWatch Logsのロググループは、デフォルトでログを無期限に保持します。長期運用ではログ量に応じたコストが増えるため、保持期間（1日〜10年）を設定するか、S3へエクスポートすることを検討します。

保持期間の仕様はAWS公式の[Amazon CloudWatch Logsとは](https://docs.aws.amazon.com/ja_jp/AmazonCloudWatch/latest/logs/WhatIsCloudWatchLogs.html)で確認できます。監査、障害調査、個人情報、費用の要件に合わせてロググループごとに保持期間を決めます。

</Callout>

### サブスクリプションフィルター

ログをリアルタイムに別サービスへ転送する機能です。[データ取り込みと分析](/books/aws-saa-c03/data-ingestion-and-analytics)の章で扱ったECS → OpenSearchの構成でも使われます。

| 転送先 | 用途 |
|---|---|
| Kinesis Data Firehose | S3やOpenSearchへの配信 |
| Lambda | ログのリアルタイム加工・通知 |
| Kinesis Data Streams | ストリーム処理 |

## CloudWatch Logs Insights

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
CloudWatch Logsに貯まったログを分析したいとき、全部目で見るのは無理ですよね？
</SpeechBubble>

CloudWatch Logs Insightsは、ロググループに対して**SQLライクなクエリで検索・集計・可視化**できる機能です。大量のログから特定のパターンを抽出したり、エラーの傾向を集計したりできます。

### クエリの例

```text
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

上記のクエリは「ERRORを含むログを新しい順に20件取得する」という意味です。

<Figure src="/images/creative_color.png" alt="分析結果からインサイトを得る人のイラスト" maxWidth="320px" />

### Logs Insightsの特徴

| 特徴 | 説明 |
|---|---|
| スキャンベースの課金 | スキャンしたデータ量に応じた従量課金 |
| 複数ロググループの横断クエリ | 最大50のロググループを同時に検索できる |
| 自動フィールド検出 | JSON形式のログは自動でフィールドをパースする |
| 可視化 | クエリ結果を棒グラフや折れ線グラフで表示できる |

Logs Insightsの検索・分析機能と現在の制限はAWS公式の[CloudWatch Logs Insightsでログを分析する](https://docs.aws.amazon.com/ja_jp/AmazonCloudWatch/latest/logs/AnalyzingLogData.html)で確認できます。

<Callout type="note">
### Logs InsightsとOpenSearchの使い分け

Logs Insightsはクエリごとのアドホック分析に向いています。常時稼働のダッシュボードや大規模な全文検索が必要な場合は、[OpenSearch Service](/books/aws-saa-c03/data-ingestion-and-analytics#amazon-opensearch-service) の方が適しています。

</Callout>

サービス固有メトリクスはAWS公式の[ECSのCloudWatchメトリクス](https://docs.aws.amazon.com/ja_jp/AmazonECS/latest/developerguide/cloudwatch-metrics.html)、[Lambdaメトリクス](https://docs.aws.amazon.com/ja_jp/lambda/latest/dg/monitoring-metrics-types.html)、[RDSのモニタリング](https://docs.aws.amazon.com/ja_jp/AmazonRDS/latest/UserGuide/MonitoringOverview.html)、[AWS DMSのモニタリング](https://docs.aws.amazon.com/ja_jp/dms/latest/userguide/CHAP_Monitoring.html)、[VPC Flow Logs](https://docs.aws.amazon.com/ja_jp/vpc/latest/userguide/flow-logs.html)で確認できます。

CloudWatchは性能と可用性の監視が中心です。費用と使用量はCost Explorer・AWS Budgets、S3の利用傾向はS3 Storage Lensで確認します。費用分析は[コンピューティングのコスト最適化](/books/aws-saa-c03/cost-optimized-compute)、Storage Lensは[ストレージのコスト最適化](/books/aws-saa-c03/cost-optimized-storage)で扱います。

## CloudTrailとAWS Configで変更を追跡する

CloudWatchが性能と動作を監視するのに対し、CloudTrailはAWS上の操作、AWS Configはリソース設定の状態と変化を記録します。

| 確認したいこと | サービス | 記録する内容 |
|---|---|---|
| 誰が、いつ、どのAPIを呼んだか | AWS CloudTrail | ユーザー、ロール、AWSサービスによるコンソール・CLI・SDK・API操作 |
| リソースがどの設定だったか | AWS Config | 対応リソースの設定、関係、設定履歴 |
| 設定が組織の基準に準拠しているか | AWS Config Rules | ルールに対する準拠・非準拠 |
| 操作ログを長期保存・分析したい | CloudTrail Trail / CloudTrail Lake | S3への配信、イベントデータストアへの保存とクエリ |

[AWS CloudTrail](https://docs.aws.amazon.com/ja_jp/awscloudtrail/latest/userguide/cloudtrail-user-guide.html)はアカウント内の操作をイベントとして記録します。イベント履歴では管理イベントを確認でき、証跡を作るとS3へ配信し、必要に応じてCloudWatch LogsやEventBridgeとも連携できます。

[AWS Config](https://docs.aws.amazon.com/ja_jp/config/latest/developerguide/WhatIsConfig.html)はリソースの設定と関係の履歴を提供し、Config Rulesで設定を評価します。たとえばSecurity Groupがいつ変更されたかをConfigで調べ、変更を実行した主体とAPI呼び出しをCloudTrailで調べます。

<MermaidDiagram
  chart={`
flowchart TB
    CHANGE["AWS Resource Change"] --> TRAIL["CloudTrail<br/>Who / When / API"]
    CHANGE --> CONFIG["AWS Config<br/>State / Relationship / History"]
    TRAIL --> S3["S3 / CloudTrail Lake"]
    TRAIL --> EVENT["CloudWatch Logs / EventBridge"]
    CONFIG --> RULE["Config Rules<br/>Compliance Evaluation"]
    EVENT --> RESPONSE["Alert / Automated Response"]
    RULE --> RESPONSE
`}
/>

<Callout type="note">
### CloudTrailとAWS Configは置き換え関係ではない

CloudTrailだけでは、ある時点のリソース設定全体を判断できません。AWS Configだけでは、すべてのAPI呼び出しの詳細を追う用途を代替できません。「操作」と「設定状態」を組み合わせて変更原因を調べます。

</Callout>

## AWS X-Rayで分散トレーシングする

分散トレーシングは、1つのリクエストが複数のサービスや依存先を通る経路と処理時間を関連付けて追跡する方法です。メトリクスで「APIが遅い」と分かっても原因サービスを特定できないとき、AWS X-Rayのトレースを使ってリクエスト単位で調べます。

| 用語 | 役割 |
|---|---|
| Trace | 1つのリクエスト全体の記録 |
| Segment | 1つのサービスやリソースが行った処理の記録 |
| Subsegment / Span | Segment内の処理や下流呼び出しの記録 |
| Trace Map | サービスと依存先、エラー、レイテンシーを可視化する図 |

<MermaidDiagram
  chart={`
flowchart TB
    CLIENT["Client Request"] --> API["API Gateway<br/>Trace Segment"]
    API --> LAMBDA["Lambda<br/>Trace Segment"]
    LAMBDA --> DB["DynamoDB<br/>Downstream Span"]
    LAMBDA --> EXTERNAL["External API<br/>Downstream Span"]
    API --> MAP["X-Ray Trace Map"]
    LAMBDA --> MAP
    DB --> MAP
    EXTERNAL --> MAP
`}
/>

X-Rayは共通のリクエストに属するSegmentをTraceへまとめ、サービス間の経路を可視化します。概念はAWS公式の[X-Rayの概念](https://docs.aws.amazon.com/ja_jp/xray/latest/devguide/xray-concepts.html)で確認できます。

新しくアプリケーションを計測する場合は、AWS Distro for OpenTelemetry（ADOT）とCloudWatch Agent、またはOpenTelemetry SDKとCollectorを使ってメトリクスとトレースを送る構成を検討します。現在の計測方法とX-Ray SDKとの比較は[CloudWatch Application Signalsでサポートされる計測設定](https://docs.aws.amazon.com/ja_jp/AmazonCloudWatch/latest/monitoring/Getting-Started-App-Signals.html)で確認できます。

<Marker>Metricsは集計された傾向、Logsは個別の記録、Tracesはサービスをまたぐ1リクエストの経路を調べるために使います。</Marker>

<Callout type="warning">
### トレースはすべて自動でつながるとは限らない

リクエスト経路の各サービスでTrace Contextを伝播し、必要な箇所を計測します。サンプリングで収集量と費用を制御しつつ、エラーや高レイテンシーの調査に必要なトレースを残します。

</Callout>

## Amazon EventBridge

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
EventBridgeはCloudWatchの一部なんですか？別のサービスですか？
</SpeechBubble>

Amazon EventBridgeは、もともと **CloudWatch Events** という名前でした。現在は独立したサービスとして進化していますが、機能的にはAWSリソースの**状態変化をイベントとして検知し、ルールに基づいてアクションを実行**するサービスです。

<Figure src="/images/meeting_color.png" alt="イベント駆動の連携を設計するイラスト" maxWidth="320px" />

### EventBridgeの仕組み

<MermaidDiagram
  chart={`
flowchart TB
    SRC["Event Source"] -->|"Event"| BUS["Event Bus"]
    BUS --> R1["Rule 1"]
    BUS --> R2["Rule 2"]
    R1 --> T1["Lambda"]
    R2 --> T2["SQS"]
    R2 --> T3["Step Functions"]
`}
/>

| 構成要素 | 説明 |
|---|---|
| イベントソース | AWSサービス、SaaSアプリ、カスタムアプリからイベントを発生させる |
| イベントバス | イベントを受け取るパイプライン。デフォルトバスの他にカスタムバスも作れる |
| ルール | イベントパターンまたはスケジュールに基づいてターゲットを呼び出す |
| ターゲット | Lambda、SQS、SNS、Step Functions、ECS Taskなど |

### よく使われるパターン

| ユースケース | イベントソース | ターゲット |
|---|---|---|
| EC2インスタンスが停止したら通知 | EC2 State Change | SNS |
| S3にファイルがアップロードされたら処理 | S3 PutObject | Lambda |
| 毎日深夜にバッチ処理を実行 | スケジュール（cron）。今は後述のEventBridge Schedulerが推奨 | Lambda / ECS Task |
| AWS Health イベントを検知して対応 | AWS Health | Lambda / SNS |

<SpeechBubble character="/images/fork_suit_man_color.png" name="先生" side="right">
EventBridgeは[疎結合アーキテクチャ](/books/aws-saa-c03/decoupled-architecture)の章でも扱っています。試験では「AWSサービスの状態変化に自動対応する」要件でEventBridgeが正解になります。
</SpeechBubble>

<Callout type="note">
### EventBridge vs SNS

どちらもイベントを配信しますが、EventBridgeは**イベントの内容でフィルタリング**できるのが強みです。SNSはシンプルなPub/Subで、EventBridgeはイベントパターンマッチングによる細かいルーティングが可能です。

</Callout>

### イベントパターンの書き方

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
「イベントの内容でフィルタリングできる」とありましたが、ルールにはどうやって条件を書くんですか？
</SpeechBubble>

ルールの条件は**イベントパターン**というJSONで書きます。イベントパターンは、絞り込みたいイベントと同じ形をしています。たとえばEC2インスタンスが終了（`terminated`）したときのイベントは、次のような形で届きます。

```json
{
  "version": "0",
  "detail-type": "EC2 Instance State-change Notification",
  "source": "aws.ec2",
  "account": "111122223333",
  "region": "us-west-1",
  "detail": {
    "instance-id": "i-1234567890abcdef0",
    "state": "terminated"
  }
}
```

このイベントだけを拾うルールのイベントパターンは、次のように書きます。

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": {
    "state": ["terminated"]
  }
}
```

照合の決まりは次の2つです。

1. **値は配列で書き、どれか1つに一致すればよい**。`"state": ["terminated", "stopped"]` なら、終了か停止のどちらでも一致する
2. **複数のフィールドを書いたら、すべてを満たす必要がある**。上の例では、`source`・`detail-type`・`detail.state` の3つがすべて一致したときだけルールが動く

完全一致のほかに、次のような条件も書けます（[コンテンツフィルタリング](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-event-patterns-content-based-filtering.html)）。

| 条件 | 書き方の例 | 意味 |
|---|---|---|
| 前方一致 | `"region": [{ "prefix": "us-" }]` | `us-` で始まる |
| 後方一致 | `"FileName": [{ "suffix": ".png" }]` | `.png` で終わる |
| 否定 | `"state": [{ "anything-but": "initializing" }]` | `initializing` 以外 |
| 数値の範囲 | `"Price": [{ "numeric": [">", 10, "<=", 20] }]` | 10より大きく20以下 |
| 存在する | `"ProductName": [{ "exists": true }]` | フィールドがある |

<Marker>1つのルールに設定できるターゲットは最大5つです。</Marker>同じイベントをもっと多くの宛先に配りたいときは、ルールを分けます（[イベントバス](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-event-bus.html)）。

### イベントバスの種類

| 種類 | 受け取るイベント | 使いどころ |
|---|---|---|
| デフォルトイベントバス | AWSサービスのイベント（EC2の状態変化など）を自動で受け取る | AWSリソースの変化に反応する |
| カスタムイベントバス | 自分のアプリケーションが送るイベント | 注文確定などアプリのイベントを配る |
| パートナーイベントバス | SaaSパートナーが送るイベント | 外部SaaSの出来事に反応する |

公式ドキュメントは、新しいアプリケーションならカスタムイベントバスから始めるよう勧めています（[イベントバス](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-event-bus.html)）。アプリケーションからは、`PutEvents` APIでカスタムイベントを送ります。

```bash
aws events put-events \
  --entries '[{"EventBusName": "orders", "Source": "com.example.orders", "DetailType": "OrderPlaced", "Detail": "{\"orderId\": \"1234\"}"}]'
```

| パラメーター | 説明 |
|---|---|
| `EventBusName` | 送り先のイベントバス（名前かARN）。省略するとデフォルトイベントバス |
| `Source` | イベントの送り元を表す名前。ルールの `source` で絞り込む |
| `DetailType` | イベントの種類。ルールの `detail-type` で絞り込む |
| `Detail` | イベントの中身（JSON文字列）。ルールの `detail` で絞り込む |

`Source`・`DetailType`・`Detail` の3つがないエントリは失敗します（[PutEventsRequestEntry](https://docs.aws.amazon.com/eventbridge/latest/APIReference/API_PutEventsRequestEntry.html)）。

**戻り値**：エントリごとの結果（成功なら `EventId`、失敗なら `ErrorCode` と `ErrorMessage`）。一部のエントリが失敗しても残りは処理されるので、失敗したエントリだけ送り直す（[PutEvents でのイベントの送信](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-putevents.html)）

SaaSのイベントを受け取るには、パートナー側で作られた**パートナーイベントソース**を、自分のアカウントのパートナーイベントバスに関連付けます（[SaaSパートナーからイベントを受信する](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-saas.html)）。

<Figure src="/images/inspiration_color.png" alt="イベントの流れを組み立てるイラスト" maxWidth="320px" />

### 別のアカウントへイベントを送る

複数のAWSアカウントを使っていると、各アカウントのイベントを監視用のアカウントに集めたくなります。EventBridgeでは、**別のアカウントのイベントバスをルールのターゲットにできます**。

<MermaidDiagram
  chart={`
flowchart TB
    SRC["アカウントAのイベント"] --> RA["アカウントAのルール"]
    RA -->|"IAMロール"| BUS["アカウントBのイベントバス"]
    BUS --> RB["アカウントBのルール"]
    RB --> T["ターゲット"]
`}
/>

設定は次の3つです（[AWS アカウント間でのイベントの送受信](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-cross-account.html)）。

1. **受信側:** イベントバスの**リソースベースポリシー**で、送信を許すアカウントIDか、Organizationsの組織IDを指定する
2. **送信側:** ルールのターゲットに、受信側のイベントバスのARNを指定する。送信側にはイベントを送るためのIAMロールが必要
3. **受信側:** 届いたイベントに一致するルールを作り、ターゲットを設定する

<Callout type="warning">
### 受信側のルールには account を書く

他のアカウントからイベントを受け入れると、受信側のルールのうち、そのイベントに一致するものがすべて動きます。公式は、他のアカウントからのイベントを受け入れるアカウントでは、ルールのイベントパターンに `account` を書いて、どのアカウントのイベントかを絞るよう強く勧めています。また、受信側でさらに別のアカウントへ転送するルールを作っても、受け取ったイベントは3つ目のアカウントには届きません。

</Callout>

### アーカイブとリプレイ

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
ターゲットのLambdaにバグがあって、イベントを正しく処理できていなかったら、そのイベントはもう取り戻せないんですか？
</SpeechBubble>

**アーカイブ**を作っておけば取り戻せます。アーカイブは、イベントバスに届いたイベントを（イベントパターンで絞り込んで）保存しておく機能です。保持日数を指定でき、指定しなければ無期限に保存されます。

保存したイベントは**リプレイ**で、イベントバスにもう一度流せます（[イベントのアーカイブと再生](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-archive.html)）。

1. リプレイする期間（開始時刻と終了時刻）を指定する
2. 必要なら、そのうち特定のルールだけに流すよう指定する
3. イベントは、アーカイブ元のイベントバスに流れる。別のイベントバスには流せない
4. リプレイしてもアーカイブからイベントは消えない

リプレイされたイベントには `replay-name` フィールドが付くので、受け取った側で「再送されたイベントか」を見分けられます。バグを直したあとに処理をやり直す、新しく追加したターゲットに過去のイベントを流して試す、といった使い方をします。

### EventBridge Pipes

**EventBridge Pipes**は、1つのソースと1つのターゲットを、間に処理を挟んでつなぐ機能です（[Amazon EventBridge Pipes](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-pipes.html)）。

<MermaidDiagram
  chart={`
flowchart TB
    SRC["ソース（SQSなど）"] --> F["フィルター"]
    F --> E["エンリッチメント"]
    E --> T["ターゲット（Step Functionsなど）"]
`}
/>

| 段階 | 役割 | 必須か |
|---|---|---|
| ソース | イベントを取り出す元。SQSキュー、Kinesis Data Streams、DynamoDBストリーム、Amazon MQ、Amazon MSK、Apache Kafkaのいずれか | 必須 |
| フィルター | イベントパターンで、ターゲットに送るイベントを絞る。課金されるのは一致したイベントだけ | 任意 |
| エンリッチメント | Lambda関数、Step Functions（Expressワークフロー）、API Gateway、API送信先のいずれかを呼んで、イベントのデータを補う | 任意 |
| ターゲット | 処理したイベントの送り先 | 必須 |

たとえば「SQSに届いた注文から、決済済みのものだけを選び、顧客情報を足してStep Functionsのワークフローを始める」処理を、つなぎ役のLambdaを書かずに作れます。ソースの順序が保証されている場合は、その順序のままターゲットまで届きます（[パイプのソース](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-pipes-event-source.html)、[エンリッチメント](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/pipes-enrichment.html)）。

公式ドキュメントは、<Marker>Pipesをソースとターゲットをつなぐポイントツーポイントの連携、イベントバスを多対多のルーティング</Marker>に向くものと位置づけています。複数のサービスにイベントを配るならイベントバス、決まったソースとターゲットを1本でつなぐならPipesです。

### API送信先

**API送信先**（API destinations）を使うと、ルールやPipesのターゲットに外部のHTTPSエンドポイントを指定できます（[API 送信先](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-api-destinations.html)）。

- 認証方法と認証情報は**接続**（Connection）で設定する。認証情報はSecrets Managerに保存される
- 1秒あたりの呼び出し回数の上限を設定でき、外部APIに負荷をかけすぎないようにできる
- 呼び出しに失敗したイベントは再試行され、上限を超えたらDLQに送るか破棄される。上限を低くしすぎると処理が追いつかないため、DLQを設定しておく

<SpeechBubble character="/images/fork_suit_man_color.png" name="先生" side="right">
問題文の要件とEventBridgeの機能は、「複数アカウントのイベントを1か所に集める → 別アカウントのイベントバスをターゲットにする」「過去のイベントをもう一度処理したい → アーカイブとリプレイ」「SQSからStep Functionsへ、コードを書かずにつなぎたい → Pipes」「外部のSaaSのAPIを呼びたい → API送信先」と対応させて覚えると整理しやすいです。これは公式ドキュメントの各機能の説明をもとにした、筆者の整理です。
</SpeechBubble>

## EventBridge Scheduler

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
上の表に「毎日深夜にバッチ処理を実行」がありました。決まった時刻に動かすのも、EventBridgeのルールで作るんですか？
</SpeechBubble>

ルールにスケジュールを設定するやり方（**スケジュールルール**）もありますが、AWSの公式ドキュメントは、スケジュールでターゲットを呼び出すなら **EventBridge Scheduler** を使うよう勧めています。スケジュールルールは「EventBridgeのレガシー機能」と書かれています（[スケジュールに従って実行するルールの作成](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-create-rule-schedule.html)）。

EventBridge Schedulerは、**スケジュールの作成・実行・管理だけを受け持つサーバーレスのサービス**です。イベントバスやルールは使わず、スケジュールそのものにターゲットを1つ設定します。

<Figure src="/images/calling_suit_man_color.png" alt="決まった時刻に処理を呼び出す人のイラスト" maxWidth="320px" />

### スケジュールルールとの違い

| 項目 | スケジュールルール | EventBridge Scheduler |
|---|---|---|
| 位置づけ | EventBridgeのレガシー機能 | スケジュール専用のサービス。公式の推奨 |
| スケジュールの種類 | `rate` / `cron` | `rate` / `cron` / 1回限り（`at`） |
| タイムゾーン | UTC+0 のみ | タイムゾーンを指定できる（例: `Asia/Tokyo`） |
| 作れる場所 | デフォルトのイベントバスだけ | スケジュールグループにまとめて管理 |

スケジュールルールでは、日本時間の深夜2時に動かしたければ、UTCに直して「前日の17時」と書く必要があります。EventBridge Schedulerならタイムゾーンを指定して、そのまま「2時」と書けます。タイムゾーンを指定したスケジュールは夏時間にも自動で合わせられます（[スケジュールの種類](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/schedule-types.html)）。

### スケジュール式の3種類

| 式 | 書き方 | 例 | 意味 |
|---|---|---|---|
| rate式 | `rate(値 単位)` | `rate(5 minutes)` | 5分ごとに実行 |
| cron式 | `cron(分 時 日 月 曜日 年)` | `cron(0 2 * * ? *)` | 毎日2時0分に実行 |
| at式（1回限り） | `at(yyyy-mm-ddThh:mm:ss)` | `at(2026-12-01T09:00:00)` | 指定した日時に1回だけ実行 |

cron式では、日と曜日の両方に `*` は書けません。片方に `*` を使ったら、もう片方は `?` にします。

<Callout type="warning">
### 1回限りのスケジュールは、実行後も残る

`at` 式で作ったスケジュールは、実行が終わっても自動では消えず、アカウントのスケジュール数の上限にも数えられます。公式は実行後に削除することを勧めており、作成時に `ActionAfterCompletion` を `DELETE` にしておくと、完了後に自動で削除されます（[EventBridge スケジューラのクォータ](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/scheduler-quotas.html)、[CreateSchedule API](https://docs.aws.amazon.com/scheduler/latest/APIReference/API_CreateSchedule.html)）。

</Callout>

### 仕組み — 実行ロールとDLQ

<MermaidDiagram
  chart={`
flowchart TB
    ROLE["実行ロール"] --- SCH["EventBridge Scheduler"]
    SCH -->|"cron / rate / at"| T["ターゲット"]
    SCH -->|"再試行を使い切った"| DLQ["SQS DLQ"]
`}
/>

時刻が来ると、EventBridge Schedulerは次の順で動きます。

1. スケジュールに設定された**実行ロール**（IAMロール）を引き受ける
2. そのロールの権限でターゲットを呼び出す
3. 呼び出しに失敗したら、設定した再試行回数と最大保持時間の範囲で再試行する
4. それでも届かなかったイベントは、設定していれば**DLQ**（SQSの標準キュー）に送る

<Marker>ターゲットを呼び出す権限は、実行ロールにアタッチしたポリシーで与えます。</Marker>ロールの信頼ポリシーで、EventBridge Schedulerがそのロールを引き受けられるようにしておく必要があります（[EventBridge スケジューラのセットアップ](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/setting-up.html)）。DLQにはFIFOキューは使えません（[デッドレターキューの設定](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/configuring-schedule-dlq.html)）。

### 呼び出せるターゲット

| 種類 | 内容 |
|---|---|
| テンプレート化されたターゲット | Lambda、SQS、SNS、Step Functions、ECS（RunTask）、EventBridge（イベントバス）など12サービスの代表的な操作を、ARNを指定するだけで呼び出せる |
| ユニバーサルターゲット | 270以上のAWSサービス、6,000以上のAPIオペレーションを直接呼び出せる |

ユニバーサルターゲットを使えば、「毎晩20時に開発環境のRDSを停止する」のような処理を、Lambdaを書かずにRDSの `StopDBInstance` APIを直接呼ぶ形で作れます。サービス数・API数は[EventBridge スケジューラとは](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/what-is-scheduler.html)、テンプレート化されたターゲットの一覧は[テンプレート化されたターゲット](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/managing-targets-templated.html)の記載によるものです。

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
きっちりその時刻でなくてもいい処理もありますよね。
</SpeechBubble>

そういう処理には**柔軟な時間枠**（Flexible time windows）を設定します。たとえば1時間ごとのスケジュールに15分の時間枠を付けると、予定時刻から15分以内のどこかでターゲットを呼び出します。呼び出しが分散されるので、たくさんのスケジュールが同じ時刻に集中してターゲットに負荷がかかるのを避けられます（[柔軟な時間枠の設定](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/managing-schedule-flexible-time-windows.html)）。時刻どおりに動かしたいときは `Mode` を `OFF` にします。

### CLIで作るときのパラメーター

日本時間の毎日2時にLambdaを呼び出すスケジュールは、次のように作ります。

```bash
aws scheduler create-schedule \
  --name nightly-batch \
  --schedule-expression "cron(0 2 * * ? *)" \
  --schedule-expression-timezone "Asia/Tokyo" \
  --flexible-time-window '{"Mode": "OFF"}' \
  --target '{"RoleArn": "<実行ロールのARN>", "Arn": "<LambdaのARN>"}'
```

| パラメーター | 説明 |
|---|---|
| `--name` | スケジュールの名前 |
| `--schedule-expression` | `rate` / `cron` / `at` のいずれかの式 |
| `--schedule-expression-timezone` | タイムゾーン。省略すると式はUTC+0で評価される |
| `--flexible-time-window` | 柔軟な時間枠。`Mode` は `OFF` か `FLEXIBLE`（`FLEXIBLE` なら `MaximumWindowInMinutes` も指定） |
| `--target` | 呼び出すターゲットのARNと、Schedulerが引き受ける実行ロールのARN |

**戻り値**：作成したスケジュールのARN（`ScheduleArn`）

<SpeechBubble character="/images/fork_suit_man_color.png" name="先生" side="right">
「イベントに反応して動かす」ならEventBridgeのルール、「日時を決めて動かす」ならEventBridge Scheduler、と分けて覚えると整理しやすいです。これは公式がスケジュール用途にSchedulerを勧めていることをもとにした、筆者の整理です。
</SpeechBubble>

## 監視設計の全体像

実務では、これらの機能を組み合わせて監視を設計します。

```text
AWSリソース
  -> CloudWatch Metrics（数値を収集）
```

## 実務例: APIの遅延を検知して変更原因まで調べる

ALB、ECS、RDSで動くAPIを監視する場合、通知だけで終わらず、原因をたどれるデータをそろえます。

<MermaidDiagram
  chart={`
flowchart TB
    USERS["Users"] --> ALB["Application Load Balancer"]
    ALB --> ECS["ECS Service"]
    ECS --> RDS["Amazon RDS"]
    ALB --> METRICS["CloudWatch Metrics"]
    ECS --> LOGS["CloudWatch Logs"]
    ECS --> TRACE["X-Ray Traces"]
    METRICS --> ALARM["CloudWatch Alarm"]
    ALARM --> SNS["SNS Notification"]
    CHANGE["CloudTrail + AWS Config"] --> INVESTIGATE["Incident Investigation"]
    LOGS --> INVESTIGATE
    TRACE --> INVESTIGATE
    SNS --> INVESTIGATE
`}
/>

1. ALBのエラー率と応答時間、ECSのCPU・メモリ、RDSの接続数とレイテンシーを収集する
2. 利用者影響に近いALBの指標でAlarmを作り、SNSへ通知する
3. ECSのアプリケーションログをLogs Insightsで検索する
4. X-Ray Trace Mapから遅延しているサービスと下流呼び出しを特定する
5. 発生時刻付近のCloudTrailとAWS Configを確認し、デプロイや設定変更との関連を調べる
6. 復旧後にアラーム状態、エラー率、トレースのレイテンシーが戻ったことを確認する

この流れは各サービスの機能を障害調査へ対応させた、筆者の整理です。アラームのしきい値と評価期間は、通常時の実測値、サービスレベル目標、許容する検知時間から決めます。

## 試験問題での判断パターン

| 問題文の要件 | 選択の起点 | 判断理由 |
|---|---|---|
| EC2のメモリやディスク使用率を監視したい | CloudWatch Agent + カスタムメトリクス | EC2の標準メトリクスには含まれない |
| しきい値超過を通知したい | CloudWatch Alarm + SNS | メトリクスを評価し、状態変化で通知できる |
| メトリクスを使って台数を増減したい | CloudWatch Alarm / ターゲット追跡 + Auto Scaling | 負荷指標をスケーリングへ使える |
| 複数ログからエラーを一時的に調査したい | CloudWatch Logs Insights | ログを対話的に検索・集計できる |
| 誰がSecurity Groupを変更したか調べたい | CloudTrail | APIを呼び出した主体と操作を記録する |
| Security Groupが過去にどの設定だったか調べたい | AWS Config | リソース設定と関係の履歴を確認できる |
| 設定が組織の基準に準拠するか評価したい | AWS Config Rules | 設定をルールで評価できる |
| マイクロサービス間の遅延箇所を追いたい | AWS X-Ray / Application Signals | リクエスト経路と依存先をトレースできる |
| AWSリソースの状態変化に反応したい | EventBridge Rule | イベントパターンで選び、ターゲットを呼べる |
| 指定日時やcronで処理を実行したい | EventBridge Scheduler | タイムゾーン、1回限り、rate、cronを扱える |

この表は[SAA-C03試験ガイドのタスク2.2](https://docs.aws.amazon.com/ja_jp/aws-certification/latest/solutions-architect-associate-03/solutions-architect-associate-03-domain2.html)と各サービスの公式ドキュメントをもとにした、筆者の整理です。

<Callout type="note">
### 監視で混同しやすい点

- Alarmはメトリクスの状態を評価し、EventBridge Ruleはイベント内容に一致したときにターゲットを呼び出します
- CloudTrailは操作、AWS Configはリソース設定、CloudWatch Logsはアプリケーションやサービスのログを扱います
- Metricsだけでは個別リクエストの経路を追えないため、分散処理の原因調査にはTracesを組み合わせます
- 通知を増やすだけでは復旧は速くなりません。利用者影響、担当者、対応手順、エスカレーション先をアラームごとに決めます

</Callout>

## まとめ

CloudWatchとEventBridgeは、AWSの運用・監視の土台です。

- <Marker>**Metrics** — AWSリソースの数値を収集・可視化。メモリ監視にはカスタムメトリクスが必要</Marker>
- **Logs** — ログの収集・保存。サブスクリプションフィルターで他サービスへ転送可能
- **Logs Insights** — ログに対するSQLライクなクエリ分析。アドホックな調査に最適
- **Alarms** — しきい値と評価期間でメトリクスを判定し、通知や自動対応を実行
- **CloudTrail / AWS Config** — AWSの操作とリソース設定の変化を追跡
- **AWS X-Ray** — 分散したサービスを通るリクエストをトレース
- **EventBridge** — AWSリソースの状態変化に反応して自動アクションを実行
- **EventBridge Scheduler** — 日時を決めてターゲットを呼び出す。タイムゾーン指定・1回限り・再試行とDLQに対応し、スケジュール用途では公式の推奨

SQS、SNS、EventBridge、Step Functionsの使い分けは[疎結合アーキテクチャ](/books/aws-saa-c03/decoupled-architecture)で扱います。
