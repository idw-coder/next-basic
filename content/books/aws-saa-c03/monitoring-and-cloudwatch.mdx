## CloudWatch Metrics

CloudWatch Metricsは、AWSリソースの**数値データを時系列で収集・可視化**する機能です。EC2のCPU使用率、ELBのリクエスト数、RDSの接続数など、多くのAWSサービスが自動的にメトリクスを送信します。

### 標準メトリクスとカスタムメトリクス

| 種類 | 説明 | 例 |
|---|---|---|
| 標準メトリクス | AWSが自動で収集。追加費用なし | EC2: CPUUtilization、NetworkIn |
| カスタムメトリクス | ユーザーが独自に送信する | メモリ使用率、アプリのキュー長 |

<Callout type="warning">
### EC2のメモリ使用率は標準メトリクスに含まれない

EC2の標準メトリクスにはCPU使用率やネットワークは含まれますが、**メモリ使用率やディスク使用率は含まれません**。これらを監視するにはCloudWatch Agentをインストールしてカスタムメトリクスとして送信する必要があります。試験でもよく問われるポイントです。

</Callout>

### メトリクスの期間と保持

| 期間 | 保持期間 |
|---|---|
| 1秒（高解像度） | 3時間 |
| 60秒（標準） | 15日 |
| 5分 | 63日 |
| 1時間 | 15ヶ月 |

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
メトリクスを元に自動で何かさせたい場合はどうしますか？
</SpeechBubble>

それが **CloudWatch Alarms** の役割です。メトリクスがしきい値を超えたら、SNS通知を送ったり、Auto Scalingのスケールアウトをトリガーしたり、EC2インスタンスを停止・再起動したりできます。

## CloudWatch Logs

<Figure src="/images/search_woman_color.png" alt="ログを調査している人のイラスト" maxWidth="320px" />

CloudWatch Logsは、AWSリソースやアプリケーションの**ログを収集・保存・検索**するサービスです。

### ログの階層構造

<MermaidDiagram
  chart={`
flowchart LR
    LG["Log Group"] --> LS1["Log Stream 1"]
    LG --> LS2["Log Stream 2"]
    LG --> LS3["Log Stream 3"]
    LS1 --> E1["Log Event"]
    LS1 --> E2["Log Event"]
    LS1 --> E3["Log Event"]
`}
/>

| 用語 | 説明 |
|---|---|
| ロググループ（Log Group） | ログの保持期間やアクセス制御を共有するログストリームのまとまり。通常はサービスやアプリ単位で作成する |
| ログストリーム（Log Stream） | 時系列のログイベントの連続。通常はインスタンスやコンテナ単位で作成される |
| ログイベント（Log Event） | タイムスタンプとメッセージで構成される1件のログ |

### 主なログ送信元

| 送信元 | 方法 |
|---|---|
| EC2 | CloudWatch Agent をインストール |
| ECS / Fargate | `awslogs` ログドライバーを指定 |
| Lambda | 自動で `/aws/lambda/{関数名}` に送信 |
| API Gateway | ステージの設定で有効化 |
| VPC Flow Logs | VPC・Subnet・ENI単位で有効化 |
| Route 53 | DNSクエリログ |

<Callout type="note">
### ログの保持期間はデフォルト「無期限」

CloudWatch Logsのロググループは、デフォルトでログを無期限に保持します。長期運用ではログ量に応じたコストが増えるため、保持期間（1日〜10年）を設定するか、S3へエクスポートすることを検討します。

</Callout>

### サブスクリプションフィルター

ログをリアルタイムに別サービスへ転送する機能です。[データ取り込みと分析](/books/aws-saa-c03/data-ingestion-and-analytics)の章で扱ったECS → OpenSearchの構成でも使われます。

| 転送先 | 用途 |
|---|---|
| Kinesis Data Firehose | S3やOpenSearchへの配信 |
| Lambda | ログのリアルタイム加工・通知 |
| Kinesis Data Streams | ストリーム処理 |

## CloudWatch Logs Insights

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
CloudWatch Logsに貯まったログを分析したいとき、全部目で見るのは無理ですよね？
</SpeechBubble>

CloudWatch Logs Insightsは、ロググループに対して**SQLライクなクエリで検索・集計・可視化**できる機能です。大量のログから特定のパターンを抽出したり、エラーの傾向を集計したりできます。

### クエリの例

```text
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

上記のクエリは「ERRORを含むログを新しい順に20件取得する」という意味です。

<Figure src="/images/creative_color.png" alt="分析結果からインサイトを得る人のイラスト" maxWidth="320px" />

### Logs Insightsの特徴

| 特徴 | 説明 |
|---|---|
| スキャンベースの課金 | スキャンしたデータ量に応じた従量課金 |
| 複数ロググループの横断クエリ | 最大50のロググループを同時に検索できる |
| 自動フィールド検出 | JSON形式のログは自動でフィールドをパースする |
| 可視化 | クエリ結果を棒グラフや折れ線グラフで表示できる |

<Callout type="note">
### Logs InsightsとOpenSearchの使い分け

Logs Insightsはクエリごとのアドホック分析に向いています。常時稼働のダッシュボードや大規模な全文検索が必要な場合は、[OpenSearch Service](/books/aws-saa-c03/data-ingestion-and-analytics#amazon-opensearch-service) の方が適しています。

</Callout>

## Amazon EventBridge

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
EventBridgeはCloudWatchの一部なんですか？別のサービスですか？
</SpeechBubble>

Amazon EventBridgeは、もともと **CloudWatch Events** という名前でした。現在は独立したサービスとして進化していますが、機能的にはAWSリソースの**状態変化をイベントとして検知し、ルールに基づいてアクションを実行**するサービスです。

<Figure src="/images/meeting_color.png" alt="イベント駆動の連携を設計するイラスト" maxWidth="320px" />

### EventBridgeの仕組み

<MermaidDiagram
  chart={`
flowchart LR
    SRC["Event Source"] -->|"Event"| BUS["Event Bus"]
    BUS --> R1["Rule 1"]
    BUS --> R2["Rule 2"]
    R1 --> T1["Lambda"]
    R2 --> T2["SQS"]
    R2 --> T3["Step Functions"]
`}
/>

| 構成要素 | 説明 |
|---|---|
| イベントソース | AWSサービス、SaaSアプリ、カスタムアプリからイベントを発生させる |
| イベントバス | イベントを受け取るパイプライン。デフォルトバスの他にカスタムバスも作れる |
| ルール | イベントパターンまたはスケジュールに基づいてターゲットを呼び出す |
| ターゲット | Lambda、SQS、SNS、Step Functions、ECS Taskなど |

### よく使われるパターン

| ユースケース | イベントソース | ターゲット |
|---|---|---|
| EC2インスタンスが停止したら通知 | EC2 State Change | SNS |
| S3にファイルがアップロードされたら処理 | S3 PutObject | Lambda |
| 毎日深夜にバッチ処理を実行 | スケジュール（cron）。今は後述のEventBridge Schedulerが推奨 | Lambda / ECS Task |
| AWS Health イベントを検知して対応 | AWS Health | Lambda / SNS |

<SpeechBubble character="/images/fork_suit_man_color.png" name="先生" side="right">
EventBridgeは[疎結合アーキテクチャ](/books/aws-saa-c03/decoupled-architecture)の章でも扱っています。試験では「AWSサービスの状態変化に自動対応する」要件でEventBridgeが正解になります。
</SpeechBubble>

<Callout type="note">
### EventBridge vs SNS

どちらもイベントを配信しますが、EventBridgeは**イベントの内容でフィルタリング**できるのが強みです。SNSはシンプルなPub/Subで、EventBridgeはイベントパターンマッチングによる細かいルーティングが可能です。

</Callout>

## EventBridge Scheduler

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
上の表に「毎日深夜にバッチ処理を実行」がありました。決まった時刻に動かすのも、EventBridgeのルールで作るんですか？
</SpeechBubble>

ルールにスケジュールを設定するやり方（**スケジュールルール**）もありますが、AWSの公式ドキュメントは、スケジュールでターゲットを呼び出すなら **EventBridge Scheduler** を使うよう勧めています。スケジュールルールは「EventBridgeのレガシー機能」と書かれています（[スケジュールに従って実行するルールの作成](https://docs.aws.amazon.com/ja_jp/eventbridge/latest/userguide/eb-create-rule-schedule.html)）。

EventBridge Schedulerは、**スケジュールの作成・実行・管理だけを受け持つサーバーレスのサービス**です。イベントバスやルールは使わず、スケジュールそのものにターゲットを1つ設定します。

<Figure src="/images/calling_suit_man_color.png" alt="決まった時刻に処理を呼び出す人のイラスト" maxWidth="320px" />

### スケジュールルールとの違い

| 項目 | スケジュールルール | EventBridge Scheduler |
|---|---|---|
| 位置づけ | EventBridgeのレガシー機能 | スケジュール専用のサービス。公式の推奨 |
| スケジュールの種類 | `rate` / `cron` | `rate` / `cron` / 1回限り（`at`） |
| タイムゾーン | UTC+0 のみ | タイムゾーンを指定できる（例: `Asia/Tokyo`） |
| 作れる場所 | デフォルトのイベントバスだけ | スケジュールグループにまとめて管理 |

スケジュールルールでは、日本時間の深夜2時に動かしたければ、UTCに直して「前日の17時」と書く必要があります。EventBridge Schedulerならタイムゾーンを指定して、そのまま「2時」と書けます。タイムゾーンを指定したスケジュールは夏時間にも自動で合わせられます（[スケジュールの種類](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/schedule-types.html)）。

### スケジュール式の3種類

| 式 | 書き方 | 例 | 意味 |
|---|---|---|---|
| rate式 | `rate(値 単位)` | `rate(5 minutes)` | 5分ごとに実行 |
| cron式 | `cron(分 時 日 月 曜日 年)` | `cron(0 2 * * ? *)` | 毎日2時0分に実行 |
| at式（1回限り） | `at(yyyy-mm-ddThh:mm:ss)` | `at(2026-12-01T09:00:00)` | 指定した日時に1回だけ実行 |

cron式では、日と曜日の両方に `*` は書けません。片方に `*` を使ったら、もう片方は `?` にします。

<Callout type="warning">
### 1回限りのスケジュールは、実行後も残る

`at` 式で作ったスケジュールは、実行が終わっても自動では消えず、アカウントのスケジュール数の上限にも数えられます。公式は実行後に削除することを勧めており、作成時に `ActionAfterCompletion` を `DELETE` にしておくと、完了後に自動で削除されます（[EventBridge スケジューラのクォータ](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/scheduler-quotas.html)、[CreateSchedule API](https://docs.aws.amazon.com/scheduler/latest/APIReference/API_CreateSchedule.html)）。

</Callout>

### 仕組み — 実行ロールとDLQ

<MermaidDiagram
  chart={`
flowchart LR
    ROLE["実行ロール"] --- SCH["EventBridge Scheduler"]
    SCH -->|"cron / rate / at"| T["ターゲット"]
    SCH -->|"再試行を使い切った"| DLQ["SQS DLQ"]
`}
/>

時刻が来ると、EventBridge Schedulerは次の順で動きます。

1. スケジュールに設定された**実行ロール**（IAMロール）を引き受ける
2. そのロールの権限でターゲットを呼び出す
3. 呼び出しに失敗したら、設定した再試行回数と最大保持時間の範囲で再試行する
4. それでも届かなかったイベントは、設定していれば**DLQ**（SQSの標準キュー）に送る

<Marker>ターゲットを呼び出す権限は、実行ロールにアタッチしたポリシーで与えます。</Marker>ロールの信頼ポリシーで、EventBridge Schedulerがそのロールを引き受けられるようにしておく必要があります（[EventBridge スケジューラのセットアップ](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/setting-up.html)）。DLQにはFIFOキューは使えません（[デッドレターキューの設定](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/configuring-schedule-dlq.html)）。

### 呼び出せるターゲット

| 種類 | 内容 |
|---|---|
| テンプレート化されたターゲット | Lambda、SQS、SNS、Step Functions、ECS（RunTask）、EventBridge（イベントバス）など12サービスの代表的な操作を、ARNを指定するだけで呼び出せる |
| ユニバーサルターゲット | 270以上のAWSサービス、6,000以上のAPIオペレーションを直接呼び出せる |

ユニバーサルターゲットを使えば、「毎晩20時に開発環境のRDSを停止する」のような処理を、Lambdaを書かずにRDSの `StopDBInstance` APIを直接呼ぶ形で作れます。サービス数・API数は[EventBridge スケジューラとは](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/what-is-scheduler.html)、テンプレート化されたターゲットの一覧は[テンプレート化されたターゲット](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/managing-targets-templated.html)の記載によるものです。

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
きっちりその時刻でなくてもいい処理もありますよね。
</SpeechBubble>

そういう処理には**柔軟な時間枠**（Flexible time windows）を設定します。たとえば1時間ごとのスケジュールに15分の時間枠を付けると、予定時刻から15分以内のどこかでターゲットを呼び出します。呼び出しが分散されるので、たくさんのスケジュールが同じ時刻に集中してターゲットに負荷がかかるのを避けられます（[柔軟な時間枠の設定](https://docs.aws.amazon.com/ja_jp/scheduler/latest/UserGuide/managing-schedule-flexible-time-windows.html)）。時刻どおりに動かしたいときは `Mode` を `OFF` にします。

### CLIで作るときのパラメーター

日本時間の毎日2時にLambdaを呼び出すスケジュールは、次のように作ります。

```bash
aws scheduler create-schedule \
  --name nightly-batch \
  --schedule-expression "cron(0 2 * * ? *)" \
  --schedule-expression-timezone "Asia/Tokyo" \
  --flexible-time-window '{"Mode": "OFF"}' \
  --target '{"RoleArn": "<実行ロールのARN>", "Arn": "<LambdaのARN>"}'
```

| パラメーター | 説明 |
|---|---|
| `--name` | スケジュールの名前 |
| `--schedule-expression` | `rate` / `cron` / `at` のいずれかの式 |
| `--schedule-expression-timezone` | タイムゾーン。省略すると式はUTC+0で評価される |
| `--flexible-time-window` | 柔軟な時間枠。`Mode` は `OFF` か `FLEXIBLE`（`FLEXIBLE` なら `MaximumWindowInMinutes` も指定） |
| `--target` | 呼び出すターゲットのARNと、Schedulerが引き受ける実行ロールのARN |

**戻り値：** 作成したスケジュールのARN（`ScheduleArn`）

<SpeechBubble character="/images/fork_suit_man_color.png" name="先生" side="right">
「イベントに反応して動かす」ならEventBridgeのルール、「日時を決めて動かす」ならEventBridge Scheduler、と分けて覚えると整理しやすいです。これは公式がスケジュール用途にSchedulerを勧めていることをもとにした、筆者の整理です。
</SpeechBubble>

## 監視設計の全体像

実務では、これらの機能を組み合わせて監視を設計します。

```text
AWSリソース
  -> CloudWatch Metrics（数値を収集）
  -> CloudWatch Alarms（しきい値で検知）
  -> SNS / Auto Scaling（通知・自動対応）

アプリケーション / AWSサービス
  -> CloudWatch Logs（ログを収集）
  -> Logs Insights（アドホック分析）
  -> サブスクリプションフィルター -> OpenSearch（常時ダッシュボード）

AWSリソースの状態変化
  -> EventBridge（イベント検知）
  -> Lambda / SQS / Step Functions（自動処理）
```

<SpeechBubble character="/images/usingcomputer_suit_woman_color.png" name="学習者">
試験ではどのように問われますか？
</SpeechBubble>

SAA-C03では「メモリ使用率を監視したい → カスタムメトリクス + CloudWatch Agent」「ログを横断分析したい → Logs Insights or OpenSearch」「AWSリソースの変化に自動対応したい → EventBridge」のように、**要件からどの機能を選ぶか**が問われます。

## まとめ

CloudWatchとEventBridgeは、AWSの運用・監視の土台です。

- <Marker>**Metrics** — AWSリソースの数値を収集・可視化。メモリ監視にはカスタムメトリクスが必要</Marker>
- **Logs** — ログの収集・保存。サブスクリプションフィルターで他サービスへ転送可能
- **Logs Insights** — ログに対するSQLライクなクエリ分析。アドホックな調査に最適
- **EventBridge** — AWSリソースの状態変化に反応して自動アクションを実行
- **EventBridge Scheduler** — 日時を決めてターゲットを呼び出す。タイムゾーン指定・1回限り・再試行とDLQに対応し、スケジュール用途では公式の推奨
