Multi-AZにしていれば、災害対策もできていると考えていいですか？
</SpeechBubble>

高可用性はAZ障害などに備える設計ですが、**災害対策**（Disaster Recovery、DR）はリージョン障害や大規模障害からどう復旧するかを考える設計です。

[SAA-C03試験ガイドのタスク2.2](https://docs.aws.amazon.com/ja_jp/aws-certification/latest/solutions-architect-associate-03/solutions-architect-associate-03-domain2.html)では、RTOとRPO、バックアップ、データレプリケーション、復旧方式、マルチリージョン構成を要件に合わせて選ぶ力が対象です。

<Marker>Multi-AZは同一リージョン内の可用性を高めます。リージョン規模の障害へ備えるには、別リージョンに何を複製し、どの順序で復旧するかを別に設計します。</Marker>

## RTOとRPO

| 指標 | 意味 | 確認する問い |
|---|---|---|
| RTO | 障害発生からサービス復旧までに許容できる時間 | 何分・何時間以内に業務を再開するか |
| RPO | 復旧時点からさかのぼって許容できるデータ損失の時間 | 何分・何時間前までのデータへ戻ってよいか |

RTOとRPOは、技術方式を決める前に業務側と合意します。AWSのDRホワイトペーパーでは、RTOとRPOを災害発生後のダウンタイムとデータ損失に関する目標として定義しています。詳細はAWS公式の[DR目標](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-dr-objectives.html)で確認できます。

RTOとRPOを短くするほど、別リージョンで常時稼働させるリソース、継続的なレプリケーション、自動化、試験が増えます。すべての機能を同じ値にせず、決済、参照画面、分析バッチなど業務ごとに目標を分けます。

<Callout type="warning">
### バックアップ間隔だけでRPOを保証しない

1時間ごとにバックアップしても、取得失敗や別リージョンへのコピー遅延があれば1時間のRPOを満たせません。復旧ポイントの作成時刻とコピー完了時刻を監視し、復元試験で実測します。

</Callout>

## DR戦略

| 戦略 | コスト | 復旧速度 | 概要 |
|---|---:|---:|---|
| Backup and Restore | 低 | 遅い | バックアップから復元 |
| Pilot Light | 中 | 中 | 最小構成だけ別リージョンに用意 |
| Warm Standby | 高 | 速い | 縮小版の本番環境を常時稼働 |
| Multi-Site Active/Active | 最高 | 最速 | 複数リージョンで常時稼働 |

この比較は、AWS公式の[クラウドにおけるDRオプション](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html)をもとにした定性的な整理です。必要以上にActive/Activeを選ぶと、RTOとRPOを満たしても費用と運用負荷が増えます。

### Backup and Restore

通常時は別リージョンへバックアップを保管し、災害時にデータとアプリケーションを復元します。別リージョンの常時稼働リソースを抑えられる一方、復元、再構築、検証に時間が必要です。

<MermaidDiagram
  chart={`
flowchart TB
    PRIMARY["Primary Region<br/>Application + Data"] --> BACKUP["Backup / Snapshot"]
    BACKUP --> VAULT["DR Region<br/>Backup Vault / S3"]
    VAULT -->|"災害時に復元"| RESTORE["Restored Data"]
    IAC["Infrastructure as Code"] --> APP["Rebuilt Application"]
    RESTORE --> APP
`}
/>

AWS公式の[Backup and Restore](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/backup-and-restore.html)では、データのバックアップに加えて、Infrastructure as Codeでインフラストラクチャを再構築する構成を示しています。

### Pilot Light

別リージョンでは、データベースやデータ複製などシステムの中核だけを常時稼働させます。災害時にアプリケーション層をデプロイまたはスケールアウトし、通信を切り替えます。

<MermaidDiagram
  chart={`
flowchart TB
    PRIMARY["Primary Region<br/>Full Stack"] -->|"Data Replication"| CORE["DR Region<br/>Core Data Services"]
    TEMPLATE["Infrastructure as Code"] -->|"災害時に起動"| COMPUTE["Application / Compute"]
    CORE --> COMPUTE
    COMPUTE --> ROUTE["Route 53<br/>Failover"]
`}
/>

Pilot Lightの構成と復旧手順はAWS公式の[Pilot Light](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/pilot-light.html)で確認できます。

### Warm Standby

別リージョンで、機能する縮小版の本番環境を常時稼働させます。災害時は待機系を本番容量へスケールし、通信を切り替えます。Pilot Lightより常時費用は増えますが、アプリケーション層を一から起動する時間を短縮できます。

<MermaidDiagram
  chart={`
flowchart TB
    USERS["Users"] --> ROUTE["Route 53"]
    ROUTE --> PRIMARY["Primary Region<br/>Full Capacity"]
    PRIMARY -->|"Data Replication"| STANDBY["DR Region<br/>Reduced Capacity"]
    ROUTE -.->|"災害時に切り替え"| STANDBY
    STANDBY -->|"Scale Out"| RECOVERY["Production Capacity"]
`}
/>

縮小版を常時稼働させる考え方はAWS公式の[Warm Standby](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/warm-standby.html)で確認できます。

### Multi-Site Active/Active

複数リージョンでアプリケーションを常時稼働させ、両方へ通信を送ります。一方のリージョンが停止しても、正常なリージョンが処理を継続します。最短のRTOを目指せますが、データの整合性、競合、リージョン間の依存、容量、デプロイ順序を管理する必要があります。

<MermaidDiagram
  chart={`
flowchart TB
    USERS["Users"] --> ENTRY["Route 53 / Global Accelerator"]
    ENTRY --> REGION_A["Region A<br/>Active Application"]
    ENTRY --> REGION_B["Region B<br/>Active Application"]
    REGION_A --> DATA_A["Regional Data Store"]
    REGION_B --> DATA_B["Regional Data Store"]
    DATA_A <-->|"Multi-Region Replication"| DATA_B
`}
/>

AWS公式の[Multi-Site Active/Active](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/disaster-recovery-workloads-on-aws/multi-site-active-active.html)では、複数リージョンから利用者へサービスを提供する構成と復旧上の考慮事項を説明しています。

## 代表サービス

| 要件 | サービス・機能 |
|---|---|
| EC2ワークロードのDR | AWS Elastic Disaster Recovery |
| 複数サービスのバックアップ管理 | AWS Backup |
| S3のリージョン間複製 | S3 Cross-Region Replication |
| RDSの復旧 | Snapshot、Automated Backup、Read Replica |
| DNSフェイルオーバー | Route 53 Failover Routing |
| グローバルな入口 | CloudFront、Global Accelerator |

### バックアップと継続レプリケーションを使い分ける

AWS Backupは、対応するAWSサービスのバックアップスケジュール、保持、バックアップボールト、別リージョンや別アカウントへのコピーを一元管理します。S3 Cross-Region Replicationは、S3オブジェクトを別リージョンのバケットへ継続的に複製します。

バックアップは過去の復旧ポイントへ戻す用途、レプリケーションは別拠点へデータを追従させる用途が中心です。誤更新や論理破損が複製先へ伝わる可能性を考え、両方を同じものとして扱いません。AWS BackupとS3 Replicationの保護・保持設定は[データ保護](/books/aws-saa-c03/data-security)で詳しく扱います。

AWS Backupの仕組みはAWS公式の[バックアッププラン](https://docs.aws.amazon.com/ja_jp/aws-backup/latest/devguide/about-backup-plans.html)、S3の複製要件は[オブジェクトのレプリケーション](https://docs.aws.amazon.com/ja_jp/AmazonS3/latest/userguide/replication.html)で確認できます。

### RDSの復旧ポイントを選ぶ

RDSの自動バックアップを有効にすると、保持期間内の指定時点へDBインスタンスを復元できます。ポイントインタイムリカバリは既存DBを巻き戻すのではなく、新しいDBインスタンスを作成します。復元後にパラメータ、セキュリティグループ、アプリケーションの接続先を確認します。

手動スナップショットは明示的な復旧点を残す場合に使います。自動バックアップ、スナップショット、Read Replicaは保持方法と目的が異なるため、RPO、RTO、リージョン障害への要件から選びます。RDSの復元動作はAWS公式の[指定した時点へのDBインスタンスの復元](https://docs.aws.amazon.com/ja_jp/AmazonRDS/latest/UserGuide/USER_PIT.html)で確認できます。

### AWS Elastic Disaster Recoveryでサーバーを復旧する

**AWS Elastic Disaster Recovery**（AWS DRS）は、ソースサーバーのブロックストレージをAWS上のステージング領域へ継続的にレプリケートし、復旧時にAWS上のインスタンスとして起動するサービスです。オンプレミスや他クラウドを含むサーバーワークロードをAWSへ復旧する場合の候補になります。

通常時は低コストのステージングリソースを使い、復旧訓練と本番切り替えでは起動設定に基づいて復旧用インスタンスを作成します。対応するOS、ネットワーク、ライセンス、復旧後の依存関係を事前に検証します。仕組みはAWS公式の[AWS Elastic Disaster Recoveryとは](https://docs.aws.amazon.com/ja_jp/drs/latest/userguide/what-is-drs.html)で確認できます。

### Route 53で復旧先へ通信を切り替える

Route 53のフェイルオーバールーティングでは、プライマリとセカンダリのレコードを作り、ヘルスチェック結果に基づいて応答先を切り替えます。DNSレスポンスはクライアントやリゾルバーにキャッシュされるため、切り替え後の再接続とTTLを含めてRTOを評価します。

Route 53のヘルスチェックとフェイルオーバーの動作はAWS公式の[DNSフェイルオーバーの設定](https://docs.aws.amazon.com/ja_jp/Route53/latest/DeveloperGuide/dns-failover.html)で確認できます。

<Callout type="note">
### DRは復旧演習まで含めて設計

バックアップやレプリケーションを設定していても、実際に切り替えられなければDRにはなりません。実務では復旧手順、権限、DNS切り替え、データ整合性、定期訓練まで設計します。

</Callout>

## マルチリージョンのデータ層

アプリケーションを別リージョンで起動できても、必要なデータへアクセスできなければ復旧は完了しません。データベースごとのレプリケーション方式、書き込み先、整合性、昇格手順を決めます。

### Aurora Global Database

Aurora Global Databaseは、1つのプライマリリージョンと複数のセカンダリリージョンにまたがるAuroraクラスターを構成します。通常はプライマリリージョンで書き込み、セカンダリリージョンを読み取りや災害復旧に使います。

<MermaidDiagram
  chart={`
flowchart TB
    APP_A["Application<br/>Primary Region"] --> WRITER["Aurora Writer"]
    WRITER --> CLUSTER_A["Primary Aurora Cluster"]
    CLUSTER_A -->|"Cross-Region Replication"| CLUSTER_B["Secondary Aurora Cluster"]
    APP_B["Application<br/>DR Region"] --> CLUSTER_B
    CONTROL["Switchover / Failover"] --> CLUSTER_B
`}
/>

計画作業では管理されたスイッチオーバー、障害時にはフェイルオーバーを使います。切り替え後はアプリケーションの書き込み先と接続先を確認します。構成と切り替え方式はAWS公式の[Amazon Aurora Global Database](https://docs.aws.amazon.com/ja_jp/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html)で確認できます。

### DynamoDB Global Tables

DynamoDB Global Tablesは、選択した複数リージョンへDynamoDBテーブルのレプリカを配置するマルチリージョン機能です。各リージョンのアプリケーションが近いレプリカを利用でき、1つのリージョンが分離しても別リージョンで処理を継続する設計に使えます。

<MermaidDiagram
  chart={`
flowchart TB
    USERS["Global Users"] --> ROUTING["Application Routing"]
    ROUTING --> APP_A["Application<br/>Region A"]
    ROUTING --> APP_B["Application<br/>Region B"]
    APP_A --> TABLE_A["DynamoDB Replica<br/>Region A"]
    APP_B --> TABLE_B["DynamoDB Replica<br/>Region B"]
    TABLE_A <-->|"Global Tables Replication"| TABLE_B
`}
/>

Global Tablesを選ぶときは、利用可能な整合性モードとリージョン、同じ項目への同時書き込み、アプリケーションの再試行を確認します。機能と構成条件はAWS公式の[DynamoDB Global Tables](https://docs.aws.amazon.com/ja_jp/amazondynamodb/latest/developerguide/GlobalTables.html)で確認できます。

| 要件 | Aurora Global Database | DynamoDB Global Tables |
|---|---|---|
| データモデル | リレーショナル | キーバリュー・ドキュメント |
| 通常の書き込み構成 | プライマリリージョンのWriter | 複数リージョンのレプリカを利用可能 |
| 主な判断軸 | SQL、トランザクション、昇格手順 | アクセスパターン、整合性、競合 |

この比較は、DR方式を絞るための筆者の整理です。データモデルを変えてまでDR機能だけを採用せず、アプリケーション要件と運用手順を含めて選びます。

## 実務での構成例 — ECサイトを別リージョンへ復旧する

通常は東京リージョンで稼働し、重大障害時に別リージョンへ切り替えるECサイトを考えます。業務側が注文機能と商品閲覧機能に異なるRTO・RPOを定め、注文データを優先して復旧します。

<MermaidDiagram
  chart={`
flowchart TB
    USERS["Users"] --> R53["Route 53<br/>Failover Routing"]
    R53 --> PRIMARY["Primary Region<br/>ALB + Application"]
    R53 -.-> STANDBY["DR Region<br/>Warm Standby"]
    PRIMARY --> DATA_A["Primary Database"]
    DATA_A -->|"Cross-Region Replication"| DATA_B["DR Database"]
    BACKUP["AWS Backup"] --> VAULT["Cross-Region Backup Copy"]
    IAC["Infrastructure as Code"] --> STANDBY
    DATA_B --> STANDBY
`}
/>

設計と復旧手順では次を確認します。

1. 注文、在庫、商品画像などデータごとにRPOを決める
2. DRリージョンのネットワーク、IAMロール、KMSキー、証明書を準備する
3. Infrastructure as Codeから同じ構成を再作成できるようにする
4. データ複製の遅延とバックアップコピーの完了を監視する
5. 待機系を必要容量へ拡張してからRoute 53で通信を切り替える
6. 決済、通知、外部APIなどリージョン外の依存先も疎通確認する
7. 復旧後のデータ整合性を確認し、元リージョンへ戻すフェイルバック手順を用意する

## 試験問題での判断パターン

| 問題文の要件 | 第一候補 | 判断理由 |
|---|---|---|
| 最低コストで別リージョンへ復旧できればよく、復旧に時間を取れる | Backup and Restore | 待機系の常時稼働を抑えられる |
| データ層だけ常時維持し、障害時にアプリケーションを起動する | Pilot Light | 中核データを維持しながら通常時の計算資源を抑えられる |
| 縮小版のシステムを常時稼働し、短時間で容量を増やす | Warm Standby | 起動済みの全機能を拡張して切り替えられる |
| 複数リージョンで常時リクエストを処理し、最短のRTOを求める | Multi-Site Active/Active | 正常なリージョンが継続処理できる |
| Auroraを別リージョンへ複製し、障害時にDBを昇格する | Aurora Global Database | セカンダリクラスターをDR先にできる |
| DynamoDBを複数リージョンから利用する | DynamoDB Global Tables | リージョンごとにレプリカを配置できる |
| オンプレミスのサーバー群をAWSへ継続複製して復旧する | AWS Elastic Disaster Recovery | ブロックレベルで複製しAWS上で復旧できる |
| 複数サービスの復旧ポイントを別リージョンへ保管する | AWS Backup | バックアッププランとコピーを一元管理できる |

この表は、要件から第一候補を絞るための筆者の整理です。実際の選択ではRTO、RPO、依存関係、データ整合性、リージョンごとのサービス提供状況、費用を確認します。

## よくあるハマりどころ

### Multi-AZだけでリージョン障害にも対応できると思う

Multi-AZは同一リージョン内のAZ障害へ備える構成です。リージョン障害を要件に含める場合は、別リージョンへのデータ配置、アプリケーション起動、通信切り替えを設計します。

### レプリケーションをバックアップの代わりにする

論理破損や意図しない更新が複製先へ伝わる可能性があります。過去の復旧ポイントへ戻すバックアップと、別リージョンへ追従させるレプリケーションを要件に応じて組み合わせます。

### DRリージョンのクォータと鍵を確認しない

バックアップがあっても、復旧先のサービスクォータ、KMSキー、IAM権限、証明書、ネットワークが準備できていなければRTO内に復旧できません。復旧訓練ではデータ以外の依存要素も確認します。

### 切り替えだけを試してフェイルバックを試さない

元リージョンの復旧後に、どちらのデータを正として同期し直すかを決めます。切り戻し中の二重書き込みを防ぎ、フェイルバックまでを手順化します。

## まとめ

DR設計では、RTO/RPOに応じてコストと復旧速度のバランスを取ります。

- <Marker>RTOは復旧時間、RPOは許容データ損失</Marker>
- Backup and Restoreは低コストだが復旧に時間がかかる
- Warm StandbyやActive/Activeは速いが高コスト
- Aurora Global DatabaseやDynamoDB Global Tablesでデータを別リージョンへ配置する
- Route 53、S3 Replication、AWS Backup、Elastic Disaster Recoveryを使い分ける

S3、EBS、EFS、FSxの性能要件による使い分けは、[ストレージ選択](/books/aws-saa-c03/storage-selection)で扱います。
