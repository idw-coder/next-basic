フロントエンドとバックエンドをつなぐAPIは、チーム開発において最も重要なインターフェースです。
API設計が雑だと、フロントエンド側が個別対応に追われ、バックエンド側も一貫性のないコードになります。

この章では、RESTfulなAPI設計のルールと、実務で迷いやすいポイントを整理します。

## RESTの基本原則

REST（Representational State Transfer）は「リソース」を中心に考える設計スタイルです。

| 原則                     | 説明                                                                   |
| ------------------------ | ---------------------------------------------------------------------- |
| リソース指向             | URLはリソース（名詞）を表し、動詞は使わない                            |
| HTTPメソッドで操作を表現 | GET=取得, POST=作成, PUT/PATCH=更新, DELETE=削除                       |
| ステートレス             | リクエスト単体で処理が完結する（サーバーにセッション状態を持たせない） |

```
⭕ /api/users/123        — ユーザーというリソース
❌ /api/getUser?id=123   — 動詞が入っている
❌ /api/deleteUser/123   — 操作がURLに含まれている
```

## HTTPメソッドの使い分け

| メソッド | 操作     | べき等性 | 例                         |
| -------- | -------- | -------- | -------------------------- |
| GET      | 取得     | あり     | `GET /api/products`        |
| POST     | 作成     | なし     | `POST /api/products`       |
| PUT      | 全体更新 | あり     | `PUT /api/products/123`    |
| PATCH    | 部分更新 | 書き方次第 | `PATCH /api/products/123`  |
| DELETE   | 削除     | あり     | `DELETE /api/products/123` |

`PATCH` のべき等性は、書き方によって変わります。[RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html)は、`PATCH` はべき等ではないとしたうえで、べき等になるように発行することもできると説明しています。

```json
// べき等: 何回送っても name は同じ値になる
{ "name": "田中" }

// べき等ではない: 送るたびに在庫数が変わる
{ "op": "increment", "field": "stock", "value": 1 }
```

## レスポンス形式の統一

エンドポイントごとにレスポンスの形が違うと、フロントエンドは取得処理をエンドポイントの数だけ書くことになります。形を揃える方法としてよく使われるのが、**エンベロープパターン**です。

エンベロープパターンは、本体のデータを `data` などのキーの下に入れ、一覧の件数のような付加情報を別のキーに分ける形式です。

```json
{
  "data": [
    { "id": 1, "title": "API設計の基本" },
    { "id": 2, "title": "URL設計とルーティング" }
  ],
  "meta": {
    "page": 1,
    "perPage": 20,
    "total": 48
  }
}
```

配列をそのまま返す形と比べます。

| 形式 | 例 | あとから付加情報を足すとき |
|---|---|---|
| 配列をそのまま返す | `[{ "id": 1 }]` | 配列にはキーを足せないので、レスポンスの形を変えることになり、既存の利用者が動かなくなる |
| エンベロープ | `{ "data": [{ "id": 1 }] }` | `meta` などのキーを足すだけで、既存の利用者はそのまま動く |

実装前に次の項目を決めて、設計書に書いておきます。項目の選び方は筆者の整理です。

| 決めること | 例 |
|---|---|
| 成功時の形 | 本体は `data`、付加情報は `meta` |
| 失敗時の形 | `error` の下に `code` と `message` |
| キーの命名規則 | `createdAt`（キャメルケース）か `created_at`（スネークケース）のどちらかに統一 |
| 日時の形式 | `2026-03-01T09:00:00Z` のようなISO 8601形式 |
| 値がないときの表現 | キーを省略するか `null` を返すか |

レスポンスに `"success": true` を入れる例も見かけますが、成否はステータスコードで判定できるので、この本では入れません。

## ステータスコードの選び方

APIを利用する開発者がエラーハンドリングを正しく実装するには、ステータスコードが一貫したルールで返されている必要があります。

| ステータスコード          | 意味                   | 使いどころ               |
| ------------------------- | ---------------------- | ------------------------ |
| 200 OK                    | 成功（データ返却あり） | GET、PATCH成功時         |
| 201 Created               | リソース作成成功       | POST成功時               |
| 204 No Content            | 成功（データ返却なし） | DELETE成功時             |
| 400 Bad Request           | リクエストの形式が不正 | バリデーションエラー     |
| 401 Unauthorized          | 認証が必要             | トークン未指定・期限切れ |
| 403 Forbidden             | 権限がない             | ロール不足               |
| 404 Not Found             | リソースが存在しない   | 存在しないID指定         |
| 409 Conflict              | 競合が発生             | 重複登録、在庫不足、楽観ロック衝突 |
| 422 Unprocessable Content | 形式は正しいが処理不能 | ビジネスルール違反       |
| 500 Internal Server Error | サーバー内部エラー     | 予期しない例外           |

エラーの場合は、次の順番で判定すると選びやすくなります。

<Figure

  maxHeight="none"

/>

迷いやすい箇所は、[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)で次のように定義されています。

- **401と403:** `401` は有効な認証情報がないことを示し、`WWW-Authenticate` ヘッダーを付けて返す必要があります。`403` は、サーバーがリクエストを理解したうえで実行を拒否したことを示します
- **403と404:** アクセスできないリソースの存在を隠したいときは、`403` の代わりに `404` を返してもよいとされています
- **409:** リソースの現在の状態と競合して完了できないときに使います。利用者が競合を解消して再送できる場面が想定されています
- **400と422:** `400` はリクエスト構文の誤りなど、クライアント側のエラーを示します。`422` は、構文は正しいものの、指示された内容を処理できないことを示します

実際に `400` と `422` のどちらをバリデーションエラーに使うかは、APIによって違います。この本では、形式の誤りは `400`、形式は正しくても業務ルールに反するものは `422` に揃えます。

エラーレスポンスの形式もプロジェクト全体で統一しておくと、フロントエンド側が共通のエラーハンドリングを組めます。

```json
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "指定されたIDのユーザーが存在しません",
    "details": []
  }
}
```

標準の形式としては、[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)のProblem Details（`application/problem+json`）もあります。`code` の決め方や `details` の中身は、[エラー設計](/books/system-design/10-error-handling-design)と[バリデーション設計](/books/system-design/11-validation-design)で扱います。HTTPステータスコード自体の意味は、[HTTPステータスコード一覧](/books/http-and-web-api/03-status-codes)で確認できます。

## ページネーション設計

一覧APIは、全件を一度に返さず、分割して返します。方式は主に2つあります。

- **オフセット方式**: 先頭から何行飛ばすかを指定する。`GET /api/articles?page=2&perPage=3`
- **カーソル方式**: 前のページの最後の行を基準に、その続きを取得する。`GET /api/articles?limit=3&cursor=eyJpZCI6OH0`

### SQLの違い

新着順に1ページ3件を返すとき、2ページ目のSQLは次のように変わります。

```sql
-- オフセット方式: 先頭から3行飛ばして3行取得する
SELECT id, title FROM articles
ORDER BY id DESC
LIMIT 3 OFFSET 3;

-- カーソル方式: 前のページの最後の id(8) より小さい行を3行取得する
SELECT id, title FROM articles
WHERE id < 8
ORDER BY id DESC
LIMIT 3;
```

### オフセット方式の2つの問題

オフセット方式には、[Use The Index, Luke!](https://use-the-index-luke.com/sql/partial-results/fetch-next-page)でも説明されている問題が2つあります。

1. **後ろのページほど遅くなる。** データベースは、飛ばす行も先頭から数える必要があります
2. **行が増えるとページがずれる。** 位置の数え方が毎回先頭からになるためです

2つ目を図で確認します。

<Figure

  caption="図1: オフセット方式は位置で数えるのでずれる。カーソル方式は値で続きを探すのでずれない"
  maxHeight="none"
  maxWidth="720px"
/>

順番に見ていきます。

1. 1ページ目で `id` が 10、9、8 の行を表示します
2. 次のページを開く前に、`id` が 11 の行が追加されます
3. オフセット方式は 11、10、9 を飛ばすので、8、7、6 を返します。`id` 8 が2回表示されます
4. カーソル方式は `id < 8` の行を探すので、7、6、5 を返します

### カーソル方式のレスポンス

カーソル方式では、次のページを取得するための値をレスポンスに含めます。

```json
{
  "data": [
    { "id": 10, "title": "..." },
    { "id": 9, "title": "..." },
    { "id": 8, "title": "..." }
  ],
  "meta": {
    "nextCursor": "eyJpZCI6OH0"
  }
}
```

この `eyJpZCI6OH0` は、`{"id":8}` をBase64URLでエンコードした文字列です。クライアントには中身を解釈させず、受け取った値をそのまま次のリクエストの `cursor` に渡してもらいます。こうしておくと、基準にする列をあとから変えてもクライアントを修正せずに済みます。最後のページでは `nextCursor` を `null` にします。

### カーソル方式の注意点

- **並び順を一意にする。** `created_at` だけで並べると、同じ日時の行でページの境界が定まりません。`ORDER BY created_at DESC, id DESC` のように一意な列を加えます
- **複数列の比較に対応しているか確認する。** `WHERE (created_at, id) < (?, ?)` の行値構文は、データベースによって対応状況が違います
- **任意のページへ直接移動できない。** 「5ページ目へ」のような操作には向きません

### どちらを選ぶか

| 比較項目 | オフセット方式 | カーソル方式 |
|---|---|---|
| ページ番号で移動 | できる | できない |
| 後ろのページの速度 | 遅くなる | インデックスがあれば、ページの位置による差が小さい |
| 読み取り中の行の追加 | 重複や抜けが起きる | 基準の値の続きを読むので起きにくい |
| 実装 | 単純 | カーソルの生成と並び順の設計が必要 |

筆者の判断基準は次のとおりです。

- ページ番号が必要な管理画面で、件数も多くないなら、オフセット方式
- 無限スクロールや、行が頻繁に増える一覧、件数が多い一覧なら、カーソル方式

どちらの方式でも、1回に取得できる件数の上限をサーバー側で決めておきます。[GitHub REST API](https://docs.github.com/ja/rest/using-the-rest-api/using-pagination-in-the-rest-api)では、多くのエンドポイントで `per_page` の上限が100で、超える値を指定すると100に減らされます。

## バージョニング戦略

APIを変更すると、既存の利用者が動かなくなることがあります。利用者を止めずに変更するための仕組みがバージョニングです。

まず、バージョンを上げる必要がある変更かどうかを分けます。[GitHub REST API](https://docs.github.com/ja/rest/about-the-rest-api/api-versions)は次のように分類しています。

| 分類 | 変更の例 |
|---|---|
| 破壊的変更（新しいバージョンで出す） | 操作の削除、パラメータやレスポンスのフィールドの削除・名前変更、必須パラメータの追加 |
| 追加的な変更（既存のバージョンにも出す） | 操作の追加、省略可能なパラメータの追加 |

バージョンの指定方法は、主に2つあります。

```http
# URLに入れる
GET /api/v1/users/42

# ヘッダーで指定する（GitHub REST APIの方式）
GET /users/42
X-GitHub-Api-Version: 2026-03-10
```

| 比較項目 | URL | ヘッダー |
|---|---|---|
| バージョンの見え方 | URLだけで分かる | ヘッダーを見ないと分からない |
| ブラウザやcurlでの確認 | URLを開くだけ | ヘッダーの指定が必要 |
| リソースのURL | バージョンごとに別のURLになる | バージョンが変わってもURLは同じ |
| 指定がないときの動作 | URLにバージョンがあるので起きない | 既定のバージョンを決めておく必要がある |

- 新しいバージョンのリリース後、以前のバージョンを少なくとも24か月サポートする
- 廃止が近づくと、`Deprecation` と `Sunset` ヘッダーで日付を通知する
- サポートが終わったバージョンを指定すると、`410 Gone` を返す

## APIリファレンスの書き方

APIリファレンスは「開発者がAPIを使うときに最初に見るドキュメント」です。
書き方が悪いと、利用者はソースコードを読むか、試行錯誤するしかなくなります。

### リソースとは

REST APIにおける**リソース**とは、APIが扱うデータの単位です。
たとえばECサイトなら「ユーザー」「商品」「注文」「カート」がリソースにあたります。

各リソースには対応する**エンドポイント**（URL）があり、HTTPメソッドで操作を表現します。

```
リソース: ユーザー（users）
├── GET    /api/users          → ユーザー一覧を取得
├── POST   /api/users          → ユーザーを新規作成
├── GET    /api/users/:id      → 特定のユーザーを取得
├── PATCH  /api/users/:id      → ユーザー情報を更新
└── DELETE /api/users/:id      → ユーザーを削除
```

### APIリファレンスに含めるべき項目

網羅的なAPIリファレンスには、以下の情報が**すべてのエンドポイント**に対して記載されています。

| 項目                 | 説明                           | 例                                 |
| -------------------- | ------------------------------ | ---------------------------------- |
| **エンドポイント**   | リソースのURL                  | `GET /api/users/:id`               |
| **メソッド**         | HTTPメソッド                   | GET, POST, PATCH, DELETE           |
| **パラメータ**       | パス・クエリ・ボディの入力値   | `:id`（パス）, `?page=2`（クエリ） |
| **リクエスト例**     | 実際のリクエストボディ         | JSONの具体的な値                   |
| **レスポンス例**     | 成功時のレスポンスボディ       | JSONの具体的な値                   |
| **ステータスコード** | 成功・エラー時のHTTPステータス | 200, 201, 400, 404                 |
| **エラーメッセージ** | エラー時のレスポンス形式       | エラーコードと説明文               |

## ちゃんと使うためのポイント

- <Marker>URLはリソース（名詞）で構成し、操作はHTTPメソッドで表現する</Marker>
- レスポンス形式はプロジェクト全体で統一する。一覧は配列をそのまま返さず、キーの下に入れる
- ステータスコードを正しく使い分けることで、フロントエンド側の分岐がシンプルになる
- ページネーションは、ページ番号が必要ならオフセット方式、無限スクロールや件数の多い一覧ならカーソル方式を検討する
- 破壊的変更は新しいバージョンで出し、古いバージョンを止める時期も決めておく
- APIリファレンスにはエンドポイント・パラメータ・リクエスト例・レスポンス例・ステータスコード・エラーメッセージを網羅する
- 迷ったらHTTP仕様に立ち返る
