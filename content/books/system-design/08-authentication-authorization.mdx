「ログイン機能を作って」と言われたとき、認証の方式選定から始められるかどうかは設計力の分かれ目です。
セッション、JWT、OAuth——それぞれの仕組みと使いどころを理解しておかないと、セキュリティ上の事故にもつながります。

この章では、認証と認可の違いから、主要な認証方式の比較までを整理します。

「認証」と「認可」って同じじゃないの？セッションとJWT、どっちを選べばいいの…？
</SpeechBubble>

## 認証と認可の違い

この2つは混同されがちですが、まったく別の概念です。

| 概念 | 質問 | 例 |
|---|---|---|
| 認証（Authentication） | 「あなたは誰？」 | ログイン、本人確認 |
| 認可（Authorization） | 「あなたは何ができる？」 | 管理者のみ削除可能、一般ユーザーは閲覧のみ |

認証が通っても、認可されていない操作はブロックする必要があります。

<MermaidDiagram chart={`
flowchart LR
    A["リクエスト"] --> B{"認証"}
    B -->|失敗| C["401 Unauthorized"]
    B -->|成功| D{"認可"}
    D -->|権限なし| E["403 Forbidden"]
    D -->|権限あり| F["処理実行"]
`} />

## 主要な認証方式の比較

| 方式 | 状態管理 | 適するケース |
|---|---|---|
| セッション | サーバー側（メモリ/DB/Redis） | 従来型Webアプリ、SSR中心 |
| JWT | クライアント側（トークン） | SPA、モバイルアプリ、マイクロサービス |
| OAuth 2.0 | 外部サービスに委譲 | ソーシャルログイン、外部API連携 |

## セッション方式の仕組み

セッション方式は、ログイン状態をサーバー側で管理する伝統的な手法です。

<MermaidDiagram chart={`
sequenceDiagram
    participant C as ブラウザ
    participant S as サーバー
    participant DB as セッションストア
    C->>S: POST /login (email, password)
    S->>DB: セッションID生成・保存
    S-->>C: Set-Cookie: session_id=abc123
    C->>S: GET /profile (Cookie: session_id=abc123)
    S->>DB: abc123 のユーザーを検索
    DB-->>S: user_id=42
    S-->>C: 200 OK (プロフィール情報)
`} />

```typescript
// Express + express-session の例
app.post('/login', async (req, res) => {
  const user = await db.findByEmail(req.body.email);
  if (!user || !await bcrypt.compare(req.body.password, user.passwordHash)) {
    return res.status(401).json({ error: '認証失敗' });
  }
  // ログイン成功時にセッションIDを作り直す（セッション固定攻撃の対策）
  req.session.regenerate((err) => {
    if (err) return res.status(500).json({ error: 'ログインに失敗しました' });
    req.session.userId = user.id;
    res.json({ message: 'ログイン成功' });
  });
});

app.get('/profile', (req, res) => {
  if (!req.session.userId) {
    return res.status(401).json({ error: '未認証' });
  }
  // req.session.userId でユーザー情報を取得
});
```

<Callout type="warning" title="ログイン時にセッションIDを作り直す">
ログイン前から使っているセッションIDをログイン後もそのまま使うと、攻撃者が事前に用意したセッションIDを被害者に使わせ、ログイン後にそのIDでなりすます攻撃（セッション固定攻撃）が成立します。ログインに成功した時点でIDを新しく発行します。`express-session` では `req.session.regenerate()` がこれに当たります（[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、英語）。
</Callout>

セッションIDを入れるCookieには `HttpOnly`・`Secure`・`SameSite` を付けます。各属性の意味は[ヘッダーとCookieの章](/books/http-and-web-api/04-headers-and-cookies#section-6)で扱っています。

<Callout type="warning" title="CSRF対策が必須">
セッション方式ではCookieが自動送信されるため、CSRF（クロスサイトリクエストフォージェリ）対策が必須です。CSRFトークンの埋め込みや、`SameSite=Lax` / `SameSite=Strict` の設定で防御します。
</Callout>

## JWTの仕組み

JWT（JSON Web Token）はトークンにユーザー情報を含め、サーバー側でセッションを持たない方式です。

### JWTの構造

JWTは3つのパートをドット（`.`）で繋いだ文字列です。

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjQyLCJleHAiOjE3MTk5MDAwMDB9.ccouJpQD9Ib7oVUwyHpQ7QgPDFmo_o-mCjNIdl2i9Hc
 ↑ Header                             ↑ Payload                                  ↑ Signature
```

| パート | 内容 | Base64URLデコードすると |
|---|---|---|
| Header | 署名アルゴリズムとトークンの種類 | `{"alg":"HS256","typ":"JWT"}` |
| Payload | ユーザー情報・有効期限 | `{"userId":42,"exp":1719900000}` |
| Signature | 改ざん検知用の署名 | HeaderとPayloadを、サーバーの秘密鍵で署名した値 |

上のトークンは、秘密鍵を `secret` という文字列にして実際に生成したものです。HeaderとPayloadは、ブラウザのコンソールで `atob('eyJ1c2VySWQiOjQyLCJleHAiOjE3MTk5MDAwMDB9')` を実行すると読めます。エンコードは通常のBase64ではなく、`+` と `/` を `-` と `_` に置き換え、末尾の `=` を省いた **Base64URL** です。`exp` は有効期限で、1970年1月1日からの秒数です（`1719900000` は2024年7月2日 06:00 UTC）。

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">
Payloadは暗号化されていないので、Base64デコードすれば誰でも中身を読める。パスワードやクレジットカード番号を入れてはいけないよ。
</SpeechBubble>

```typescript
// jsonwebtoken の例
import jwt from 'jsonwebtoken';

// トークン生成（ログイン時）
const token = jwt.sign(
  { userId: user.id },
  process.env.JWT_SECRET!,
  { expiresIn: '1h' }
);

// トークン検証（リクエストごと）
const decoded = jwt.verify(token, process.env.JWT_SECRET!, {
  algorithms: ['HS256'], // 受け付ける署名アルゴリズムを固定する
});
// decoded.userId でユーザーを特定
```

`jwt.verify()` は、署名が正しいことと、有効期限が切れていないことの両方を確かめます。上のサンプルトークンで試した結果です。

| 渡したもの | 結果 |
|---|---|
| 期限切れのトークン | `TokenExpiredError: jwt expired` |
| 署名を1文字書き換えたトークン | `JsonWebTokenError: invalid signature` |
| `algorithms: ['RS256']` を指定してHS256のトークンを検証 | `JsonWebTokenError: invalid algorithm` |

<Callout type="warning" title="jwt.decode() は検証しない">
`jsonwebtoken` には `jwt.decode()` もありますが、これはPayloadを読むだけで、署名も有効期限も確かめません。誰でも作れる偽のトークンがそのまま通ります。認証の判定には必ず `jwt.verify()` を使います。`algorithms` で受け付けるアルゴリズムを固定するのは、トークンのHeaderに書かれた `alg` を攻撃者が書き換える手口を防ぐためです（[RFC 8725 — JSON Web Token Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html)、英語）。
</Callout>

### トークンをどこに保存するか

JWTをブラウザのどこに置くかで、盗まれ方が変わります。

| 保存場所 | JavaScriptから読めるか | 主なリスク |
|---|---|---|
| `localStorage` | 読める | XSSがあると、攻撃者のスクリプトがトークンを読み出して外部へ送れる |
| `HttpOnly` 属性付きのCookie | 読めない | Cookieは自動送信されるので、CSRF対策が要る |
| メモリ（JavaScriptの変数） | 読める | リロードで消える。リフレッシュトークンを別に持つ必要がある |

OWASPは、セッションの識別子を `localStorage` に保存しないよう勧めています。JavaScriptから常に読めるためです（[OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)、英語）。

JWTを `HttpOnly` のCookieに入れるなら、セッション方式と何が違うの？
</SpeechBubble>

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">
ブラウザから見た動きはほぼ同じになるよ。違いはサーバー側で、セッション方式はリクエストのたびにセッションストアを引く、JWTは署名の検証だけで済む。その代わり、JWTは発行したあとに個別に無効化できない。

### リフレッシュトークンの設計

アクセストークンの有効期限は短くし（15分〜1時間）、長期間のログイン維持にはリフレッシュトークンを使います。

<MermaidDiagram chart={`
sequenceDiagram
    participant C as クライアント
    participant S as サーバー
    C->>S: POST /login
    S-->>C: accessToken(15分) + refreshToken(7日)
    Note over C: アクセストークンで通常のAPI呼び出し
    C->>S: GET /api/data (Authorization: Bearer accessToken)
    Note over C: アクセストークンが期限切れ
    C->>S: POST /refresh (refreshToken)
    S-->>C: 新しい accessToken
`} />

<Marker>リフレッシュトークンはサーバー側のDBに保存し、無効化できるようにしておく。ユーザーがログアウトしたら、そのリフレッシュトークンを削除する。</Marker>

## OAuth 2.0 — 認可コードフロー

OAuth 2.0は、ユーザーのパスワードを預からずに、外部サービス上のデータへのアクセス権を受け取る仕組みです。「Googleでログイン」「GitHubでログイン」は、この仕組みを土台にしています。

<Callout type="info" title="OAuth 2.0は認可、ログインはOpenID Connect">
OAuth 2.0そのものが定めているのは「このアプリに、Googleカレンダーの読み取りを許可する」といった**認可**です。「このユーザーは誰か」を伝える仕様は含まれていません。ログインに使う場合は、OAuth 2.0の上に本人情報の受け渡し（IDトークン）を足した **OpenID Connect**（OIDC）を使います。Googleのログインは、OIDCに準拠しています（[OpenID Connect — Google for Developers](https://developers.google.com/identity/openid-connect/openid-connect?hl=ja)）。
</Callout>

<YouTubeShort id="L8jKdZOtytk" title="「アクセスを許可しますか？」の正体【OAuth】" caption="パスワードを渡さずにアプリ連携できる仕組み（81秒）" />

<MermaidDiagram chart={`
sequenceDiagram
    participant U as ユーザー
    participant A as あなたのアプリ
    participant G as Google
    U->>A: 「Googleでログイン」をクリック
    Note over A: ランダムな state を生成して保存
    A->>G: 認可画面にリダイレクト（state を付ける）
    U->>G: アクセスを許可
    G->>A: 認可コードと state を返す
    Note over A: state が保存した値と一致するか確認
    A->>G: 認可コード + クライアントシークレットでトークン取得
    G-->>A: アクセストークン
    A->>G: アクセストークンでユーザー情報取得
    G-->>A: ユーザー情報(email, name等)
    A-->>U: ログイン完了
`} />

<Figure src="/images/search_woman_color.png" alt="OAuth認証の仕組みを学ぶ" caption="OAuth 2.0 では、ユーザーのパスワードを自分のサーバーに保存しなくて済む" maxWidth="260px" />

図の中の `state` は、省略すると攻撃が成立する部分です。

| パラメータ | 役割 | 省略すると |
|---|---|---|
| `state` | アプリが生成したランダムな値。戻ってきた値と照合する | 攻撃者が自分の認可コードを被害者のブラウザに送り込み、被害者を攻撃者のアカウントでログインさせられる（CSRF） |
| `code_verifier` / `code_challenge`（PKCE） | 認可コードを要求した本人だけがトークンに交換できるようにする | 認可コードを横取りされたとき、攻撃者がトークンに交換できる |

PKCEは [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) で定義されている拡張です。クライアントシークレットを安全に持てないSPAやモバイルアプリでは必須で、サーバー側のアプリでも併用が勧められています。

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">
このあたりを自分で実装すると、照合を1つ忘れただけで穴になる。実務では、各サービスが出している公式のライブラリや、認証用のライブラリに任せるのが基本だよ。
</SpeechBubble>

## ロールベースアクセス制御（RBAC）

認可の実装でよく使われるのが RBAC です。ユーザーにロール（役割）を割り当て、ロールごとに操作権限を定義します。

```typescript
// シンプルなRBACの例
type Role = 'admin' | 'editor' | 'viewer';

const permissions: Record<Role, string[]> = {
  admin:  ['read', 'write', 'delete', 'manage_users'],
  editor: ['read', 'write'],
  viewer: ['read'],
};

function authorize(userRole: Role, action: string): boolean {
  return permissions[userRole].includes(action);
}

// ミドルウェアとして使う
function requirePermission(action: string) {
  return (req, res, next) => {
    if (!authorize(req.user.role, action)) {
      return res.status(403).json({ error: '権限がありません' });
    }
    next();
  };
}

app.delete('/posts/:id', requirePermission('delete'), deletePost);
```

## 方式選定のフローチャート

<MermaidDiagram chart={`
flowchart TB
    A["ログイン機能が必要"] --> B{"ソーシャルログインが必要?"}
    B -->|はい| C["OAuth 2.0"]
    B -->|いいえ| D{"クライアントはブラウザだけで、APIも同じサイトにある?"}
    D -->|はい| G["セッション方式（HttpOnlyのCookie）"]
    D -->|いいえ| F{"モバイルアプリ、または別ドメインのAPI?"}
    F -->|はい| E["JWT + リフレッシュトークン"]
    F -->|いいえ| H["JWT（マイクロサービス間通信など）"]
`} />

この分岐は筆者の判断です。SPAであっても、APIが同じサイトにあるならセッション方式を先に検討します。`HttpOnly` のCookieはJavaScriptから読めず、ログアウトや強制失効もサーバー側でセッションを消すだけで済むためです。JWTが向くのは、Cookieを使いにくいモバイルアプリや、複数のサービスが同じトークンを検証する構成です。

## ちゃんと使うためのポイント

- <Marker>認証（誰か）と認可（何ができるか）は別の仕組みとして設計する</Marker>
- JWTはステートレスだがトークン無効化が難しい。リフレッシュトークンをDB管理して対応する
- セッション方式はCSRF対策が必須
- JWTのPayloadは暗号化されていない。秘密情報を含めない
- OAuth 2.0はパスワードを預からずに済む。ソーシャルログインに適する
- 「どの方式が正解か」ではなく、要件（SPA？SSR？モバイル？）で選ぶ

- JWTの検証は `jwt.verify()` で行い、`algorithms` を固定する。`jwt.decode()` は検証しない
- トークンやセッションIDを `localStorage` に置かない。`HttpOnly` のCookieを使う
- OAuth 2.0の `state` は必ず照合する。ログイン用途はOpenID Connect
