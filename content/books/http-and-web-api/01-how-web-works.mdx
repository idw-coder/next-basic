ブラウザのアドレスバーにURLを入力してEnterを押すと、一瞬でページが表示されます。しかしその裏側では、複数のサーバーとの通信が何段階にもわたって行われています。

この章では、Webの通信がどんな手順で進むのかを「全体の地図」として整理します。個々の技術は後の章で掘り下げるので、ここではまず流れの全体像を掴みます。

## ブラウザからページが表示されるまでの流れ

<MermaidDiagram chart={`
sequenceDiagram
    participant B as ブラウザ
    participant D as DNSサーバー
    participant S as Webサーバー
    B->>D: example.com のIPは?
    D-->>B: 93.184.216.34
    B->>S: TCP接続要求
    S-->>B: 接続OK
    B->>S: HTTP GET /index.html
    S-->>B: 200 OK + HTML
    B->>S: GET /style.css, /app.js ...
    S-->>B: 200 OK + リソース
`} />

大きく分けると **3つのフェーズ** で進みます。

1. **名前解決（DNS）** — ドメイン名をIPアドレスに変換する
2. **接続確立（TCP）** — サーバーとの通信路を確保する
3. **データのやりとり（HTTP）** — リクエストを送り、レスポンスを受け取る

この「DNS → TCP → HTTP」の順番は、Web開発のトラブルシューティングでも切り分けの基本になります。

---

## フェーズ1: 名前解決 — DNSの役割

<Figure src="/images/question_woman_04_color.png" alt="疑問を持つ女性のイラスト" maxWidth="300px" />

ブラウザは `example.com` という文字列のままでは通信できません。実際に通信するには、サーバーの **IPアドレス**（例: `93.184.216.34`）が必要です。

この「ドメイン名 → IPアドレス」の変換を行うのが **DNS（Domain Name System）** です。電話帳で名前から電話番号を調べるようなものです。

```
example.com → DNSに問い合わせ → 93.184.216.34
```

DNSの結果は一定時間 **キャッシュ** されます。ブラウザ、OS、ルーターなど複数のレイヤーにキャッシュが存在し、毎回DNSサーバーまで問い合わせるわけではありません。

<Callout type="note">
### DNSキャッシュのトラブル

サーバーのIPが変わったのに古いキャッシュが残っていて接続先が切り替わらない、というのは実務でよくあるトラブルです。DNSレコードには **TTL（Time to Live）** という有効期限が設定されていて、サーバー移行前にTTLを短くしておくのが定石です。

</Callout>

---

## フェーズ2: 接続確立 — TCPの役割

IPアドレスがわかったら、次はサーバーとの **通信路** を確保します。Web通信では **TCP（Transmission Control Protocol）** が使われます。

TCPは通信を始める前に「3ウェイハンドシェイク」と呼ばれる手順でお互いの準備を確認します。

<MermaidDiagram chart={`
sequenceDiagram
    participant C as ブラウザ
    participant S as サーバー
    C->>S: SYN (接続したい)
    S-->>C: SYN-ACK (OK)
    C->>S: ACK (了解)
    Note over C,S: 接続確立
`} />

このハンドシェイクによって、**データが確実に、正しい順序で届く** ことが保証されます。Webページは1バイトでも欠けるとHTMLやCSSが壊れるため、この信頼性が重要です。

<Callout type="column">
### HTTP/3とQUIC

HTTP/1.1とHTTP/2はTCP上で動きますが、**HTTP/3** はUDPベースの **QUIC** というプロトコル上で動きます。TCPのハンドシェイクを省略して接続を高速化する仕組みで、Googleのサービスなどで広く使われています。

</Callout>

## フェーズ3: データのやりとり — HTTPの役割

TCP接続が確立したら、いよいよ **HTTP（HyperText Transfer Protocol）** でデータをやりとりします。

HTTPは「**リクエスト → レスポンス**」の1往復が基本です。

```
ブラウザ → サーバー:  GET /index.html HTTP/1.1
サーバー → ブラウザ:  HTTP/1.1 200 OK + HTMLの中身
```

HTMLを受け取ったブラウザは、その中に書かれたCSS・JavaScript・画像の参照を見つけて、それぞれ追加のHTTPリクエストを送ります。1つのページを表示するために、数十回のHTTPリクエストが飛ぶのは普通です。

## URLの構造を分解する

HTTPリクエストの宛先となるURLは、いくつかのパーツで構成されています。

```
https://api.example.com:443/users/1?fields=name,email#profile
```

| パーツ | 値 | 意味 |
|---|---|---|
| スキーム | `https` | 通信プロトコル |
| ホスト | `api.example.com` | サーバーのドメイン名 |
| ポート | `443` | 接続先のポート番号（HTTPS既定は443） |
| パス | `/users/1` | サーバー上のリソースの位置 |
| クエリ | `?fields=name,email` | 追加のパラメータ |
| フラグメント | `#profile` | ページ内の位置（サーバーには送られない） |

Web APIの設計ではこの中の **パス** と **クエリ** を特によく使います。「リソースの特定はパスで、フィルタや並び順はクエリで」というのがREST APIの基本的な考え方です。

## HTTPSとセキュリティ

現代のWebでは、HTTPではなく **HTTPS** が標準です。HTTPSは、HTTPの通信を **TLS（Transport Layer Security）** で暗号化したものです。

| | HTTP | HTTPS |
|---|---|---|
| 通信 | 平文（暗号化なし） | TLSで暗号化 |
| ポート | 80 | 443 |
| ブラウザ表示 | 「保護されていない通信」と警告 | 鍵マーク表示 |

HTTPSがないと、通信経路上の第三者がリクエストの中身（パスワード、Cookie、APIレスポンスなど）を盗聴・改ざんできてしまいます。開発環境でもHTTPS化が推奨されるのはそのためです。

<Callout type="warning">
### HTTPのままだと何が起きるか

公共Wi-Fiなどの共有ネットワークでHTTP通信を行うと、同じネットワーク上の攻撃者にCookieやフォーム入力を傍受される可能性があります。本番環境では **HTTPS必須** です。

</Callout>

<Callout type="column">
### GitHubのcloneで見るHTTPSとSSHの違い

GitHubでリポジトリをcloneするとき、URLとして **HTTPS** と **SSH** を選べます。

```bash
# HTTPS
git clone https://github.com/example/app.git

# SSH
git clone git@github.com:example/app.git
```

どちらも「GitHubのサーバーと安全に通信する」ための方法ですが、使っている仕組みが違います。

| | HTTPS clone | SSH clone |
|---|---|---|
| 通信の仕組み | HTTPをTLSで暗号化する | SSHプロトコルで暗号化する |
| 認証方法 | GitHubのユーザー名 + Personal Access Tokenなど | PCに置いた秘密鍵 + GitHubに登録した公開鍵 |
| URLの例 | `https://github.com/user/repo.git` | `git@github.com:user/repo.git` |
| よく使う場面 | 初回設定を少なく始めたいとき、社内プロキシ環境 | 開発用PCから頻繁にpush/pullするとき |

HTTPSはこの章で扱っているWeb通信の延長にあります。ブラウザでWebサイトを見るときと同じく、TLSで通信内容を暗号化します。ただしGitHubではパスワード認証ではなく、Personal Access Tokenなどを使います。

SSHはHTTPとは別のプロトコルです。サーバーにログインしたり、Git操作を安全に行ったりするためによく使われます。SSHでは、手元のPCに **秘密鍵** を置き、対応する **公開鍵** をGitHubに登録して「このPCからの接続は本人だ」と確認します。

迷ったら、まずはHTTPSでcloneして問題ありません。pushやpullを頻繁に行う開発用PCでは、SSH鍵を設定してSSH cloneを使うと、認証情報の入力が少なくなり運用しやすくなります。

</Callout>

## DevToolsで実際に確認する

ここまでの内容は、ブラウザの **開発者ツール（DevTools）** で実際に確認できます。Chrome DevToolsを開いて（`F12` または `Cmd + Option + I`）、Networkタブを見ながら任意のページにアクセスしてみます。

### DNS・TCP・HTTPの所要時間を見る

Networkタブでリクエストを選択し、**Timing** タブを見ると、各フェーズにかかった時間がわかります。

| 項目 | 対応するフェーズ |
|---|---|
| **DNS Lookup** | ドメイン名 → IPアドレスの変換 |
| **Initial Connection** | TCPハンドシェイク |
| **SSL** | TLS暗号化のネゴシエーション |
| **Waiting (TTFB)** | サーバーが処理してレスポンスを返すまで |
| **Content Download** | レスポンスボディのダウンロード |

<Callout type="info">
### TTFBが遅いときの切り分け

**TTFB（Time to First Byte）** はサーバーの処理時間を反映します。DNS LookupやInitial Connectionは正常なのにTTFBだけ遅い場合、問題はサーバー側（遅いクエリ、重い処理など）にあります。逆にDNS Lookupが遅い場合は、DNSサーバーの応答やキャッシュの問題です。

</Callout>

### 1ページで何回リクエストが飛ぶか

NetworkタブのStatusバーに表示される「XX requests」の数字を見ると、1ページの表示に何回のHTTPリクエストが必要かがわかります。一般的なWebサイトでは **30〜100回以上** のリクエストが飛びます。HTML、CSS、JavaScript、画像、フォント、API呼び出し — それぞれが独立したHTTPリクエストです。

## よくあるトラブルと切り分け方

Web開発で「繋がらない」「表示されない」というとき、DNS・TCP・HTTPのどこでコケているかを切り分けるのが最短ルートです。

<MermaidDiagram chart={`
flowchart TD
    classDef check fill:#3b82f6,color:#fff,stroke:#2563eb
    classDef dns fill:#8b5cf6,color:#fff,stroke:#7c3aed
    classDef tcp fill:#f59e0b,color:#fff,stroke:#d97706
    classDef http fill:#22c55e,color:#fff,stroke:#16a34a

    A["サイトが表示されない"] --> B{"ping でIPに届く?"}
    B -->|No| C["DNS or ネットワークの問題"]
    B -->|Yes| D{"ポートに接続できる?"}
    D -->|No| E["ファイアウォール or サーバー停止"]
    D -->|Yes| F{"HTTPレスポンスが返る?"}
    F -->|No| G["アプリサーバーの問題"]
    F -->|Yes| H["レスポンスの中身を確認"]

    class A check
    class C dns
    class E tcp
    class G,H http
`} id="troubleshoot" />

```bash
# 1. 名前解決できるか確認
nslookup example.com

# 2. IPに到達できるか確認
ping example.com

# 3. ポートに接続できるか確認
curl -v https://example.com 2>&1 | head -20
```

`curl -v` の出力を見れば、DNS解決、TCP接続、TLSハンドシェイク、HTTPレスポンスのどこまで進んだかがわかります。

## まとめ

Webの通信は **DNS → TCP → HTTP** の3段階で進みます。

- **DNS** でドメイン名をIPアドレスに変換する
- **TCP** で信頼性のある通信路を確立する
- **HTTP** でリクエストとレスポンスをやりとりする
- **HTTPS** はHTTPをTLSで暗号化したもので、現代のWebでは必須
- **SSH** はHTTPとは別の安全な通信プロトコルで、GitHubのSSH cloneなどで使われる

この全体像を押さえておくと、「サーバーに繋がらない」「レスポンスがおかしい」といったトラブルのとき、どの層で問題が起きているかを切り分けられるようになります。
