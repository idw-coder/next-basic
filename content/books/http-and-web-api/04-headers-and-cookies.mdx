HTTPリクエストとレスポンスは、**ボディ**（本文）だけでなく **ヘッダー** という付加情報を持っています。認証トークン、コンテンツの形式、キャッシュの制御、Cookieなど、HTTP通信の重要な制御情報はすべてヘッダーでやりとりされます。

この章では、主要なHTTPヘッダーの役割と、Web開発で特に重要な **Cookie** の仕組みを整理します。

<a id="section-1"></a>

## HTTPメッセージの構造

リクエストもレスポンスも、**スタートライン + ヘッダー + 空行 + ボディ** という共通の構造です。

```
POST /api/users HTTP/1.1          ← スタートライン（メソッド、パス、バージョン）
Host: api.example.com             ← ヘッダー（複数行）
Content-Type: application/json
Authorization: Bearer eyJhbG...
                                  ← 空行（ヘッダーとボディの区切り）
{"name": "Alice"}                 ← ボディ
```

レスポンスも同様です。

```
HTTP/1.1 200 OK                   ← スタートライン（バージョン、ステータスコード）
Content-Type: application/json
Set-Cookie: session=abc123

{"id": 1, "name": "Alice"}
```

<a id="section-2"></a>

## よく使うリクエストヘッダー

<Figure src="/images/planning_suit_man_color.png" alt="計画を立てている男性のイラスト" maxWidth="300px" />

| ヘッダー | 役割 | 例 |
|---|---|---|
| `Host` | リクエスト先のホスト名 | `api.example.com` |
| `Content-Type` | ボディのデータ形式 | `application/json` |
| `Authorization` | 認証情報 | `Bearer eyJhbG...` |
| `Accept` | 受け取りたいレスポンスの形式 | `application/json` |
| `User-Agent` | クライアントの情報 | ブラウザ名やバージョン |
| `Cookie` | 保存済みCookieの送信 | `session=abc123` |

### Content-Typeの重要性

`Content-Type` はサーバーが「ボディをどう解釈するか」を決めるヘッダーです。これが間違っていると、サーバーがボディを正しくパースできません。

```
// JSON形式で送る場合
Content-Type: application/json

// フォームデータで送る場合
Content-Type: application/x-www-form-urlencoded

// ファイルアップロードの場合
Content-Type: multipart/form-data
```

<Callout type="warning">
### Content-Typeの付け忘れ

`fetch` でPOSTリクエストを送る際、`Content-Type: application/json` を付け忘れてサーバーが `{}` を受け取れない、というのはよくあるミスです。リクエストライブラリ（axios等）は自動で付けてくれることが多いですが、素の `fetch` では明示的に指定が必要です。

</Callout>

<a id="section-3"></a>

## よく使うレスポンスヘッダー

| ヘッダー | 役割 | 例 |
|---|---|---|
| `Content-Type` | レスポンスのデータ形式 | `application/json; charset=utf-8` |
| `Set-Cookie` | Cookieの設定 | `session=abc123; HttpOnly; Secure` |
| `Cache-Control` | キャッシュの制御 | `max-age=3600` |
| `ETag` | 中身の識別子（再検証に使う） | `"33a64df5"` |
| `Location` | リダイレクト先 | `/api/users/42` |
| `Access-Control-Allow-Origin` | CORS許可 | `https://example.com` |

<a id="section-4"></a>

## キャッシュ制御

`Cache-Control` ヘッダーは、ブラウザや中間プロキシに「このレスポンスをどの程度キャッシュしていいか」を指示します。

```
// 1時間キャッシュしてよい
Cache-Control: max-age=3600

// キャッシュしてはいけない
Cache-Control: no-store

// キャッシュしてよいが、使う前に再検証すること
Cache-Control: no-cache
```

| ディレクティブ | 意味 |
|---|---|
| `max-age=N` | N秒間キャッシュしてよい |
| `no-store` | 一切キャッシュしない |
| `no-cache` | キャッシュするが毎回再検証 |
| `private` | ブラウザのみキャッシュ可（CDNは不可） |
| `public` | CDNを含めキャッシュ可 |

<Callout type="column">
### no-cacheとno-storeの違い

名前が紛らわしいですが、`no-cache` は「キャッシュするな」ではなく「キャッシュしてもいいけど使う前にサーバーに確認して」という意味です。キャッシュを完全に禁止したい場合は `no-store` を使います。

</Callout>

<a id="section-4b"></a>

## ETagと条件付きリクエスト

`no-cache` の「使う前にサーバーに確認」は、具体的にどうやって確認しているのでしょうか。その仕組みが **ETag** と **条件付きリクエスト** です。

<SpeechBubble character="/images/question_woman_04_color.png" name="学習者">
確認するたびにデータを丸ごと取り直すなら、キャッシュしている意味がないんじゃない？
</SpeechBubble>

そうならないように、確認の段階では「中身が変わったかどうか」だけをやりとりします。変わっていなければ、ボディ（本文）は送られません。

### ETagは「中身の指紋」

**ETag**（Entity Tag）は、サーバーがレスポンスに付ける識別子です。中身が変われば別の値になるので、指紋のような役割を果たします。

```
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "33a64df5"

{"id": 42, "name": "Alice"}
```

値の作り方はサーバー次第です。よくあるのはボディのハッシュ値や、更新日時とバージョン番号の組み合わせです。クライアント側は値の中身を解釈せず、「前回と同じか」を比べるためだけに使います。

### If-None-Matchで「変わった？」と聞く

ブラウザはETagをキャッシュと一緒に保存しておきます。再検証が必要になると、その値を **`If-None-Match`** ヘッダーに入れてリクエストします。

<MermaidDiagram chart={`
sequenceDiagram
    participant B as ブラウザ
    participant S as サーバー
    B->>S: GET /api/users/42
    S-->>B: 200 OK + ETag: "33a64df5" + ボディ
    Note over B: ボディとETagを保存
    B->>S: GET /api/users/42 + If-None-Match: "33a64df5"
    alt 変わっていない
        S-->>B: 304 Not Modified（ボディなし）
        Note over B: 保存済みのボディを使う
    else 変わった
        S-->>B: 200 OK + ETag: "8f1c02aa" + 新しいボディ
    end
`} />

- **ETagが一致した**：サーバーは **`304 Not Modified`** を返し、ボディは送りません。ブラウザは手元のキャッシュを使います
- **ETagが一致しなかった**：通常どおり `200 OK` で新しいボディと新しいETagを返します

このように「条件を付けて、満たしたときだけ処理してもらう」リクエストを **条件付きリクエスト** と呼びます。[3章](/books/http-and-web-api/03-status-codes)で出てきた `304` は、この仕組みで返されるステータスコードです。

### Last-Modifiedとの違い

ETagより古くからある方法として、更新日時を使う **`Last-Modified`** / **`If-Modified-Since`** の組み合わせもあります。

| 方式 | サーバーが付ける | ブラウザが送り返す | 比べるもの |
|---|---|---|---|
| ETag | `ETag: "33a64df5"` | `If-None-Match: "33a64df5"` | 識別子が一致するか |
| 更新日時 | `Last-Modified: Wed, 21 Oct 2026 07:28:00 GMT` | `If-Modified-Since: Wed, 21 Oct 2026 07:28:00 GMT` | その日時より後に更新されたか |

更新日時は秒単位なので、1秒の間に2回更新されると変更を見逃します。ETagにはこの問題がありません。両方が送られてきた場合、サーバーは `If-None-Match` を優先し、`If-Modified-Since` は無視すると仕様（[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#name-if-modified-since)）で決められています。

### 強いETagと弱いETag

ETagの先頭に `W/` が付いているものは **弱いETag**（weak ETag）です。

```
ETag: "33a64df5"      ← 強いETag：1バイトでも違えば別の値
ETag: W/"33a64df5"    ← 弱いETag：意味が同じなら同じ値でよい
```

弱いETagは「バイト単位では違っても、内容としては同じ」とみなしてよい場合に使います。たとえば圧縮のかけ方が違うだけのレスポンスです。キャッシュの再検証（`If-None-Match`）ではどちらも使えます。

<Callout type="info">
### ExpressはETagを自動で付ける

Expressの `res.send()` や `res.json()` は、デフォルトでボディから弱いETagを計算してレスポンスに付けます。さらに、リクエストの `If-None-Match` と一致すれば自動で `304` を返します。DevToolsで自作APIのレスポンスを見て `ETag: W/"..."` が付いていたら、この機能によるものです。不要なら `app.set('etag', false)` で止められます（[Express API: app.set](https://expressjs.com/en/api.html#app.settings.table)）。

</Callout>

### If-Matchで更新の衝突を防ぐ

条件付きリクエストはキャッシュ専用ではありません。**`If-Match`** を使うと、「自分が読んだときから誰も書き換えていなければ更新して」と頼めます。

```
PUT /api/users/42
If-Match: "33a64df5"
Content-Type: application/json

{"id": 42, "name": "Alice Smith"}
```

その間に別の人が更新していてETagが変わっていれば、サーバーは **`412 Precondition Failed`** を返して更新を拒否します。これにより、後から保存した人が先に保存した人の変更を気づかずに上書きする「ロストアップデート」を防げます。

この「ロックはかけずに、保存の瞬間に誰かが先に変えていないかを確かめる」方式を **楽観的ロック** と呼びます。`If-Match` は、楽観的ロックをHTTPのヘッダーだけで表す方法です。

<Callout type="column">
### バージョン番号をボディで送る方式もある

楽観的ロックは、ETagを使わずに実装することもよくあります。テーブルに `version` 列を持たせてリクエストのボディで送り返してもらい、一致しなければ `409 Conflict` を返す方式です（[システム設計本の6章](/books/system-design/06-api-design)のステータスコード表もこちらの形です）。仕組みは同じで、「何と比べるか」と「どのステータスコードで断るか」が違うだけです。どちらを選ぶかに決まりはありません。筆者の整理では、HTTPの標準どおりに書くなら `If-Match` と `412`、DBの `version` 列をそのままAPIに出すならボディと `409`、と考えると選びやすくなります。

</Callout>

| ヘッダー | 条件 | 主な用途 |
|---|---|---|
| `If-None-Match` | ETagが **一致しなければ** 処理する | キャッシュの再検証（一致したら `304`） |
| `If-Match` | ETagが **一致すれば** 処理する | 更新の衝突防止（不一致なら `412`） |

参考：
- [ETag - MDN](https://developer.mozilla.org/ja/docs/Web/HTTP/Reference/Headers/ETag) — ETagの書式と使い方
- [RFC 9110 - ETag](https://www.rfc-editor.org/rfc/rfc9110#name-etag) — 強いETag・弱いETagと条件付きリクエストの一次情報

## Cookieの仕組み

**Cookie** は、サーバーがブラウザに「この値を覚えておいて、次のリクエストで送り返して」と依頼する仕組みです。HTTPは本来ステートレス（状態を持たない）ですが、Cookieによって「ログイン状態」のような状態管理が可能になります。

<MermaidDiagram chart={`
sequenceDiagram
    participant B as ブラウザ
    participant S as サーバー
    B->>S: POST /login (ID+パスワード)
    S-->>B: 200 OK + Set-Cookie: session=abc123
    Note over B: Cookieを保存
    B->>S: GET /dashboard + Cookie: session=abc123
    S-->>B: 200 OK (ログイン済みの画面)
`} />

### Cookieの流れ

1. サーバーがレスポンスに `Set-Cookie` ヘッダーを含める
2. ブラウザがその値を保存する
3. 以降、同じドメインへのリクエストに `Cookie` ヘッダーとして自動送信する

---

<a id="section-6"></a>

## Cookieのセキュリティ属性

Cookieには付加属性があり、セキュリティ上の制御に使います。

```
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

| 属性 | 意味 | 設定しないリスク |
|---|---|---|
| `HttpOnly` | JavaScriptからアクセスできない | XSSでCookieを盗まれる |
| `Secure` | HTTPS接続でのみ送信 | 平文HTTP経由で盗聴される |
| `SameSite` | クロスサイトリクエストでの送信を制御 | CSRF攻撃を受けやすい |
| `Path` | 指定パス以下でのみ送信 | 不要な範囲にCookieが飛ぶ |
| `Max-Age` | 有効期限（秒数） | ブラウザ終了時に消える |

### SameSiteの3つの値

| 値 | 挙動 |
|---|---|
| `Strict` | 他サイトからのリクエストにはCookieを送らない |
| `Lax` | 他サイトからのGETリクエスト（リンククリック）には送る |
| `None` | 常に送る（`Secure` 属性が必須） |

<Callout type="warning">
### セッションCookieには必ずHttpOnly + Secure

セッションIDをCookieに入れる場合、`HttpOnly` と `Secure` は必ず付けます。`HttpOnly` がないと、XSS脆弱性があった場合にJavaScriptからセッションIDを抜き取られます。`Secure` がないと、HTTP通信でセッションIDが平文で流れます。

</Callout>

<a id="section-7"></a>

## CookieとlocalStorageの使い分け

ブラウザでデータを保存する方法はCookieだけではありません。よく比較されるのが `localStorage` です。

| | Cookie | localStorage |
|---|---|---|
| サーバーへの送信 | **自動で送信される** | 送信されない |
| 容量 | 約4KB | 約5MB |
| 有効期限 | 設定可能 | 永続（手動削除まで） |
| JavaScript | HttpOnlyで保護可 | 常にアクセス可能 |
| 用途 | セッション管理、認証 | UI設定、一時データ |

セッション管理にはCookie（HttpOnly）、UIの状態保持にはlocalStorage、というのが一般的な使い分けです。

## DevToolsでヘッダーとCookieを確認する

### リクエスト・レスポンスヘッダーの確認

NetworkタブでリクエストをクリックするとHeadersタブが開きます。ここで **Request Headers**（送信側）と **Response Headers**（受信側）の両方を確認できます。

実務で特にチェックする項目:

| 確認項目 | 見るべきヘッダー | よくある問題 |
|---|---|---|
| 認証トークンが送れているか | `Authorization` | トークンの付け忘れ、有効期限切れ |
| データ形式が正しいか | `Content-Type` | `application/json` の付け忘れ |
| CORSが通っているか | `Access-Control-Allow-Origin` | オリジンの不一致 |
| キャッシュが効いているか | `Cache-Control`, `ETag` | 古いデータが表示される |

### Cookieの確認

Chrome DevToolsの **Application** タブ → **Cookies** で、現在のドメインに保存されているCookieの一覧と、各セキュリティ属性を確認できます。

確認すべきポイント:

- `HttpOnly` が付いているか（JavaScriptからアクセスできないようになっているか）
- `Secure` が付いているか（HTTPS限定で送信されるか）
- `SameSite` の値が適切か（CSRF対策が有効か）
- `Expires / Max-Age` が適切か（セッション切れのタイミング）

<Callout type="info">
### 「ログインしたのにすぐ切れる」の調べ方

セッションがすぐ切れる場合は、Applicationタブで以下を確認します。

1. **Cookieが保存されているか** — `Set-Cookie` にセキュリティ属性の問題があると、ブラウザがCookieを拒否することがある
2. **`Max-Age` や `Expires` の値** — 有効期限が極端に短くないか
3. **`SameSite=None` なのに `Secure` がないか** — この組み合わせだとCookieが保存されない
4. **別ドメインからのリクエストか** — `SameSite=Strict` だとクロスサイトリクエストにCookieが付かない

</Callout>

### curlでヘッダーを確認する

ブラウザを介さずにヘッダーを確認したいときは、`curl -v` が便利です。

```bash
# -v でリクエスト/レスポンスヘッダーを表示
curl -v https://api.example.com/users

# 特定のヘッダーを付けてリクエスト
curl -H "Authorization: Bearer YOUR_TOKEN" \
     -H "Content-Type: application/json" \
     https://api.example.com/users

# レスポンスヘッダーだけ確認（ボディは不要）
curl -I https://api.example.com/users
```

`curl -v` の出力で `>` がリクエスト、`<` がレスポンスのヘッダーです。APIの動作確認やデバッグで頻繁に使います。

## まとめ

- <Marker>HTTPメッセージは **スタートライン + ヘッダー + ボディ** で構成される</Marker>
- `Content-Type` はボディの解釈方法を伝える重要なヘッダー
- `Cache-Control` でキャッシュの有無と期間を制御する。`no-cache` と `no-store` の意味は違う
- **ETag** と `If-None-Match` で「変わったか」だけを確認し、変わっていなければ `304` でボディの再送を省く。`If-Match` を使えば楽観的ロックで更新の衝突も防げる
- **Cookie** はサーバーがブラウザに状態を保持させる仕組み。セッション管理の基盤
- セッションCookieには **HttpOnly + Secure + SameSite** を必ず設定する

次の章では、Web APIの設計パターンとして最も普及している **REST API** の考え方と命名規則を見ていきます。
