HTTPリクエストには必ず **メソッド** が含まれます。メソッドは、URLで指定したリソースに対して行う操作の種類（取得・作成・更新・削除など）をサーバーに伝える値です。HTTP/1.1では、リクエストの1行目の先頭に `GET /api/users/1 HTTP/1.1` のように書かれます。

この章では、Web APIで使う主要なHTTPメソッドの意味と使い分け、そして設計で重要になる **べき等性** と **安全性** の概念を整理します。

データを送るのはとりあえず全部 POST でいい気がするけど…GET や PUT ってわざわざ使い分ける必要あるの？
</SpeechBubble>

<SpeechBubble character="/images/oksign_man_color.png" name="先生" side="right">

</SpeechBubble>

## 主要なHTTPメソッド

<Figure src="/images/fork_suit_man_color.png" alt="分岐で悩む男性のイラスト" maxWidth="300px" />

最もよく使う4つのメソッドは、CRUDの各操作に対応します。

| メソッド | 意味 | CRUD | 例 |
|---|---|---|---|
| `GET` | リソースの取得 | Read | ユーザー情報を取得する |
| `POST` | リソースの作成 | Create | 新しいユーザーを登録する |
| `PUT` | リソースの全体更新 | Update | ユーザー情報を丸ごと書き換える |
| `DELETE` | リソースの削除 | Delete | ユーザーを削除する |

```
GET    /api/users/1        → ユーザー1の情報を取得
POST   /api/users           → 新しいユーザーを作成
PUT    /api/users/1        → ユーザー1の情報を全体更新
DELETE /api/users/1        → ユーザー1を削除
```

<Callout type="info">
### HTMLのフォームが送れるのはGETとPOSTだけ

`<form>` の `method` 属性でHTTPメソッドとして指定できるのは `get` と `post` の2つです（[MDN — form要素](https://developer.mozilla.org/ja/docs/Web/HTML/Reference/Elements/form)）。`PUT`・`PATCH`・`DELETE` は、JavaScriptの `fetch` などから送ります。

</Callout>

<a id="section-2"></a>

## その他のメソッド

上記4つに加えて、実務で登場するメソッドがいくつかあります。

| メソッド | 意味 | よくある使い方 |
|---|---|---|
| `PATCH` | リソースの部分更新 | 名前だけ変える、ステータスだけ変える |
| `OPTIONS` | サーバーが対応するメソッドの確認 | CORSのプリフライトリクエスト |
| `HEAD` | GETと同じだがボディなし | リソースの存在確認、キャッシュチェック |

`PUT` と `PATCH` の違いは、PUTが「リソース全体を送り直す」のに対し、PATCHが「変更したいフィールドだけ送る」という点です。

```
PUT /api/users/1
{ "name": "Bob", "email": "bob@example.com", "role": "admin" }
// ← 全フィールドを送る

PATCH /api/users/1
{ "name": "Bob" }
// ← 変えたいフィールドだけ送る
```

<Callout type="column">
### 実務でのPUT vs PATCH

理論上はPUTとPATCHの使い分けが明確ですが、実務ではPATCHだけで統一しているAPIも多いです。重要なのはチーム内で一貫したルールがあることで、「うちのAPIではPATCHで部分更新」と決めていれば問題ありません。

</Callout>

## 安全性とべき等性

HTTPメソッドには **安全性（Safe）** と **べき等性（Idempotent）** という2つの性質があります。API設計でメソッドを正しく選ぶための基準です。

**安全性** — そのリクエストがサーバーの状態を変更しないこと。GETは安全、POSTは安全ではない。

**べき等性** — 同じリクエストを1回送った場合と複数回送った場合とで、**サーバーの状態が同じになる**こと。GETやPUTはべき等、POSTはべき等ではない。

どちらも [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)（HTTPの仕様）の9.2.1節・9.2.2節で定義されています。日本語ではMDNの用語集の[安全](https://developer.mozilla.org/ja/docs/Glossary/Safe/HTTP)と[べき等](https://developer.mozilla.org/ja/docs/Glossary/Idempotent)で読めます。

| メソッド | 安全 | べき等 |
|---|---|---|
| `GET` | はい | はい |
| `POST` | いいえ | いいえ |
| `PUT` | いいえ | はい |
| `DELETE` | いいえ | はい |
| `PATCH` | いいえ | いいえ |

    A["GET"] --> S["安全 & べき等"]

### 同じなのは「サーバーの状態」で、レスポンスではない

べき等性で誤解しやすいのがDELETEです。

```
DELETE /api/users/1   → 204 No Content（削除された）
DELETE /api/users/1   → 404 Not Found（もう存在しない）
```

1回目と2回目でステータスコードは違いますが、どちらのあとも「ユーザー1が存在しない」というサーバーの状態は同じです。べき等性が見ているのはこの状態のほうなので、DELETEはべき等です。

PUTも同じ考え方です。`PUT /api/users/1` に同じボディを3回送っても、ユーザー1は3回とも同じ内容で上書きされるだけで、状態は1回送ったときと変わりません。一方、`POST /api/users` を3回送るとユーザーが3件作られます。

<SpeechBubble character="/images/question_woman_04_color.png" name="学習者">
PATCHは「名前だけ変える」なら何回送っても同じ結果になりそうだけど、べき等じゃないの？
</SpeechBubble>

`{ "name": "Bob" }` のように値をそのまま指定するPATCHは、何回送っても状態が同じになります。しかしPATCHのボディの形式は決まっておらず、「在庫を1増やす」のような差分の指示も送れます。その場合は送るたびに状態が変わります。PATCHを定義している [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html) が「PATCHは安全でもべき等でもない」としているのは、メソッドとしてべき等を保証できないためです。具体例は[システム設計の「API設計の基本」](/books/system-design/06-api-design)で扱っています。

### なぜべき等性が重要なのか

ネットワークは不安定です。リクエストを送ったのにレスポンスが返ってこなかった場合、「サーバーに届いたのか、届かなかったのか」がわかりません。

べき等なメソッド（GET、PUT、DELETE）なら、**もう一度同じリクエストを送っても問題ない** ので安全にリトライできます。POSTは送り直すと2件作成される可能性があるため、リトライには工夫が必要です。

## GETリクエストの原則

GETは最も頻繁に使われるメソッドです。いくつかの重要な原則があります。

**1. GETでデータを変更してはいけない**

```
// NG — GETで削除処理
GET /api/users/1/delete

// OK — DELETEメソッドを使う
DELETE /api/users/1
```

GETは検索エンジンのクローラーやブラウザのプリフェッチが自動的に送ることがあります。GETで副作用がある操作を作ると、意図せずデータが変更される危険があります。

**2. パラメータはクエリ文字列で渡す**

```
GET /api/users?page=2&limit=20&sort=name
```

GETにはリクエストボディを含めません。[RFC 9110の9.3.1節](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.1)は、GETリクエストのボディには一般に定義された意味がなく、実装によってはリクエストを拒否することがあるとしています。ブラウザの `fetch` も、`GET` に `body` を指定すると `TypeError` を投げます。

**3. クエリパラメータはURLエンコードする**

```
// NG — 空白や日本語をそのまま入れている
GET /api/articles?keyword=HTTP 入門&category=基礎&応用

// OK — URLで安全に扱える文字に変換する
GET /api/articles?keyword=HTTP%20%E5%85%A5%E9%96%80&category=%E5%9F%BA%E7%A4%8E%26%E5%BF%9C%E7%94%A8
```

URLでは、空白、日本語、`&`、`=`、`?` などの文字が特別な意味を持ったり、そのままでは安全に送れなかったりします。たとえば `category=基礎&応用` をそのまま送ると、`&` が「次のパラメータの区切り」と解釈され、サーバーが値を正しく読み取れません。

JavaScriptでは `URLSearchParams` を使うと、値を自動でエンコードできます。

```js
const params = new URLSearchParams({
  keyword: 'HTTP 入門',
  category: '基礎&応用',
});

fetch(`/api/articles?${params.toString()}`);
// /api/articles?keyword=HTTP+%E5%85%A5%E9%96%80&category=%E5%9F%BA%E7%A4%8E%26%E5%BF%9C%E7%94%A8
```

手動で1つの値だけ変換する場合は `encodeURIComponent()` を使います。URL全体ではなく、**パラメータの値ごと** にエンコードするのが基本です。

<Callout type="warning">
### クエリ文字列に機密情報を入れない

URLはブラウザの履歴、サーバーのアクセスログ、プロキシのログに残ります。パスワードやトークンをクエリ文字列に含めると、ログから漏洩するリスクがあります。機密情報はヘッダーやリクエストボディで送ります。

</Callout>

## POSTリクエストの使い方

POSTは新しいリソースを作成するときに使います。

```
POST /api/users
Content-Type: application/json

{
  "name": "Alice",
  "email": "alice@example.com"
}
```

レスポンスには通常 **201 Created** と、作成されたリソースの情報が返ります。

```
HTTP/1.1 201 Created
Location: /api/users/42

{
  "id": 42,
  "name": "Alice",
  "email": "alice@example.com"
}
```

`Location` ヘッダーで作成されたリソースのURLを返すのが行儀の良いAPIです。

<a id="section-6"></a>

## よくある誤用パターン

**1. すべてPOSTで処理する**

```
// NG — 全部POST
POST /api/getUser     { "id": 1 }
POST /api/deleteUser  { "id": 1 }

// OK — メソッドで意図を表現する
GET    /api/users/1
DELETE /api/users/1
```

メソッドを正しく使うと、URLを見ただけで「何をするAPIか」がわかります。

**2. GETで更新処理を行う**

```
// NG — ブラウザのプリフェッチやクローラーでも実行される
GET /api/users/1/activate
```

状態を変える操作には POST、PUT、PATCH、DELETE を使います。

## fetchで各メソッドを実際に使う

理論を押さえたら、実際のコードでHTTPメソッドを使い分けてみます。以下はブラウザの `fetch` APIでCRUD操作を行う典型的なパターンです。

```js
// GET — データの取得
const users = await fetch('/api/users').then(res => res.json());

// POST — データの作成
const newUser = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Alice', email: 'alice@example.com' }),
}).then(res => res.json());

// PUT — データの全体更新
await fetch('/api/users/42', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Bob', email: 'bob@example.com', role: 'admin' }),
});

// PATCH — データの部分更新
await fetch('/api/users/42', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Bob' }),
});

// DELETE — データの削除
await fetch('/api/users/42', { method: 'DELETE' });
```

`method` を省略するとGETになります。また、`fetch` はサーバーが404や500を返しても例外を投げません。失敗を検出するには `response.ok` を確認します。書き方は[HTTPステータスコードの章](/books/http-and-web-api/03-status-codes#section-6b)で扱っています。

### DevToolsで確認する

Chrome DevToolsのNetworkタブでリクエストを選択すると、**Method** 列にHTTPメソッドが表示されます。「この操作はGETで飛んでいるのか、POSTで飛んでいるのか」を確認する習慣をつけると、APIの挙動をデバッグしやすくなります。

Networkタブの **フィルター** で `method:POST` と入力すると、POSTリクエストだけを絞り込めます。「意図しないGETが飛んでいた」「POSTのはずがGETになっていた」といったバグの発見に役立ちます。

### POSTの二重送信を防ぐ

POSTはべき等ではないので、同じリクエストが2回届くとデータが2件作られます。2回届く原因は2つあり、対策が別です。

| 原因 | 対策 |
|---|---|
| 送信ボタンの連打 | 送信中はボタンを無効化する（フロント側） |
| タイムアウト後の再送（1回目がサーバーに届いていた） | べき等キーで、サーバーが同じ操作だと判定する |

**べき等キー**（idempotency key）は、クライアントが操作ごとに発行する一意な文字列です。サーバーは受け取ったキーを保存しておき、同じキーのリクエストがもう一度届いたら、処理をやり直さずに1回目の結果を返します。

```js
const [isSubmitting, setIsSubmitting] = useState(false);
// 1回の注文操作につきキーを1つ。再送しても同じ値を使う
const idempotencyKeyRef = useRef(crypto.randomUUID());

const handleSubmit = async () => {
  setIsSubmitting(true); // 連打対策
  try {
    const response = await fetch('/api/orders', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Idempotency-Key': idempotencyKeyRef.current, // 再送対策
      },
      body: JSON.stringify(orderData),
    });
    if (response.ok) {
      // 成功したら、次の注文のために新しいキーに替える
      idempotencyKeyRef.current = crypto.randomUUID();
    }
  } finally {
    setIsSubmitting(false);
  }
};
```

<Callout type="warning">
### キーを送信のたびに作り直すと再送対策にならない

`handleSubmit` の中で毎回 `crypto.randomUUID()` を呼ぶと、再送のたびにキーが変わり、サーバーは別の操作として処理します。キーは**操作の単位**で1つ作り、成功するまで同じ値を送ります。

また、ヘッダーを付けるだけでは何も起きません。サーバー側にキーを保存して照合する実装が必要です。`Idempotency-Key` というヘッダー名は決済APIなどで広く使われていますが、執筆時点ではIETFで[標準化の途中](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)にあるドラフトで、確定した標準ではありません。

</Callout>

## まとめ

- <Marker>HTTPメソッドは **CRUD操作** に対応する: GET=Read、POST=Create、PUT/PATCH=Update、DELETE=Delete</Marker>
- **安全性** はサーバーの状態を変えないこと、**べき等性** は何回送っても同じ結果になること
- GETは **データを変更しない・クエリパラメータをエンコードする・クエリ文字列に機密情報を入れない** が原則
- POSTは **べき等ではない** ため、リトライには注意が必要
- メソッドを正しく使い分けることで、API全体の可読性と信頼性が上がる
- べき等性が指すのは **サーバーの状態** で、レスポンスではない。2回目のDELETEが404でもDELETEはべき等

サーバーからの応答の読み方は、[HTTPステータスコード一覧](/books/http-and-web-api/03-status-codes)で扱っています。
