Web APIでやりとりするデータ形式として、現在最も広く使われているのが **JSON（JavaScript Object Notation）** です。名前にJavaScriptとありますが、言語に依存しない汎用的なデータ形式で、あらゆるプログラミング言語で扱えます。

この章では、JSONの基本的な構文、データ型、実務でのハマりどころを整理します。

## JSONの基本構文

JSONは **キーと値のペア** で構成されるテキスト形式です。

```json
{
  "id": 1,
  "name": "Alice",
  "email": "alice@example.com",
  "age": 28,
  "isAdmin": false,
  "tags": ["frontend", "react"],
  "address": {
    "city": "Tokyo",
    "zip": "100-0001"
  }
}
```

構文のルールはシンプルです。

- キーは **ダブルクォート** で囲む（シングルクォートは不可）
- 文字列は **ダブルクォート** で囲む
- 末尾のカンマ（trailing comma）は **不可**
- コメントは **書けない**

```json
// NG — JSONでよくある構文エラー
{
  'name': 'Alice',          // シングルクォートはダメ
  "age": 28,                // この行のカンマは問題ない
  "isAdmin": false,         // ← 末尾のカンマ（trailing comma）はダメ
}
```

<Callout type="note">
### JSONとJavaScriptオブジェクトの違い

JavaScriptのオブジェクトリテラルでは、キーにクォートを省略でき、シングルクォートも使え、末尾カンマも許容されます。しかしJSONは厳密で、これらは構文エラーになります。`JSON.parse()` でパースエラーが出たら、まずこの違いを疑います。

</Callout>

## JSONのデータ型

JSONで使えるデータ型は6つだけです。

| データ型 | 例 | 備考 |
|---|---|---|
| **文字列** | `"hello"` | ダブルクォート必須 |
| **数値** | `42`, `3.14` | 整数も小数も同じ |
| **真偽値** | `true`, `false` | 小文字のみ |
| **null** | `null` | 値がないことを表す |
| **配列** | `[1, 2, 3]` | 順序付きリスト |
| **オブジェクト** | `{"key": "value"}` | キーと値のペア |

JSONに **存在しない型** として、`undefined`、`Date`、関数、`BigInt`、`NaN`、`Infinity` があります。これらを `JSON.stringify()` に渡したときの結果は、型によって違います。

| 渡した値 | `JSON.stringify()` の結果 |
|---|---|
| `undefined`・関数（オブジェクトの値） | キーごと消える |
| `undefined`・関数（配列の要素） | `null` になる |
| `NaN`・`Infinity` | `null` になる |
| `Date` | ISO 8601形式の文字列になる |
| `BigInt` | **例外が投げられる**（`TypeError: Do not know how to serialize a BigInt`） |

```js
JSON.stringify({ a: undefined, b: NaN, c: new Date() })
// '{"b":null,"c":"2024-01-15T09:00:00.000Z"}'
// ← undefinedは消え、NaNはnull、Dateは文字列に

JSON.stringify([undefined, () => 1])
// '[null,null]'

JSON.stringify({ id: 1n })
// TypeError: Do not know how to serialize a BigInt
```

<Callout type="warning">
### 値が消えても、nullになっても、エラーは出ない

`BigInt` 以外は例外にならず、黙って消えるか `null` になります。「送ったはずの項目がサーバーに届いていない」ときは、その値が `undefined` になっていないかを確認します。`BigInt` を送りたいときは、`String(value)` で文字列にしてから渡します。

</Callout>

## JavaScriptでのJSON操作

### JSON.parse() — 文字列をオブジェクトに

```js
const text = '{"name": "Alice", "age": 28}';
const data = JSON.parse(text);
console.log(data.name); // "Alice"
```

### JSON.stringify() — オブジェクトを文字列に

```js
const user = { name: 'Alice', age: 28 };
const json = JSON.stringify(user);
console.log(json); // '{"name":"Alice","age":28}'

// 見やすく整形する（デバッグ用）
const pretty = JSON.stringify(user, null, 2);
```

## fetchでJSONを扱う

ブラウザの `fetch` APIでJSONを送受信する典型的なパターンです。

### GETでJSONを受け取る

```js
const response = await fetch('/api/users/1');
const user = await response.json(); // レスポンスボディをJSONとしてパース
console.log(user.name);
```

### POSTでJSONを送る

```js
const response = await fetch('/api/users', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json', // ← これが必要
  },
  body: JSON.stringify({
    name: 'Alice',
    email: 'alice@example.com',
  }),
});

const created = await response.json();
```

<Callout type="warning">
### response.json() は一度しか呼べない

`response.json()` はレスポンスボディのストリームを読み切るため、2回呼ぶと `TypeError`（Chromeでは `body stream already read`）になります。`response.text()` のあとに `response.json()` を呼んだ場合も同じです。デバッグでレスポンスを確認したい場合は、一度変数に入れてから使います。

```js
const data = await response.json();
console.log(data);      // デバッグ
processUser(data);       // 処理
```

ボディを2通りの方法で読む必要があるときは、読む前に [`response.clone()`](https://developer.mozilla.org/ja/docs/Web/API/Response/clone) で複製します。

</Callout>

## JSON以外のデータ形式

JSONが主流ですが、場面によっては他の形式も使われます。

| 形式 | 特徴 | 使われる場面 |
|---|---|---|
| **JSON** | 軽量・人間にも読みやすい | Web APIの標準 |
| **XML** | タグベース・冗長だが表現力が高い | SOAP API、設定ファイル、レガシーAPI |
| **フォームデータ** | HTMLのフォーム送信で使われる形式。2種類ある | フォーム送信、ファイルアップロード |
| **Protocol Buffers** | バイナリ形式・高速・型安全 | gRPC、マイクロサービス間通信 |
| **CSV** | カンマ区切りテキスト | データエクスポート、バッチ処理 |

```
// JSON
{"name": "Alice", "age": 28}

// XML
<user><name>Alice</name><age>28</age></user>

// URLエンコード形式（application/x-www-form-urlencoded）
name=Alice&age=28
```

フォームデータの2種類は、`fetch` の `body` に渡すオブジェクトで決まります。どちらも `Content-Type` はブラウザが自動で付けます。

| `body` に渡すもの | 自動で付く `Content-Type` | 向いている内容 |
|---|---|---|
| `new URLSearchParams({ name: 'Alice' })` | `application/x-www-form-urlencoded;charset=UTF-8` | テキストだけのフォーム |
| `new FormData(form)` | `multipart/form-data; boundary=...` | ファイルを含むフォーム |

<Callout type="column">
### なぜJSONが勝ったのか

2000年代はXMLベースのSOAP APIが主流でしたが、JSONはXMLに比べて構文がシンプルで、JavaScriptでは `JSON.parse()` だけでオブジェクトとして扱え、同じデータを表したときのサイズも小さくなります。REST APIの普及とともに、Web APIで最も使われる形式になりました。筆者の見る範囲では、新規のWeb APIでXMLを採用する例はほとんどありません。

</Callout>

## よくあるハマりどころ

### 1. 日付の扱い

JSONには日付型がないため、文字列として表現します。ISO 8601形式が標準です。

```json
{
  "createdAt": "2024-01-15T09:00:00.000Z",
  "updatedAt": "2024-01-15T12:30:00.000Z"
}
```

受け取る側で `new Date()` に変換する必要があります。

```js
const data = await response.json();
const createdAt = new Date(data.createdAt);
```

### 2. 数値の精度

JSONの仕様（[RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html)）は数値の桁数に上限を設けていません。精度が落ちるのは、JavaScriptが `JSON.parse()` で数値を `Number`（64ビット浮動小数点数）に変換するためです。`Number` が正確に表せる整数は `Number.MAX_SAFE_INTEGER`（9007199254740991）までで、それを超えると近い値に丸められます。

```js
JSON.parse('{"id": 9007199254740993}');
// → { id: 9007199254740992 } ← 1ずれる
```

エラーにはならず、値だけが変わります。そのため、IDに大きな整数を使うAPIは `"id": "9007199254740993"` のように文字列で返すことがあります。

### 3. Content-Typeを付けずにJSONを送る

`fetch` の `body` に `JSON.stringify()` の結果（文字列）を渡すと、`Content-Type` を指定しなかった場合は `text/plain;charset=UTF-8` が付きます。サーバー側のJSONパーサーの多くは `Content-Type` が `application/json` のときだけボディを解析するので、送ったJSONが読まれず、サーバーではボディが空として扱われます。送る側で `Content-Type: application/json` を明示します。

受け取る側は事情が違います。`response.json()` はレスポンスの `Content-Type` を見ず、ボディをJSONとして解析できるかだけで成否が決まります。

### 4. `Unexpected token '<', "<!DOCTYPE "... is not valid JSON`

`response.json()` で出るエラーのうち、特によく見るものです。

```
SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON
```

<SpeechBubble character="/images/question_woman_04_color.png" name="学習者">
JSONを返すAPIを呼んでいるのに、`<` なんてどこから出てきたの？
</SpeechBubble>

`<!DOCTYPE` はHTMLの先頭です。つまり、**サーバーがJSONではなくHTMLを返しています**。JSONの構文が間違っているわけではありません。HTMLが返る主な原因は次の4つです。

| 原因 | 返ってきているHTML |
|---|---|
| URLの間違い（パスのtypo、`/api` の付け忘れ） | 404ページ |
| サーバー側で例外が発生した | 500のエラーページ |
| 未ログインでログイン画面にリダイレクトされた | ログインページ |
| 開発サーバーのプロキシ設定が効いていない | フロントエンドの `index.html` |

調べるときは、DevToolsのNetworkタブでそのリクエストを選び、**ステータスコード**と **Response** タブの中身を見ます。コードで確かめるなら、`response.json()` の代わりに `response.text()` で読むと、返ってきた内容をそのまま表示できます。

```js
const response = await fetch('/api/users');
console.log(response.status, response.headers.get('content-type'));
console.log(await response.text()); // 返ってきた内容をそのまま表示
```

同じ系統のエラーに `Unexpected end of JSON input` があります。こちらは**ボディが空**のときに出ます。`204 No Content` のレスポンスに `response.json()` を呼んだ場合が代表例です。

| エラーメッセージ | ボディの状態 |
|---|---|
| `Unexpected token '<', "<!DOCTYPE "... is not valid JSON` | HTMLが返っている |
| `Unexpected end of JSON input` | 空 |
| `Expected property name or '}' in JSON at position 1` | キーがダブルクォートで囲まれていない |
| `Expected double-quoted property name in JSON at position N` | 末尾にカンマがある |

メッセージの文言はNode.js 24で確認したものです。ChromeもNode.jsと同じJavaScriptエンジン（V8）を使っています。FirefoxやSafariでは表現が変わります。

## 実務で使うfetchのパターン

ここまでの知識を組み合わせて、実務で使えるfetchのパターンを整理します。

### 基本: エラーハンドリング付きfetch

素の `fetch` はHTTPエラーでも例外を投げないため、ラッパー関数を作っておくとコードがすっきりします。

```js
async function apiFetch(url, options = {}) {
  const response = await fetch(url, {
    ...options,
    // headers は ...options より後ろに書く
    headers: {
      'Content-Type': 'application/json',
      ...options.headers,
    },
  });

  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(
      error.message || `API Error: ${response.status}`
    );
  }

  // 204 No Content はボディがない
  if (response.status === 204) return null;
  return response.json();
}

// 使い方
try {
  const user = await apiFetch('/api/users/1');
  console.log(user.name);
} catch (err) {
  console.error('取得に失敗:', err.message);
}
```

<Callout type="warning">
### `...options` を後ろに書くとContent-Typeが消える

`headers` を先に、`...options` を後ろに書くと、呼び出し側が `headers` を渡したときに `headers` プロパティごと上書きされます。`apiFetch(url, { headers: { Authorization: '...' } })` と呼ぶと、マージしたはずの `Content-Type` が無くなります。オブジェクトのスプレッドは後ろに書いたものが勝つので、`...options` を先に書きます。

</Callout>

### タイムアウトの設定

`fetch` にはデフォルトのタイムアウトがありません。時間だけで打ち切るなら、[`AbortSignal.timeout()`](https://developer.mozilla.org/ja/docs/Web/API/AbortSignal/timeout_static) を `signal` に渡すのが最も短い書き方です。

```js
try {
  const response = await fetch('/api/users', { signal: AbortSignal.timeout(10000) });
} catch (err) {
  if (err.name === 'TimeoutError') {
    console.error('10秒でタイムアウトしました');
  }
}
```

タイムアウトに加えて、「キャンセル」ボタンや画面遷移でも中断したい場合は、`AbortController` を使います。`controller.abort()` を好きなタイミングで呼べます。投げられるエラーの名前が、`AbortSignal.timeout()` は `TimeoutError`、`controller.abort()` は `AbortError` と異なる点に注意してください。

```js
async function fetchWithTimeout(url, options = {}, timeoutMs = 10000) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const response = await fetch(url, {
      ...options,
      signal: controller.signal,
    });
    return response;
  } catch (err) {
    if (err.name === 'AbortError') {
      throw new Error(`リクエストが${timeoutMs}msでタイムアウトしました`);
    }
    throw err;
  } finally {
    clearTimeout(timeoutId);
  }
}
```

<Callout type="note">
### なぜタイムアウトが重要か

タイムアウトを設定しないと、サーバーが応答しない場合にユーザーが延々と待たされます。APIのレスポンスが遅い場合に「しばらくしてからもう一度お試しください」と表示する方が、無限にローディングを見せ続けるよりユーザー体験として優れています。

</Callout>

### リトライの実装

ネットワークエラーや5xxエラーは一時的な場合が多いため、リトライが有効です。

```js
async function fetchWithRetry(url, options = {}, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const response = await fetch(url, options);

      // 5xxはリトライ対象、4xxはリトライしない
      if (response.status >= 500 && attempt < maxRetries) {
        await new Promise(r => setTimeout(r, 1000 * Math.pow(2, attempt)));
        continue;
      }

      return response;
    } catch (err) {
      // ネットワークエラーはリトライ
      if (attempt === maxRetries) throw err;
      await new Promise(r => setTimeout(r, 1000 * Math.pow(2, attempt)));
    }
  }
}
```

`Math.pow(2, attempt)` で **指数バックオフ**（1秒 → 2秒 → 4秒）を実装しています。待ち時間を伸ばしていくことで、回復途中のサーバーに届くリクエストの数を減らします。

ただし、多数のクライアントが同じ瞬間に失敗した場合、全員が同じ1秒後・2秒後に再送するので、リクエストの集中は残ります。これを避けるには、待ち時間に乱数を足して再送のタイミングをばらけさせます（**ジッター**）。

```js
const delay = 1000 * Math.pow(2, attempt) + Math.random() * 1000;
```

<Callout type="warning">
### POSTをそのままリトライしない

この関数はメソッドを見ずに再送します。`POST` は[べき等ではない](/books/http-and-web-api/02-http-methods#section-3)ので、1回目がサーバーに届いていた場合、再送でデータが2件作られます。リトライの対象は `GET` などのべき等なメソッドに限るか、べき等キーを併用します。

</Callout>

## DevToolsでJSONレスポンスを確認する

NetworkタブでAPIリクエストを選択し、**Response** タブまたは **Preview** タブを見ると、JSONレスポンスの中身が整形されて表示されます。

Previewタブではオブジェクトをツリー形式で展開でき、大きなレスポンスでも目的のフィールドを素早く探せます。

### Consoleでのデバッグ

DevToolsのConsoleで `fetch` を直接実行して、APIの動作を確認することもできます。

```js
// Consoleから直接APIを叩いて確認
const res = await fetch('/api/users');
const data = await res.json();
console.table(data); // テーブル形式で見やすく表示
```

`console.table()` は配列のデータをテーブル形式で表示するので、APIレスポンスの確認に便利です。

## まとめ

- <Marker>JSONは **キーと値のペア** で構成されるテキスト形式。Web APIの標準フォーマット</Marker>
- キーはダブルクォート必須、末尾カンマ不可、コメント不可
- `JSON.parse()` で文字列→オブジェクト、`JSON.stringify()` でオブジェクト→文字列
- `fetch` でJSONを送る際は **`Content-Type: application/json`** を明示する
- JSONには日付型がないため、**ISO 8601文字列** で表現するのが標準

- `Unexpected token '<'` は、サーバーがJSONではなくHTMLを返しているときのエラー。`response.text()` で中身を確認する
- 大きな整数は `JSON.parse()` で丸められる。`BigInt` は `JSON.stringify()` で例外になる
